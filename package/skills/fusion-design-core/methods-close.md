# 按工作模式收口

先引用任务诊断卡中的工作模式和证据动作集，再用对应规则收口。本文件不创建或重复执行证据：实际操作必须通过 [methods-execution.md](methods-execution.md) `EX6`，本文件读取同一动作 ID、执行状态和步骤账本；证据尚未运行时先回 EX6。每个证据项独立收口：

- `CORE_EVIDENCE`：随本轮研究、观察或测试产生证据，不等成品之后再补。
- `POST_ARTIFACT_ACCEPTANCE`：冻结成品版本后执行回归、对照或验收。
- `DEFERRED_NEXT_ROUTE`：本轮不执行，只检查责任人、触发条件、对象和程序是否就绪；不得写已验证。

同一工作包可有多项证据，必须分别记录结果。不要把“做实验”强加给直接制作，也不要用“已按稿”冒充方案有效。

工具产物按 [methods-tool-routing.md](methods-tool-routing.md) 分开验收：`LOW_FIDELITY_INTERACTION` 不能通过正式 UI 验收；Figma 路线的界面视觉以当前有效 Figma UI 主稿为准，经同包执行工作流完成设计后还原 Demo；本地路线以已明确选择的代码与预览版本为准；非界面视觉成品按独立视觉合同验收；`FIGMA_MOTION_PREVIEW` 不能通过正式动效成品和性能验收。

## 0. QA0 交付前三大维度综合验收与回炉修改闭环（用户可用性 × 审美与品位 × 设计标准）

任何设计产出（流程、交互、Figma UI、海报/运营图、动效/视频）在交付给用户前，**绝不能只做机械的“设计规范标准检查”**（很多符合 8px 网格、字号和对比度标准的页面依然用起来别扭、或者看起来呆板廉价）。

Agent 必须同时从 **「一、用户可用性审查（好不好用）」**、**「二、审美与视觉品位审查（好不好看）」**、**「三、设计标准与规范审查（准不准、齐不齐）」** 三个维度审查。每项写通过/不通过及依据，不打分；适用的三个维度和脚本检查均须实际完成。仅本页维度三明确限定的提供方文件名检查按其真实逐资产证据处理，仍保留原失败，不冒称脚本通过；其他适用失败不得据此豁免。

脚本 `"passed": true` 只说明该次命令实际覆盖的机械项过了，不证明未覆盖的数值或表达已验证。画面仍像线框、只换了背景色、信息归属或主次不清、决定文件里的材质在截图上指不到，维度二直接不过，整单不得交付。文字没有可见底板不等于信息归属不清，按 U3 检查实际分组与表达。禁止用分数把这种稿写成通过。

### 0.1 三大验收评价维度

#### 维度一：用户可用性审查（User Usability & Cognitive Walkthrough —— 真人用起来顺不顺、累不累、懂不懂）

跳出设计师视角，代入对本产品一无所知、处于真实使用情境（匆忙、单手、有顾虑）的目标用户，逐条审查：

- [ ] **1. 零解释可走通与低认知负荷（识别优于回忆）**：
  - 用户第一眼看到页面，能不能在 **3 秒内** 明白“这是哪、能干什么、我下一步点哪”？
  - 在当前页做决定时，是否把做判断必需的信息直接摆在了手边，而**不需要用户凭脑子去记上一页的数字、条件或规则**？
  - 一屏之内的信息分组是否控制在人的瞬时认知舒适区内（避免满屏同权重的密集模块轰炸）？
- [ ] **2. 心理模型契合与零黑话**：
  - 导航、标题、按钮和分类词，用的是**用户日常嘴里说的话**，还是产品/研发的内部系统黑话？
  - 界面形式是否符合有证据支持的用户预期？操作前的可见信息是否足以预判操作后的实际结果？
  - 按 U1/U6 核对原稿保留及制作中新添的文案，是否有实际理解、识别、判断或行动作用；删除、合并、改写或新增是否已有具体批准来源、准确版本和范围，实际文字是否与批准项一致。无效或含混文案先提出有依据的修改建议，未确认不擅自清理或记作已完成；必要规则、条件、单位及操作/无障碍标签仍完整，不能只查原稿而放过 AI 后加的无效或未确认文字。
- [ ] **3. 物理操作顺手度与省力原则**：
  - **能选不填、默认值聪明**：能可靠地选择、推荐或依照有效来源带出的内容，有没有要求用户重复输入或进行多余跳转？默认值的来源、适用性和可修改性是否明确？
  - **视觉不误导操作**：有没有为了视觉对称好看，把“执行操作”和“跳转页面”、“普通取消”和“危险删除”做成一样的样式，或者把不可点的标签做成按钮样式导致误触？
  - **触控与视线距离**：高频主操作是否在顺手热区？关联操作与报错是否紧贴触发位置，无需视线和手指大幅度来回跨越？
- [ ] **4. 情绪安全感与受挫自救**：
  - 涉及付钱、授权、删除或提交失败时，用户在犹豫的那一秒能不能立刻看到风险说明、费用明细或可撤回保障？
  - 遇到空状态、加载慢、报错或网络中断时，是否保留了用户辛苦填好的内容，并直接给出了“下一步点哪里自救”的人话出口？
  - 有没有为了短期数据硬塞打断用户主任务的弹窗、假倒计时或“拒绝比接受更难点”的算计感？

#### 维度二：审美与视觉品位审查（Aesthetic & Taste Critique —— 到底好不好看、有没有气场与质感、去 AI 廉价感）

规范合格不等于有美感。从平面构成、色彩关系、留白气场与反套路四个角度做审美把关：

- [ ] **1. 留白气场与正负形呼吸感（「间」与减法美学）**：
  - 先判断表达是否足够：关键内容区是否具备支持本轮目标的字形、图形、关系与空间节奏，还是只有一张完成的主图、其余仍是未设计的通用文字？后者回 V3/V5 补足需要的表达，再判断减法；克制不等于省略设计，丰富也不等于填满空白。
  - 页面或海报的留白是**积极的呼吸空间（引导视线、烘托主体）**，还是因为不敢留白而用边框、底色块、分割线把每个角落塞得满满当当？
  - **减法测试**：“如果删掉这个外框 / 背景块 / 装饰图标，画面会不会反而更干净高级、信息依然清晰？”——如果是，必须删掉；严禁出现“卡片套卡片再套卡片”的套娃堆砌。
- [ ] **2. 视觉重心、造型张力与视线韵律（聚焦层 × 信息层 × 色彩层）**：
  - 画面有没有一个一眼抓人的 **视觉重心（Hero Focus）**？字号阶梯是否拉开了有张力的反差（主标题与正文是否有足够跨度，而非温吞的 14px/16px/18px 平铺）？
  - 用户的视线从「第一眼焦点 → 核心判断信息 → 行动点」滑过的轨迹是否自然优美，还是满屏有四五个同样抢眼的色块/大字在互相打架？
- [ ] **3. 色彩关系、面积比例与画面干净度（防“脏、俗、粉、腻”）**：
  - **色彩面积与主次**：主导色、结构色与强调色的实际面积是否形成预期重心、信息主次和感受？60-30-10可作参考，不是所有表达的固定比例；大色面与强撞色按目标和控制质量判断，不直接等于廉价。
  - **色彩关系**：配图、背景、卡片与按钮是否形成有意的协调或对比，实际前景/背景组合是否可读？统一语言不要求所有区域同冷暖、同明度或同饱和度，不能为“同频”把有作用的反差全部中和。
- [ ] **4. 去 AI 塑料感（Anti-AI Slop）、头像角色与整体表达完成度**：
  - **避免模板化装饰**：渐变、图标、底板及材质是否服务本轮表达、信息识别与视线节奏，是否存在无意义重复或与概念脱节的通用装饰？功能图标核对真实库资产及同套系；表现图标、图形与局部装饰可按 V5/V7 由本轮主视觉派生制作或生成，须有对应风格依据、真实资产及最小尺寸辨识证据。需要的图标不因“做减法”机械删去，也不为了丰富度逐条追加。真实摄影仍按 IM 核对来源与使用方式。
  - **人物头像与角色形象审美四检（防丑铁律）**：① 有没有把欧美 B 端 SaaS 的“豆豆眼、僵硬橡皮泥秃头/大胡子塑料小人”错塞进国内 C 端或游戏界面？② 头像是否帶有突兀的纯黑背景块或抠图黑边？③ 同屏多个头像是否属于**同一套系（Same Pack / 统一画风、头肩比例、打光与底色）**，有无东拼西凑感？④ 入稿前是否已通过 `Read` 读图筛查确保五官灵动高颜值？
  - **视觉锚点与整体完成度**：画面有可识别的重心，其他关键区以符合其作用的文字、图形和节奏承接同一方向。视觉锚点不是唯一需要设计的区域，不能靠一处精致主图为其余未完成区放行；活泼或丰富的目标也不被统一改成克制。
- [ ] **5. 功能完备度、交互合理性与拒绝“半成品原型感”**：
  - **页面职责与功能完备度**：成品是否承担了已明确的完整页面职责，包含任务所需入口、内容、操作及状态；关键对象是否在实际尺寸下保持可辨识？
  - **交互控件合理性**：收集或选择信息所用的控件（下拉、Picker、弹窗、胶囊点选、跳页）是否符合用户直觉与省力原则？
  - **表达与风格到位**：信息分组、排版、图形及适用组件是否共同体现已确定的作用、主次和风格；需要容器/材质时是否真实落实？由留白和对齐建立的清晰分组同样成立，不以每条信息都有底板、边框或装饰为完成标准。
  - **主图之外的表达完成度**：按同一 DS2/V3/V5 记录，在实际尺寸逐项看主副标题、眉题/标签、关键内容区、主要按钮及适用图形的字形、字重、色彩、字距、行高、比例、形态、表面和空间关系；它们是否支持同一视觉方向且有主次。先对照 CT0 的明确制作要求核验实际资产和采用位置，未满足直接记失败，不由“普通字体可读”或“已有功能图标”代替。关系性内容的索引、含义与视觉组织分别检查；仅有编号和文字不自动通过。承担表达的文字仅换普通字族、控件只沿用默认实心外观或微改圆角时，须判断是否已满足目标并留实际画面依据；不足就返回对应方法，不能以参数齐全、主图精致或装饰数量替代完成度。
- [ ] **6. 同类真实竞品并排对比（`side_by_side.py`）**：
  - **先看画面，再查作者说明。** 用准确成图、本轮任务及有效用户反馈判断第一印象、传达内容、参与意愿的设计依据和具体缺陷，再回查决定及资产；不能先读“已完成/通过”后按其措辞找证明。可用独立审稿视角时不继承作者结论；没有该能力则按同样次序自审，不伪称独立评审或真人测试。
  - 对照范围服从本轮委托。局部修改或精确还原已有有效主稿时，以准确基线及受影响状态做实际对照，不为该项重开全页探索或新找外部标杆；需要形成新视觉表达的范围仍按下列适用参考检查。
  - 运行 `python3 scripts/side_by_side.py --shot <成品截图> --width <宽> --height <高> --refs <RR 存下的 2–3 张同方向真实界面截图> -o compare-r1.png`，用 `Read` 打开拼图。
  - 仅在 DS1「主视觉引领分支」的 KV 样张自审中，按其表达目标使用适用的主视觉、海报或编辑设计参考，引用同一来源记录；不把这次对比冒称完整界面验收。完整代表页及整套界面仍按真实界面参考检查。
  - 以设计总监视角回答三问：① 放在一起看，我们的完成度能不能达到成熟上线产品水准；② 逐个功能区块对照标杆，信息层级、字体排版、配图或材质差在哪；③ 哪里显得土、简陋或有 AI 模板味。
  - 只要完成度不如标杆或漏掉核心模块，必须退回修改并出下一轮对比图，严禁自评放水。

营销/活动另按 CC3 核对完整表达：不读设计说明，能否从标题、主体图形、核心参与区与行动区指认本案主张和组织关系；关键图形是在帮助这项活动表达，还是只有通用符号与题目关键词插图。V3 的字形质量、V5 的功能辨识与主题表现分别判断，生成资产存在、同套同色及逐字准确不能自动放行。按 U6 连读文案并核对点击预期与真实流程；已发现而未批准修改的问题保留待决定，不能记作质量通过。人的明确活泼或丰富目标须在准确画面中有依据，不能统一收成克制，也不以装饰数量替代。

优化存量设计时，在授权范围内用准确旧稿与新稿并排，分别指出关键区域的改善、退步和未解决问题；再结合适用成熟参考判断完成度。不能只列新资产或已改参数，回避整体是否变差；没有可指认改善、或新增问题抵消原改善时回查最早受影响决定并重审。有限范围不能支持整体优劣结论时明确范围，不把自审判断冒称真实用户效果。

#### 维度三：设计标准与工程规范审查（Design Standards & Spec Compliance —— 准不准、齐不齐、能不能 1:1 落地）

在“好用”且“好看”的基础上，核对专业基本功与工程可交付性：

- [ ] **1. 平面四要素、栅格精度与自动化几何体检（强制运行 `scripts/ui_geometry_audit.py`）**：
  - 对齐轴线严整、亲密性（组内间距 < 组外间距）严格成立、同类对象重复规则一致；同类按 U3 的语义角色、用途与状态判断，需比较的内容维度对齐，有依据的职责/状态变体有记录，不能任意换样式；
  - 所有横排条强制 `align-items: center`；图标按钮里放成品 SVG 文件且光学居中（不用 `<` `>` 等文本字符）；
  - **凡产出 HTML/Web 界面，交付前必须运行 `python3 scripts/ui_geometry_audit.py <html文件> --width <目标宽> --height <目标高> --expect <区>=<九宫格位置> ...`**，且每个顶层功能区已按 `U3` 标 `data-zone`，`--expect` 逐区写入 `design-decisions.md` 第 2 块的位置。消费级主屏加 `--consumer`；首页再加 `--page-type home`；第 2 块写了视觉主角面积的加 `--hero <区>=<百分比>`。报 `HOME_IS_ONE_OBJECT`（首页看不出产品会给出什么）或 `LICENSE_ON_SCREEN`（授权句画在界面上）也是 FAIL。脚本优先用 Playwright 按目标尺寸实测；实测尺寸和目标不同会报 `VIEWPORT_MISMATCH`，区的位置和第 2 块不同会报 `ZONE_POSITION_MISMATCH`，区内内容压到别的区会报 `ZONE_CONTENT_INTRUSION`，主角区比写下的面积小会报 `HERO_AREA_SHORT`，第一屏是输入框而最大的图不足屏幕 40% 会报 `FORM_SCREEN`，都算 `FAIL`。脚本自动实测 DOM `getBoundingClientRect()`，若报出 `ZONE_MARKUP_MISSING`（没标功能区，无法检查分区碰撞）、`ICON_RAW_TEXT_GLYPH`（字符冒充图标）、`ICON_INLINE_HAND_DRAWN`（按钮里是手写 SVG 路径）、`ICON_CHILD_OFF_CENTER`（图标未居中）、`HEADER_VERTICAL_MISALIGNMENT`（横排条未垂直居中）、`ZONE_BOUNDING_BOX_COLLISION`（功能区重叠打架）、`FORM_SCREEN`、`HERO_AREA_SHORT` 或 `BANNED_HAND_DRAWN_SVG_AVATAR`（代码手画人脸），一律判定为 `FAIL` 并回炉，直到脚本 `"passed": true`。`FORM_SCREEN` 和 `HERO_AREA_SHORT` 同时算维度二第 5 项不过，退回画面级配方和视觉主角，不许只改颜色。几何对齐过了、色值过了，灰条测试和并排对比仍要做。若报 `AVATAR_CULTURAL_FIT_CHECK`（`WARN`），说明用了素材库 3D 人物头像：读图确认画风与产品文化一致、同屏同一套系即可保留，否则转 AI 同母体成套生图。3D 图标、道具、徽章不在此检查范围内。
- [ ] **2. 风格规格与排版规范**：
  - 实际 Hex 色值、圆角/切角阶梯、阴影/毛玻璃/金属石材边框参数、字族与字阶严格匹配本轮有效规格。预设路线沿用 `V0` 所选风格编号或 `style-presets/` 参数包；DS1「主视觉引领分支」按 DS2 从已确认 KV 与有效品牌规范提取的任务规格逐项对照，推导值保留来源、依据和适用范围，不伪称品牌事实。按正式主稿精确还原时，仍以该准确版本的值和资产为准。
  - 颜色有适用的语义角色，对比度运行 `python3 scripts/color_intelligence.py contrast --css <页面引入的主题 CSS>` 并按 CI5 核对实际覆盖；渐变、纹理、图片和透明叠加另查文字/图标所在的最不利背景与状态，不用纯色脚本结果代替。颜色、效果与圆角引用本轮集中规格。常规文字核对真实字重、覆盖与可读行距，不伪造字体文件能力；表达性字形允许按 V3 设计轮廓、排列及行间关系，以准确文字、实际尺寸辨识和不遮挡为依据，不受“所有多行只能增行高”的一刀切限制。金额与核心数据保留真实值和适用数字规则。

### 0.1 补充：信息作用到实际画面的承接

### 0.3 交付前强制终审（最后一步；用整套方法论验收成品，不可跳过）

成品由整套方法论推出，验收也用整套方法论：问题与价值、成功标准、流程、交互、UI、视觉、动效、验证，逐层对照**最终成品**检查。条目见 `SKILL.md`「审查不通过必须改完再交」的 A–H 共 25 条。几何脚本只覆盖 UI 层的对齐、分区碰撞和图标来源，跑过脚本不等于审过。

1. **先以设计总监视角看成品。** 用 `Read` 打开成品截图（Figma 稿用导出图），核对是否达到最初的设计目标、功能与交互控件是否完备合理、风格与材质是否到位，并用 `side_by_side.py` 与同类成熟产品截图并排比对；仅 DS1 KV 样张按 0.1 使用适用的视觉参考。若交付了 HTML/代码界面，再运行 `python3 scripts/ui_geometry_audit.py <html文件> --width <目标宽> --height <目标高>`；多页面的预设路线运行 `python3 scripts/style_consistency_audit.py <所有页面> --preset <预设>`，KV 推导规格路线运行 `python3 scripts/style_consistency_audit.py <所有页面>` 并按 0.1/DS5 补齐 DS2 逐项数值与状态证据，两项均须通过；对比度运行 `python3 scripts/color_intelligence.py contrast --css <主题CSS>`、无障碍运行 `python3 scripts/a11y_audit.py <html文件>`。可操作 Demo 还要按主路径实际点一遍，包括一个失败分支。不看图、不走路径，不算审过。
2. **本轮用过的每个方法，拿它细则里的「完成证据」对照成品再验一遍。** 逐项核对已用方法要求的状态、分支、恢复及其他适用结果。用过却没验 = 未终审。
3. **A–H 逐条写「过 / 不过 / 不适用」。** 每条带一处成品上能指认的位置，禁止写「整体协调、符合规范」。纯海报没有流程和交互时，C、D 和 E 里不适用的写原因；A、B、F 和 H 仍要审。
4. **适用项未通过就修改并重审。** 画面对照结论与验收状态必须一致，不能同时记录完成度不足和审美通过。脚本保留原始结果，适用失败修正；仅提供方文件名项按维度三已定义的受限核验处理，不影响其他失败。按 `0.2` 回到最早受影响方法，修正后重新渲染并复核受影响项，不重复未受影响检查。未解决的问题不得用自评通过或延期优化声明代替。
5. **结果写进交付的「任务诊断」。** 缺一层，或任何一条不是「过 / 不适用」，都不得交付。
6. **用户确认本轮方案可复用时**，按 [methods-resource-routing.md](methods-resource-routing.md) `AM` 入库：`asset_memory.py deposit ... --confirm`。未确认不入库。

## 0.4 代表页与最终人工确认

本节将原 QA0 提前用于每次设计成果展示，并保留整套完成后的终审；不是另建一套审美标准。适用于设计与视觉优化交付，不将方法研究报告误作多页面设计。

### 方向样张与正式代表页的边界

必要前置完成后，可按 [DS1](methods-style-engine.md) 在独立草稿制作方向样张，先实际渲染、执行适用 QA0、自我校正，再供人选择。方向样张只解决视觉方向，未覆盖范围明确记录，不称完整代表页验收或整套通过。用户选择方向后仍需完成完整代表页、自审并明确确认其扩展用途；不得把方向选择直接记为 `REPRESENTATIVE_CONFIRMED`。原多页扩展及最终确认不变。

候选均未接受时按 DS1 的具体反馈分支定位原因和倾向，修订后仍须自审并回到原选择点；已认可部分按范围保留，不以再次出图代替理解反馈，也不把未选状态记作批准。

主视觉引领任务按 DS1 条件分支执行，在同一记录保留 AI 的必要分析、概念/方案推导及来源依据，按有效 TR0 路线制作实际 KV，自审后供人看图选择，不强制先请人选择文字方案。工具路线、关键事实与业务取舍仍按原规则确认。KV 仅是方向样张，不再另凑 2–3 个整页方向；AI 推导与 KV 确认均不能代替完整代表页、自审或其扩展确认，也不放宽正式主稿精确还原要求。用户明确只委托纯文字方案咨询时，在该范围收口，不追加 KV 制作。

### 多页面：先完成一个代表页

1. 清点本轮页面与关键状态，选择一个最能检验核心任务、视觉语言、内容密度和主要组件的页面。说明选择理由；不能故意挑最简单的登录页或空状态绕过主体设计。可提前做整体流程、页面职责、依赖和共享资源规划，但不在代表页确认前批量制作其余页面的正式视觉稿。
2. 将代表页做到本轮要求的完整保真度，包含完整页面内容与核心状态；只做首屏、灰框、风格板或文字说明不能替代完整代表页。需要依赖未制作页面时注明范围，不能谎称端到端链路已验证。
3. **给用户看之前，必须执行原 QA0 的三维审查**，尤其完整执行维度二的审美检查和真实参考并排对比；所需脚本、操作回归与 CC5 按本页适用范围执行。多页一致性尚无对象时记录延期到整套验收，不虚报通过。
4. 截图或导出必须来自实际渲染的准确版本、目标设备尺寸；实际打开截图和并排图，逐项指出构图重心、比例、疏密节奏、字体层级、色彩、图片裁切及清晰度、材质和组件细节中的具体问题。选择与目标职责/表达相符的成熟参考，禁止以明显较弱或无关样本自证通过。用了预设、图库或组件不构成审美通过证据，几何脚本也不能替代看图。
5. 有问题先修改，再重新渲染、看图与复核；影响其他审查项时重跑相应检查。记录“问题位置 → 原因 → 修改 → 修改后证据”，发现的问题未解决不能标通过。渲染、读图或必要检查无法执行时明确记录未完成及阻断，不将未审稿当作已审成果请求确认。
6. 自审通过后展示可查看的代表页、准确版本、简短的审查与修正结果，并明确请求用户确认是否以此为基础扩展其他页面。状态为 `WAIT_REPRESENTATIVE_CONFIRMATION`，本轮停止扩展，等待用户明确回复；异步问题发出后也不得先做其余页面。选定风格、工具返回成功、Agent 自评通过、用户未回复，都不是代表页确认。
7. 用户提出修改时，修改代表页并重新自审后再次请求确认；明确确认后记录原话/来源、确认版本和范围，状态为 `REPRESENTATIVE_CONFIRMED`，将该版本作为后续共享视觉基线。若后续需显著改变已确认视觉方向或核心交互，先修订代表页、自审并重新确认受影响基线，再扩展。

### 扩展后：整套自审，再最终人工确认

1. 以已确认代表页扩展其余页面，允许按各页职责调整布局，不机械复制同一模板。每个新增页面在展示前执行适用的 QA0 与审美校正，不能让一个通过的代表页为其余页面代审。
2. 全部完成后，针对准确版本重新执行原 0.3 全套终审，覆盖全部页面、关键状态、跨页视觉一致性和完整主路径及失败分支；问题改完再审。确认后的代表页若被共享样式改动影响，也要重新核验。
3. 自审通过后提供整套可查看成果、页面覆盖范围和简短验证结果，明确请求最终人工确认。状态为 `WAIT_FINAL_CONFIRMATION`；只能表述为“设计及自审完成，待最终确认”，不得称为用户已验收。
4. 收到明确最终确认后，记录确认版本和范围，状态为 `FINAL_CONFIRMED`。若有修改意见，修复并重审受影响页面与跨页关系后，再请求最终确认。用户最终确认不替代自审，自审通过也不替代用户确认；可复用资产入库仍遵守原授权条件。

单页面任务直接执行本页 QA0、自我校正与最终人工确认，不人为增加一次代表页确认。上述记录写入现有 `design-decisions.md` 和步骤账本：阶段、页面/状态范围、版本、截图/并排图路径、QA0 结果、修正记录、人工确认状态与来源。检查未执行写未执行，不得把计划写成证据。

## 1. 直接制作验收

适用：范围确切、上游有效、局部低风险。

检查：

- 任务清单逐项完成。
- 未修改范围外内容。
- 文案、尺寸、状态、资产来源符合输入。
- 受影响页面或组件做基本回归。
- 未将假设性优化混入制作。

**完成证据**：修改前后对照、文件/节点、覆盖清单、回归结果。  
**决策**：交付 / 修正。  
不要求用户研究或价值实验。

## 2. 局部优化验收

适用：问题位置已知，修改局部设计决定。

检查：

1. 写明原问题和受影响决定。
2. 对比修改前后：问题是否被直接解决。
3. 回归受影响路径、共享组件和关键状态。
4. 检查是否引入新的理解、操作或一致性问题。
5. 若优化目标是行为提升，定义观测指标，但不把静态检查称为行为验证。

**完成证据**：前后对比、受影响范围、回归清单；如有用户/数据则附行为证据。  
**决策**：交付 / 继续验证 / 回退。

## 3. 问题探索收口

适用：问题、用户、情境、价值或成功判断未知。

检查：

- 事实、解释、假设分开。
- 核心判断可追溯到材料。
- 已形成可设计的问题和可观察成功。
- 未确定内容列最小补证。
- 尚未形成方案时，不用视觉稿冒充探索完成。

**完成证据**：问题卡、证据索引、主要洞察、待验证假设、下一决策。  
**决策**：进入流程/概念设计 / 补研究 / 停止。

## 4. 方案验证收口

先确认子型。

### 4.1 验证准备

适用：本轮只交测试就绪载体，正式验证未获授权、未排期或暂无样本。

检查：

- 待验证判断及明确不验证项已写清。
- `TEST_INPUT`、代表性内容、路径、关键失败和版本已冻结。
- PROTO1 预测试通过，不需要主持人解释才能走通预定脚本。
- 原型完整性以 `POST_ARTIFACT_ACCEPTANCE` 在本轮收口。
- 正式验证以 `DEFERRED_NEXT_ROUTE` 记录责任人、样本、触发条件、程序和结果将改变的决定。

**完成证据**：冻结原型、预测试记录、已知模拟/限制和延期验证合同。  
**决策**：测试就绪 / 修正载体 / 因缺输入阻断。  
测试就绪时动作标 `DONE_PREPARED`、外部执行状态标 `PREPARED`；被测决定保持 `TEST_INPUT`。没有真人观察记录，不得写 `DONE/EXECUTED`、已验证、继续投入或停止。

### 4.2 验证执行

只选能回答当前判断的一种主验证。仅将待验证判断直接对应的决定标为 `TEST_INPUT`；测试载体涉及但本轮不判断的决定保留原状态，必要时标 `FROZEN`，不得批量覆盖。测试前不重开，结果再决定回到哪项。

#### VAL 共用执行合同

所有 VAL1–VAL4 都必须使用 [methods-execution.md](methods-execution.md) `EX6` 的同一证据动作和生命周期：

- `PLAN_ONLY`：只有 D9-PLAN、筛选/覆盖、脚本、同意说明和记录模板。
- `PREPARED`：冻结对象、合格参与者或真实交付对象、排期、材料和记录方式已就绪，但尚无真实场次。
- `EXECUTED`：真实验证或人工交付已经发生，并有场次 ID、场次头、逐步观察和实际结果。

开始前冻结：

```text
证据动作 ID / VAL 类型：
待验证判断 / 明确不验证：
D9-PLAN 版本：
测试对象及冻结版本：
目标行为群体 / 纳入与排除条件 / 筛选依据：
计划覆盖的人群、情境、平台、任务和高风险条件：
样本与停止规则及其风险深度依据：
成功 / 失败 / 无结论信号：
允许提示、禁止提示和中性提示规则：
参与同意 / 记录与录制同意 / 敏感信息处理：
结果将更新的决定：
```

每个真实场次记录：

```text
场次 ID / 执行状态：
日期、时间、时区 / 方式与情境：
参与者代号 / 行为群体 / 筛选依据：
主持人 / 记录者：
对象、原型或交付版本：
任务及起始状态：
参与同意 / 录制同意：
逐步行为、原话、提示、结果与证据位置：
程序偏差、中止、隐私或安全事件：
```

样本、覆盖和停止完全引用 N4 的 D9-PLAN 与风险深度，不设统一人数。继续执行不再改变当前判断、预定覆盖已满足且高后果冲突已处理时才可停止；程序失效、覆盖不足或信号互相冲突时标 `NO_CONCLUSION` 或补证。`PLAN_ONLY/PREPARED` 不能产出验证结论；没有场次 ID 和观察记录不能标 `EXECUTED`。

#### VAL1 概念理解

**触发问题**：用户是否理解方案解决什么、是否与自己的任务相关？  
**最低输入**：一句概念、故事板或可阅读概念原型；目标行为群体。  
**跳过**：任务是直接制作/还原，或概念含义已由近期证据确认。

**步骤**：先让用户复述“这是什么、对谁、何时用、结果是什么”；再问他会在什么真实情境采用。禁止先解释标准答案。

**产出**：用户复述、误解点、采用/不采用情境。  
**完成证据**：逐场复述和误解可定位，并按 D9-PLAN 预先定义的成功、失败、无结论信号判断；不得测试后临时用“大多数”改写通过门。  
**不得替代**：口头“喜欢”不能证明会用或能完成。

#### VAL2 任务走查

**触发问题**：用户能否在不被教学的情况下完成关键任务？  
**最低输入**：通过 `PROTO1` 检查的冻结版本、可操作主路径、D5 反馈、关键失败分支、真实任务原话。  
**跳过**：没有交互任务，或本轮只验证概念理解。

**步骤**

1. 给目标，不给操作步骤。
2. 观察卡点、误操作、成功/失败行为。
3. 卡住后才给中性提示，并记“需提示才过”。
4. 记录关键状态和失败出口。

**产出**：逐步观察记录、完成/失败、提示点。  
**完成证据**：版本、样本、任务脚本和路径证据齐全。  
**不得替代**：主持人演示、截图或静态评审。

#### VAL3 内容与信任

**触发问题**：用户是否看懂关键信息，并有足够证据做决定？  
**最低输入**：半真实内容、关键承诺、风险/证据和目标用户。  
**跳过**：问题与内容/信任无关，或只需验证任务操作。

**步骤**：先测无提示理解；让用户指出做决定所依据的信息、仍担心什么、哪些承诺不可信；比较内容或证据变量时保持结构一致。

**产出**：理解偏差、信任来源、缺失证据、阻断决定。  
**完成证据**：用户能指出而非被提示出价值和证据。  
**不得替代**：视觉精美、品牌偏好不能冒充信任证据。

#### VAL4 人工价值交付

**触发问题**：自动化、智能能力或重开发在投入前是否真的产生价值？  
**最低输入**：明确输入、人工可交付结果、成功行为和伦理/告知边界。  
**跳过**：价值已由真实功能验证，或人工模拟会误导/违规。

**步骤**：用人工或半人工交付目标结果；记录用户愿意提供什么输入、等待多久、怎样判断能用、是否再次使用；不得谎称不存在的自动化已完成。

**产出**：输入要求、结果标准、价值行为、自动化必要性。  
**完成证据**：用户实际使用结果而非口头意愿。  
**不得替代**：技术可行性、安全和规模成本评估。

#### 通用测试脚本

```
待验证判断：
成功 / 失败行为：
任务原话（给目标，不给步骤）：
观察重点：
禁止提示及中性提示规则：
回顾问题（只保留回答当前判断所需）：
```

无真人场次时只能交 `PLAN_ONLY/PREPARED`、预测试和失败点，不得写 `EXECUTED` 或“已验证”。

#### 学习决策

只有证据动作达到 `EXECUTED` 且满足 D9-PLAN 的覆盖与停止规则后，才记录证实、证伪、意外，并四选一：继续投入 / 修正方案但保留问题定义 / 重写问题定义 / 停止。`PLAN_ONLY/PREPARED/NO_CONCLUSION` 不进入四选一。

同时更新受影响决定：

- 支持且证据范围足够：`TEST_INPUT → CONFIRMED`。
- 证伪：`TEST_INPUT → MISSING/RESOLVE_NOW`，回到最早受影响决定。
- 无结论：`TEST_INPUT → ASSUMPTION` 或 `BLOCKED`，不得写已验证。

**完成证据**：测试版本、样本、观察记录和明确决策。  
“喜欢”“看起来流畅”不是完成证据。

## 5. 设计还原/交付验收

适用：依据正式主稿或规格还原、扩展、交接。

检查：

- 来源文件、Frame/组件、版本和资产可追溯。
- 布局、字、色、间距、图片、状态和交互逐项对照。
- 关键行为动态走过，不只看截图。
- 已覆盖、未覆盖、无法验证分别列明。
- 任何例外或偏差有明确依据；缺资产不降级成占位成品。
- 精确还原任务存在未经授权的差异时，必须修复或标阻断，不能带差异交付为完成。

**完成证据**：准确节点/版本、逐项对照、动态检查记录、残留差异。  
**决策**：交付 / 修正 / 因缺输入阻断。  
一致性通过不代表产品方向已验证。

## 6. 行为放大（仅当任务明确要求）

先定义关键行为、基线、目标和反指标。一次只验证一个改动。

损耗审计：

- 是否打断主任务？
- 是否使用恐惧、羞耻或虚假稀缺？
- 拒绝是否比接受更难？
- 是否造成误触或质量下降？

任一为是：修改方案或停止。不到“目标用户做出关键行为且价值点匹配”不做大规模放大。
