# UI 方法库

UI 方法只解决已知职责内的信息表达与操作表现，不能替代未解决的流程或交互决定。
正式 UI 方案按 [methods-tool-routing.md](methods-tool-routing.md) `TR3` 与 [methods-visual.md](methods-visual.md) `VT` 分流。制作载体由同包 [Figma执行工作流](../fusion-figma-workflow/SKILL.md)恢复或收集：已有本产品Figma主稿或已选Figma时，先在Figma设计、精修，再还原Demo；B端或只换文案也不自动改变此路线。明确选择本地代码时复用组件与配方。UI与界面视觉组成同一分支，不固定另开视觉阶段。

## U0 UI 落地前置分流（存量延展 / 纯 B 端公开库快搭 / C 端 0→1 视觉决策）

**触发问题**：页面职责、信息层级（U1–U3）与所用组件类型（U4）明确后，采用哪条路径把界面快速、准确地搭出来？  
**最低输入**：页面职责、信息结构、产品属性（B 端 / C 端、国内 / 国际化）及是否存在现成相关页面。  
**跳过**：任务仅改文案或仅做静态规范审计。

**分流步骤**

1. **第 1 问：有没有现成的相关页面或既有设计规范？**
   - **有（存量延展）** → 走 **路线 1：存量延展模式**。
     - 从现有 Figma 主稿、截图或线上页面直接提取 **5 个视觉常量**：主色与辅助色、背景与卡片层级、圆角大小、字号阶梯、图标粗细与风格。
     - 直接复用既有组件拼装新页面，**不重新选风格**；只补现有页面未覆盖的新组件或新状态。
     - 仅当用户明确要求“本次顺便改版升级视觉风格”或“把产品改成某某风格”时，才转入 [methods-style-engine.md](methods-style-engine.md)：先探索 3 个方向，用户确认后再批量改代码（`DS1`）。
   - **没有（从 0 到 1 新建）** → 进入第 2 问。
2. **第 2 问：这是纯 B 端/中后台，还是 C 端/强品牌体验产品？**
   - **纯 B 端（企业中后台、内部系统、数据管理台、标准 SaaS 后台）** → 走 **路线 2：公开组件库快搭模式**。
     - 不做繁琐的感性视觉风格探索，直接按生态推荐并绑定成熟公开组件库：

| 生态 / 场景 | 默认推荐连接的公开组件库 | 视觉与组件特点 | 适用 B 端类型 |
| :--- | :--- | :--- | :--- |
| 国内标准企业中后台 | `Ant Design` | 复杂表格、树形、穿梭框、多级表单最全，蓝白理性，研发开箱即用 | ERP、CRM、政务/金融中后台、复杂审批与管理系统 |
| 国内现代清爽办公/数据台 | `Arco Design` / `TDesign` | 间距舒适、色彩温和、Figma 与代码组件对齐度高 | 协同工具、内容管理后台（CMS）、营销与数据运营平台 |
| 国际化 SaaS / 现代 AI 工具后台 | `shadcn/ui`（Radix + Tailwind） | 极简黑白灰 + 1px 细边、现代克制、无传统后台沉重感 | 出海 SaaS、AI 工作台、开发者后台、现代轻量 B2B 产品 |
| 海外传统企业 / 跨端系统 | `MUI` / `Fluent UI` | 遵循 Google 或桌面办公习惯，高密度数据控件成熟 | 海外企业内部系统、桌面端重度专业软件 |

     - **不问用户，Agent 直接定这 3 件事后开工**：① 组件库：项目已有技术栈或组件库就沿用，否则按上表的生态与场景选；② 主色：已知品牌色就替换，否则用组件库默认色并标注“可替换为品牌色”；③ 密度：表格、审批、数据密集型页面用紧凑 Compact，其余用标准 Default。交付时一句话说明这三项选择。组件库的主题从 `style-presets/` 直接取，不手调：Ant Design 用 `ant-design`，Material 用 `material-3`，shadcn 用「企业中后台」或「极简 SaaS」风格族里的主题。应用方式见 [methods-style-engine.md](methods-style-engine.md) `DS3`。
   - **C 端产品 / 游戏 UI（或需要强品牌差异化的产品官网 / 游戏化活动页 / B 端 C 化体验产品）** → 走 **路线 3：0→1 风格库（国际化 8 种 / 国内 8 种 / 游戏 10 种 / 通用质感 6 种）与 6 维视觉决策漏斗**（见 [methods-visual.md](methods-visual.md) `V0`）。风格选定后，按 [methods-style-engine.md](methods-style-engine.md) 取出整套预设和绑定的线上资源，批量应用并验收跨页一致性。

**产出**：UI 落地方案分流结论（路线 1 / 路线 2 / 路线 3）及绑定的组件库或风格决策入口。  
**完成证据**：存量迭代未误走 0→1 重选风格；纯 B 端已绑定公开组件库与密度；C 端 0→1 已进入语境过滤与风格决策漏斗。  
**不得替代**：U1–U4 的信息分级与组件功能判断（先定用什么组件解决任务，再定用什么库或风格呈现）。

## U1 最少信息分级

**触发问题**：用户先看什么，完成任务最少需要什么？  
**最低输入**：页面职责和信息清单。  
**跳过**：有有效 UI 主稿且任务仅还原。

**步骤**

- L1：不知道它就不懂页面或无法做主判断；一页 1–2 项。
- L2：完成主行动所需。
- L3：帮助、次要入口。
- L4：元数据。
- 全部都重要时重新删减或分组。

**产出**：信息清单与 L1–L4。  
**完成证据**：能说清每一层为何存在。  
**不得替代**：页面职责。

## U2 单一主行动

**触发问题**：用户下一步该做什么是否明确？  
**最低输入**：已确认的主行动。  
**跳过**：纯阅读、无行动页面。

**步骤**

1. 主行动与职责表一致。
2. 同组只保留一个实心强调；其余降级或移位。
3. 主行动至少在面积、字重、对比中满足两项更强。
4. 危险动作不与正常推进同等强调。
5. 运营和装饰不得隔开关键判断与主行动。

**产出**：主/次行动层级。  
**完成证据**：2 秒内能指出下一步。  
**不得替代**：用强视觉掩盖错误行动。

## U3 对比、亲密、对齐、重复（含防错位、防碰撞、防散装布局硬约束）

**触发问题**：界面是否可扫读、可分组、一致，且不存在元素错位、重叠打架或同类组件长相不一？  
**最低输入**：结构稿或现有页面。  
**跳过**：非界面资产。

**步骤**

1. 冻结修改前对象和版本，按页面或区域建立审计记录。
2. 修改前、修改后分别记录：阅读顺序、组内 / 组外间距、对齐轴、使用的 spacing token、重复规则、例外及理由；没有正式 token 时标缺口，不自行命名。
3. **对比**：眯眼先看到对象、关键判断和主行动；装饰先被看到则减噪。
4. **亲密**：
   - 组内间距小于组外。说明某个对象的标签、错误、计数、结果，必须贴着它所属的对象或容器，不能裸字悬空在背景上（例如表单报错飘在两个输入框中间、商品角标离开商品卡、游戏里的牌型结果飘在半空）。
   - **同一状态只在一个位置反馈**：同一件事（已选几项、当前结果、校验状态）全屏只出现一次，不在对象上贴一个、在按钮上方再写一行同样意思的话。
5. **对齐**：
   - **先分区，再摆元素**：多区域页面（工作台、看板、仪表盘、地图页、播放器、游戏 HUD、横屏页面）先用 CSS Grid / Flex 划出互不侵入的功能区，每个顶层功能区写上 `data-zone="<区名>"`。区内元素跟随所属区域布局，禁止整页散装 `position: absolute` 盲写坐标。可变长内容（列表、手牌、标签组、消息）在自己的区内滚动、折叠或缩放，不能越界压住别的区。主操作组锚定在所在区的对齐轴上，不被可变内容挤偏。
   - **信息坐进容器，不飘在底上**：每一组要读的信息（标题、人数、状态、操作）放进所选风格自己的容器：卡片、名牌、木沿、标签。禁止把这些字直接写在页面背景上。「直接制作」也不跳过这一步。容器还没定，不许上色。
   - **横排条垂直居中**：顶栏、导航条、工具条、胶囊信息条都用 `display: flex; align-items: center;`，图标按钮和文字共用同一条水平中线（`centerY` 偏差 $\le 1\text{px}$）。单个图标按钮旁边不堆上大下小两行标题（第一行会高于按钮中心，看起来像按钮掉下去了）；次要信息用 `·` 分隔放同一行，或放进独立副栏。
   - **图标按钮光学居中**：不用 `<`、`>`、`+`、`×`、`⚙` 这类文本字符充当按钮图标（字体 baseline 会让它偏左或偏下）。按钮用 `display: inline-flex; align-items: center; justify-content: center; line-height: 0;`，里面放 IconScout 或成熟图标库下载的成品 SVG 文件（`<img>`、`<use href="assets/….svg">`，或配方库的 `<span class="r-ico i-名字">`：用 `component_recipe.py icon-css` 把文件转成 data URI 遮罩，能跟文字同色，`file://` 打开也不丢），不自己手写 `<path>`。
6. **重复**：
   - 同类对象用同一套结构、样式和相对间距：列表项、卡片、席位、联系人、商品、表格行，各自内部的头像、名称、数值、标签位置完全一致。禁止同类里一个带框、一个不带框、一个换了颜色。

**产出**：调整后的层级与间距规则，以及含阅读顺序、组内 / 组外间距、对齐轴、spacing token、重复规则和例外的修改前后审计记录。  
**完成证据**：眯眼、分组、对齐和一致性检查通过，且通过 `scripts/ui_geometry_audit.py` 自动几何检测（零重叠碰撞、Header 与图标 `centerY` 误差 $\le 2\text{px}$、同类组件结构一致）；每项修改可回溯修改前问题与修改后规则，所有例外有理由。  
**不得替代**：可用性测试。

## U4 组件

**触发问题**：用什么控件最直接地完成已知任务？  
**最低输入**：用户意图、数据量、选择数量和后果。  
**跳过**：组件由既有设计系统和主稿明确指定。

**选择**

1. 对每个操作填写决策轴：用户意图、候选数量与是否已知、单选 / 多选、输入 / 选择、使用频率、后果、可逆性、设备与输入方式、数据量及增长、可访问性要求、可复用的设计系统组件。
2. 基于同一组决策轴提出适用候选，比较完成步数、发现与理解成本、错误与恢复、极限数据、键盘 / 读屏 / 触控支持及系统一致性；未知项标缺口。
3. 对范围内的搜索、筛选、日期、上传、排序、分页、长列表逐项执行同一判断；不适用写理由，不从操作名称直接推出固定组件。
4. 选择满足已知任务与可访问性要求、且优先复用设计系统的候选；记录淘汰理由、代价和仍需验证的条件。
5. 实现仍须保证按钮说明动作与对象、标签持续可见、报错不清空有效输入、可比较内容维度对齐。

**产出**：组件决策轴记录、候选比较、选择及依据。  
**完成证据**：选择能由决策轴复算，组件减少而非增加理解和操作成本；搜索、筛选、日期、上传、排序、分页、长列表均已覆盖或说明不适用。  
**不得替代**：设计系统规范；有系统时优先复用。

## U7 对象表现形式与尺寸分级

**触发问题**：界面里出现用户在现实或该领域里本来就认得的对象时，用什么形式表现它；缩小到实际显示尺寸后，用户还靠什么认出它？  
**最低输入**：界面里的对象清单、每个对象的实际渲染尺寸（含最小尺寸）、所在平台和使用情境。  
**跳过**：纯文本信息、表单字段和没有现实对应物的抽象数据。

对象举例：卡牌、棋子、筹码、骰子、票据、车票机票、货币、证件、商品、食物、地图与地点、日历日期、文件类型、设备、角色、天气、交通工具。

**步骤**

1. **找识别特征。** 对每个对象写出用户靠什么认出它：形状、图案、配色、版式、符号或固定位置。来源是现实中的样子，或该领域成熟产品已经形成的惯例，不是设计师临时发明。
2. **按形式优先级选。** 沿用该对象自己的视觉惯例 > 简化图形或图标 > 文字。文字只做补充说明或无障碍标注，**不能用对象的名称代替对象本身**。在需要识别对象的位置写「某某」两个字，视为这个对象没设计。
3. **按实际尺寸分档。** 按真实渲染尺寸定 2–3 档：完整、缩略、极小。每一档都要保留最少的识别特征：缩小时删的是细节，不是识别特征。优先使用该领域本来就有的缩略方式，而不是自己发明。例如：
   - 扑克牌叠放时只露左上角标，用点数加花色；王牌的角标是小王冠或小丑图形，大小王靠红黑区分。
   - 票据缩成列表时，保留类型色条和关键数字。
   - 地图缩小时，从地形细节退到地点标记。
   - 头像缩小时，从半身像退到头部，再退到首字母圆。
   - 文件缩小时，从缩略预览退到类型图标加扩展名色块。
4. **在真实尺寸下看。** 按最小档实际尺寸截图检查：同类对象之间能一眼区分，例如不同牌、不同票种、不同文件类型。区分不了就加强识别特征，不改成写字。
5. **同类全档统一。** 同类对象的每一档都来自同一套素材和画风；素材按 `V5` / `V7` 先找现成成品，没有再按统一风格生成。

**产出**：对象表现表，列出对象、识别特征及其惯例来源、各尺寸档的形式与像素尺寸、素材来源。  
**完成证据**：最小档截图里同类对象能一眼区分；没有任何一处用对象名称文字代替对象本身。  
**不得替代**：素材授权、视觉风格选择。

## U5 状态

**触发问题**：默认之外，界面在真实数据和失败条件下是否完整？  
**最低输入**：页面职责和交互状态。  
**跳过**：纯静态展示物。

**步骤**：检查默认、加载、空、成功、失败/校验、权限、禁用、极限内容；不适用项写理由。

空态：`现在没有【对象】。【下一步】。`  
错误：`【对象】没成功，因为【原因】。你可以【动作】。`

**产出**：状态表与状态稿。  
**完成证据**：不只交理想填满态；主失败有行动。  
**不得替代**：交互异常出口。

## U6 界面文案

**触发问题**：标题、按钮、帮助和错误是否帮助用户行动？  
**最低输入**：对象词表、职责、状态。  
**跳过**：正式文案冻结且本轮不得修改。

**步骤**

- 标题写对象或任务。
- 按钮写动词+对象。
- 帮助写现在怎么做，不写品牌口号。
- 数字带单位；称谓和动作词全程一致。
- 截断不得破坏关键判断。

**产出**：页面文案表。  
**完成证据**：没有“确定/提交/出错了”等脱离上下文空话。  
**不得替代**：法律、品牌或专业领域文案审核。

## UI 验收

若工作包包含任何 UI 方法，交付前 UI 层按 U1–U7 逐条检查（信息分级、单一主行动、对比、亲密、对齐、重复、组件、对象表现形式与尺寸分级、状态、文案）。这只是整套终审的其中一层，问题与价值、流程、交互、视觉、验证各层同样要对照成品验收。任何一条不过，先改再重审，通过后才交付。见 [methods-close.md](methods-close.md) `QA0` 第 0.3 节。
