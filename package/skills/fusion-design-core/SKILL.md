# 设计师完整工作流（Design Thinking OS）

本 Skill 模拟一名**成熟设计师 + 设计总监**接到工作后的真实思考、决策、调库、选工具与终审全流程。

---

## 产品主线先于设计

本模块是融合产品锤中的设计环节，产品主入口统一组织目标、领域需求、边界、方案、PRD和交接。先读取同包[产品启动条件](../fusion-product-agent/references/product-start.md)，核对本轮目标、核心范围、终点及其用户输入/既有决定/明确委托来源。只有产品名称或AI自行写出的候选画像、目标、流程，不算有效产品输入。

若目标或核心范围仍有改变方向的缺口，回到产品主线给出可理解的推荐并通过原生Question询问，等待必要答案；不得直接开展受影响的正式设计或Demo制作。设计研究可以支持讨论，不能替人决定为什么做和先做什么。直接调用本Skill也遵守此条件，不要求另启一个Agent。专业设计判断、调研和QA0继续按下述方法执行；已有有效输入、局部改动或明确委托按范围复用，不重做访谈。

## 流程位置与回传

本环节沿用[产品主线六阶段与设计四步骤](../fusion-product-agent/references/progress-navigation.md)。每次成果、修订或提问回复，最终首行保留产品第几/6阶段，设计中附设计第几/4步、当前模块及真实状态；结尾交代下一动作或用户所需选择。四步骤对应下文的研究/流程交互、视觉决策、制作、终审，不按回复次数推进。向产品主入口回传同样的信息，不因要求自然语言、隐藏方法代号而省略导航，也不增加人工审批。

## 成果、工作环节与专业设计路径

接单先读 [成果、环节与子任务目录](methods-deliverable-routing.md) 的总则，再读取匹配的主成果、独立环节或专项条目。AI 根据委托范围明确主成果或独立环节、本轮工作范围与起止、子成果及依赖；工作方式、交付载体和本轮终点分别记录，不让使用者选内部编号。研究、流程、信息架构与交互可以是完整项目的环节，也可独立委托；图表、资产、动效、视频及其他成果可独立交付或嵌入项目，不作为互斥的平行分类。适用路径决定哪些专业判断必须成立，RT0 决定各部分深度与具体方法，工具在此之后选择。

已有流程、信息架构、内容和交互须核对本次适用性，复核通过才复用；只改局部则只回查受影响依赖。界面任务按流程/复核 → 信息架构与页面职责 → 内容表达与层级 → 具体交互 → 视觉推进；平面传播按信息主次 → 表达与构图 → 风格制作推进；其他类型走对应条目。各环节可迭代回查，不能接单后直接套 UI 或生图。

下文页面、控件、头像及 UI 调库门禁仅在对应界面/资产分支适用。只委托研究、流程、信息架构、图表、图标或其他局部成果时，到该范围结束，不补做上级项目或强制先选 UI 风格；专业路径不新增工具权限，不豁免适用的原有确认与验收。目录中的专项缺口须如实处理，不因列入范围就宣称全部能力已齐备。

本轮主成果是产品界面与网站，或复合项目中包含界面设计时，读取 [产品界面与网站详细流程](workflow-product-interface.md)，只应用到该界面范围。九个工作环节接回下文原四步骤和 N0–N5，不新增全局阶段或逐步审批；先判断哪些新做、修改、复核或复用，每个适用环节按所选方法的完成证据自审，再交给下游。其他成果仍按目录走自己的路径。

视觉表达先按 [CT7](methods-context.md) 核对既有品牌、指定风格、参考、委托人偏好与禁区；会改变本轮决定的关键事实或约束未知时带推荐提问，仅缺主观偏好可依据任务和参考推导候选，不把未知写成用户无偏好或先用默认风格制作后再命名。候选按 [DS1](methods-style-engine.md) 实际检查整体感受差异，单换物件或配色的同风格方案标为变体。文字按 [V3](methods-visual.md) / [TY](methods-resource-routing.md) 区分作用、更新与维护需要：主副标题、眉题可采用独立字形资产，排版须设计字重、颜色、字距、行高及构图关系；字体包可选，在线资源核对实际可用性。按 DS2/V5 将同一方向落实到标签、主要控件和适用图标，判断形态、渐变/表面、材质与空间，展示前审完整图文组合；不强制所有静态文字生图或逐项加装饰。上述要求嵌入原环节，不新增全局阶段或固定第二轮审批。

主题表达由主视觉带动且需据此延展页面时，按 DS1「主视觉引领分支」执行：理解产品/受众/目标与参考 → AI 推导并筛选方案 → 必要输入及工具路线成立后制作主视觉 → 自审后让人看图选择 → DS2 推导整页规格、按 V7 分层制作和数据合成 → 完整代表页及原有确认。不强制先选无图文字方案，也不重复整页方向候选；纯文字咨询、普通工具页、局部修改和严格还原按原范围执行。

评估 Skill 时，按 [独立试跑与方向溯源](WORKFLOW-REVIEW.md) 使用无前文的执行上下文，只提供原始任务、原始输入、待测版本及必要权限边界；不传历史偏好、候选或推荐。保留每个方向来自哪里，不把沿用历史的演示称为独立测试。

图标选择与调库统一按 [V5](methods-visual.md)：承接页面职责和内容层级，先定必要性、作用、图文主次与实际尺寸，再定表现分组和检索。允许页面内多组表现，组内优先同一真实集合及视觉变体，组间保留整体协调；不把关键词或风格标签当作选择完成。

本 Skill 只保存可跨任务使用的方法、判断依据、适用条件和验收规则；不收录项目 Demo、具体业务案例、示范答案或试跑产物。实际任务内容和测试证据单独保存在本地任务目录，不回填为通用默认。空白记录模板及实际工具/资源目录继续服务方法执行。

## 工具路线先推荐、确认后执行

工具选择与确认的唯一依据为 [TR0](methods-tool-routing.md)。该制作动作的必要专业前置完成后，先说明“根据成果与现状，推荐哪条工具路线、为什么、改哪里、交付什么、实际能力和必要取舍”，请人决定再制作；测试原型、方向样张和正式页面均在此范围内。工具确认不固定等到全部交互或视觉完成：前期确需测试载体时，先明确验证问题、满足 PROTO1 最低输入，再确认对应原型路线后制作。只读检查可先做，已有覆盖本轮的明确路线直接引用，不对每个步骤重问。后文工具、组件和素材细则均为已确认路线内的执行方法，不能作为自动选路或绕过确认的理由。

## 补充入口：任务性质与创意概念（嵌入原流程，不替代原步骤）

涉及新设计判断或“优化现有页面”时，先读 [methods-creative-concept.md](methods-creative-concept.md)。接单时执行 CC1，区分业务目标、设计性质、技术载体与已批准约束；研究/竞品后、风格和组件制作前，按 CC2–CC4 判断并推导必要的创意概念；F4 与 CC2 共用同一套概念候选和选择记录，分别补行为干预与主题/体验组织的适用依据；不重复开两套探索，候选数按问题决定。流程、信息架构、内容、交互与视觉仍各自设计和检查。QA0 加入 CC5 的适用检查。原有用研、三类竞品、流程、交互、风格确认、调库、工具路由和三审全部保留，不新增固定审批轮次。

下文“有现成页面就延展”“排除宣传海报”“组件先行”等规则按职责适用：存量延展须有已批准的适用基线；真实界面仍用于交互取证，海报/包装可另作表达与机制参考；组件实现服务已推导的概念，不能替代概念。普通工具页、明确局部修饰和严格还原按补充方法的跳过条件执行，不强制创意包装。

## 多页面制作与人工确认门禁（在原有流程内执行）

涉及多个页面的设计或视觉优化时，执行 [methods-close.md](methods-close.md)「0.4 代表页与最终人工确认」：先制作一个完整代表页 → Agent 实际看图、运行原 QA0（含审美并排对比）、修改并重审 → 展示准确版本并等待用户明确确认 → 才能继续其余页面 → 全部完成后再次运行 QA0 与跨页检查 → 请用户最终确认。选定风格不等于确认代表页，代表页确认不等于整套验收；沉默不视为确认。

上文“不新增固定审批轮次”指不向所有任务统一追加文字概念审批；主视觉引领分支记录 AI 推导依据及人的真实看图选择，不再叠加整页方向探索。关键事实、业务取舍和工具路线仍按原规则确认，本条代表页及最终确认保留。单页任务省略扩展门禁，仍须展示前自审及最终人工确认。

## 开工与分步门禁（先做设计判断，再确认方向与制作）

1. **产品启动条件成立后，理解使用者与任务，再判断设计重点。**
   - 读取 [methods-intake.md](methods-intake.md)、[methods-context.md](methods-context.md)，并按 [methods-routing.md](methods-routing.md)「RT0 设计判断与研究深度」形成当前判断：谁在什么情境进入页面、要完成什么、已有何种经验与预期、怎样算成功。
   - 从方向、体验和表现三个层面审视请求，区分症状与可能的主要障碍；可提出更上游的解释，但不因“资深判断”擅改业务目标或授权范围。
   - AI 根据各问题的影响、证据可靠性、行业模式成熟度、试错代价和补证成本，分别决定思考深度，不要求人先选深度，也不把所有维度一律做浅或做深。

2. **先完成必要推导与原有方向确认，再进入正式制作；研究不是固定问答轮次。**
   - **【前置判断与汇报】**：
     1. 保留完整方法库，根据待回答的问题选择并实际执行研究、竞品、流程和交互方法；已有适用结论直接复用。用户、情境与任务理解每次都要成立，但不必每次重做访谈或完整研究。
     2. 桌面调研走 [methods-research.md](methods-research.md) `R0.1`；三类竞品分别按问题判断必要性，需要时依照 [methods-competitive.md](methods-competitive.md) 和 `RR` 取真实样本。范围与样本量由待回答问题、覆盖和新增信息是否改变判断决定，不为凑截图数量调用方法。用于后续 QA0 并排审美验收的参考要求仍按原验收规则执行。
     3. 简洁汇报：使用者/任务/预期的理解及依据、当前主要问题与备选解释、研究和方法的选择理由、实际结论及其设计影响、待决事项。事实、推断和假设分开；不把思考过程或已批准材料重复写成长报告。
     4. 无法取得真实访谈或观察证据时，先做可执行的桌面调研并检查已有材料；影响方向的关键未知转为给使用者的问题，说明为何重要、不同答案的影响与推荐。区分请求补充事实、提供真实用户材料和作业务取舍；人的决定不冒充用户验证。必要答案未到时暂停依赖部分，独立工作继续。
     5. 按成果路径完成必要前置设计/复核后，由 AI 推导方向，在有效工具路线内制作独立样张、自审并供人看图选择，不设必经文字方案审批：
        - **视觉风格方向选择**：普通 0→1 未指定风格时，按 DS1 比较同一代表内容的实际样张；主视觉引领分支直接制作 1–2 张可比较的主视觉，均解释差异、依据与推荐，不重复整页方向；
        - **人物头像画风**：包含角色/用户头像时，按原要求询问画风；
        - **交互方案与交付载体**：确认必要的交互取舍、设备场景及本地 Demo / Figma 等交付要求。
     6. **样张制作与正式应用分开**：必要前置未成立时不进入视觉样张制作。前置成立、且工具路线已按 TR0 明确确认或有适用既有选择后，允许在独立草稿目录/设计分区内按 DS1 调用预设、组件、素材和相应制作工具，形成待选样张；不修改现有项目的正式实现、不铺开其他页面、不将候选记作已批准。展示并发出方向选择问题后停止，等明确回复再正式应用。选方向不能绕过正式代表页自审、人工确认和最终确认。

   - **【制作（用户选定风格并确认交互后）：调取风格/组件/IconScout 库落盘 → 写出 `design-decisions.md` → 制作与总监终审】**
     - 主视觉引领分支先按 DS2 从已确认主视觉建立本轮任务规格，下面预设命令仅用于实际采用的功能底座；不能为满足命令而把整页套回近似预设，也不虚构预设 ID。实际素材、字体、对比度与组件复用仍须检查。
     - 收到用户选定的风格方向后，按本轮适用范围和实际采用的来源执行下列动作；已有有效系统/组件先复核复用，不为运行命令扩大局部任务：
       1. 预设路线运行 `python3 scripts/style_preset.py show <实际采用的风格编号>`；主视觉引领分支读取确认主视觉及 DS2 任务规格，不强制该命令。两者均对实际主题运行 `color_intelligence.py contrast`，字体按 V3/TY 核对，`typography_intelligence.py pick` 可作适用检索起点；
       2. 本地组件代码路线采用配方底座时执行 `python3 scripts/component_recipe.py copy <实际采用的配方ID> --to <任务目录> --preset <实际底座编号>` 并实际复用；主视觉引领分支按 DS2 映射到任务主题，项目已有合适组件按 DS3 复核复用，不为运行命令虚构编号或覆盖确认表达。不能只看 `show` 就声称实际调库；
       3. 按 V3/V5 取得实际采用的字形、功能图标和表现资产；采用 IconScout 时实际检索下载，成熟库或已授权生成路线保留对应真实文件与证据，不为过门下载未采用资产；
       4. 凡有角色/用户头像，先用 `iconscout.py` 检索并过 `V5` 第 7 条判断门；库内无匹配同套系头像时，**严格按用户在第一轮选定的头像画风（Q版3D卡通 / 国风插画 / 写实人物）**锁定统一母体风格前缀，调用生图工具成套生成头像图片（`avatar-*.png/jpg` 存入 `<任务目录>/assets`），**严禁用“名字首字圆圈”回退充数！**
       5. 写出本轮适用的 `<任务目录>/design-decisions.md`；仅本地组件代码路线运行 `python3 scripts/verify_library_usage.py <任务目录> [--require-avatars N] [--require-photos]`，按 QA0 核对原始报告、实际覆盖及逐资产采用证据。适用失败须修正；仅提供方文件名检查不适配时按 QA0 的限定规则核验，不能伪称脚本通过。Figma 路线核对目标组件/变量及真实素材的采用与可访问性，不以本地 CSS 已生成作为开工条件。
   - **砍掉 4 项浪费时间的无用功（不要再白跑）**：
     1. **0→1 新项目且无 `.design-memory/index.json` 时，不跑 `asset_memory.py search`**（空库必未命中）；
     2. **0→1 新建的空白 Figma 文件，严禁调用 `figma_search_design_system` / `figma_get_libraries`**（空白文件只会搜出无关的 Material 普通内容卡片，语义完全不适用）；
     3. **目标是高保真设计稿或可交互 Demo 时，不默认先画灰框，也不得给灰框填色充当正式高保真。确有待验证判断时，可按 PROTO1/TR0 在满足输入并确认对应制作路线后制作独立测试原型；已有有效原型优先复用，测试原型与正式 UI 分开**；
     4. **游戏/UI 表面纹理（桌布、木纹、金属边框）不跑 `real_image.py`**。

以下四步主要展开产品界面与网站，以及复合项目中的界面部分。它们不是所有主成果的通用流水线；只委托其他成果或独立环节时依上方目录使用对应专业路径、原有可复用方法与适用验收，不强行进入全部 UI 制作。

## 一、设计师接单后的完整运作流程（按任务情况分流）

### 第一步：看需求给到了什么程度，决定从哪切入（研究 → 竞品 → 流程 → 交互）

接到任务后，先读取 [methods-intake.md](methods-intake.md)、[methods-context.md](methods-context.md)、[methods-routing.md](methods-routing.md)，判断上游给的信息处在哪个阶段：

1. **如果是 0→1 的需求（方向或使用方式尚未清楚）**
   - 按上方设计判断入口，先识别使用者、情境、任务、已有预期及关键不确定。完成必要推导，不直接选风格或制作。
   - **用户理解与证据**：按问题读取 [methods-research.md](methods-research.md) `R0–R8`（含 `R0.1` 桌面调研）与 [methods-context.md](methods-context.md)；功能和行业惯例可支持任务角色、基本预期的初步推断，不能自动证明具体人群属性、能力或动机。
   - **分类竞品**：扫描 `CMP1/2/3` 各自能回答什么；需要新增取证时走 `RR`，已有适用证据直接引用，不适用则说明理由，不强制三类全部新做。
   - **流程与交互**：保留 [methods-flow.md](methods-flow.md) `F1–F5`、[methods-interaction.md](methods-interaction.md) `I1–I6` 与 [methods-ui.md](methods-ui.md) `U1–U7`，实际调用解决本轮问题的方法。形成页面职责、主路径、信息层级、对象表现、控件及关键反馈的有效依据；完整方法库不等于每次把所有方法跑一遍。

2. **如果产品经理已经给了需求文档、字段清单或“交互原型”（局部优化 / 新建单屏）**  
   - **产品经理给的“交互”往往只是一个业务预期，不是真正的交互设计。** 设计师绝不能不加思考地照着字段清单画个表单或把页面砍成半成品。
   - 必须先读取 [methods-interaction.md](methods-interaction.md) 和 [methods-ui.md](methods-ui.md)，审视上游方案合不合理，在局部或整体上对 **信息架构、步骤切页（`I1`）、页面职责（`I3`）、异常反馈（`I5–I6`）以及具体的交互表现形式（`U4 组件选型`）** 做专业修改与决策：
     - **页面职责必须准确（`I3`）**：依据本页任务检查必要内容、入口、结果与导航是否完整，不能用局部画面替代完整页面职责。
     - **具体交互形式由设计师决定（`U4`）**：根据选择数量、频率、上下文、设备及可恢复性决定控件和页面组织；能可靠带出或选择的内容，避免要求重复输入。
     - 如果发现上游安排对用户不合理（需要删减、合并或后置某些步骤），用提问工具给出专业建议让用户确认。

3. **如果已有正式设计主稿要求还原，或只是替换已确认文案**  
   - 直接按正式主稿与规范执行还原和一致性检查（[methods-close.md](methods-close.md)）。

### 第二步：交互形式确定后，进入 UI 设计与视觉风格决策（必读 [methods-ui.md](methods-ui.md) `U0` + [methods-visual.md](methods-visual.md) `V0` + [methods-style-engine.md](methods-style-engine.md) `DS`）

**只有在第一步的页面职责、功能模块、对象尺寸（`U7`）与交互控件（`U4`）全部确定后**，才进入 UI 阶段，打开 [methods-visual.md](methods-visual.md) 按 `U0` 三路分流：

1. **情况 A｜存量项目风格延展（`U0` 路线 1）**  
   - 如果项目已经有现成页面、设计系统或组件库，直接去读已有的设计规范与组件库（`DS0`），提取现有的主辅色、背景与卡片层级、圆角、字号阶梯、图标风格进行延展，不重新选风格。

2. **情况 B｜纯 B 端 / 企业中后台从 0 到 1（`U0` 路线 2）**  
   - 直接调用成熟的公开组件库（国内中后台用 `Ant Design` / `Arco Design` / `TDesign`；出海 SaaS / AI 工作台用 `shadcn/ui`；海外企业用 `MUI` / `Fluent UI`）及 `style-presets/systems/` 预设快速搭建。

3. **情况 C｜C 端产品 / AI 产品 / 游戏 / 强品牌界面从 0 到 1（`U0` 路线 3 → `V0` 风格决策 + `DS` 风格引擎 + `CI` 配色 + `TY` 字体）**  
   - **必须先打开 [methods-visual.md](methods-visual.md) 查阅 `V0` 的预设参数字典**，结合用户语境、目标感受与行业约束筛选可用资源，推导相应视觉表达；资源分类不能代替本轮判断。
   - **风格怎么决策（`V0` Step 2 & `DS1`）**：
     - **绝不允许在未向用户汇报完第一步（使用者与任务理解、必要研究结论或复用依据、相关流程与交互方案）之前就提前定死风格！**
     - 普通 0→1 未指定风格时，按 DS1 给出 2–3 个实质不同的方向样张并说明推荐；主视觉引领任务按 DS1 的 AI 推导 → 实际主视觉看图选择路径执行，不再强制整页候选。必要前置和工具确认均保留。
   - **正式应用参数在用户选定方向后配齐并写入 `design-decisions.md`；方向样张可提前按 DS1 在隔离位置读取或导出候选参数，明确标为待确认**：
     - 风格规格：预设路线运行 `python3 scripts/style_preset.py show <预设编号>`（导出/应用用 `export` / `apply`）；主视觉引领分支读取 DS2 任务规格及主视觉确认来源；
     - 语义色与对比度：预设路线可用 `python3 scripts/color_intelligence.py contrast --preset <预设编号>`；任务推导规格检查实际主题 `contrast --css <主题CSS>`，不得以无关预设代测；
     - 字体与字阶：`python3 scripts/typography_intelligence.py pick --family <风格族> --langs zh,en`。

> **正式制作准出检查（方向样张按 DS1 单独记录，不冒充正式制作）**：
> 正式制作前，任务目录必须已经生成包含以下 4 块内容的 `design-decisions.md`，并先向用户展示核心推导结论。前置已成立、方向尚未选定的样张按 [DS1](methods-style-engine.md) 在同一决定文件中记录前置依据、候选、隔离位置、自审和待确认状态，允许为样张调用制作工具；不能填成已选风格或正式准出：
> 1. `D1–D9` 决定链状态与工作模式；
> 2. 用户/情境/任务/预期及来源、研究深度与方法选择依据、实际研究和适用竞品结论（或复用/不展开理由）、关键假设及待决项、页面职责（`I3`）、功能模块清单、领域对象尺寸分级（`U7`）与具体交互控件选型（`U4`）；
> 3. 已选方向及规格来源（预设编号，或已确认主视觉与 DS2 推导规格的准确版本）、语义色 Hex、字体字阶、适用组件/配方、真实素材清单与组件应用边界；
> 4. 「前置推导已完成，现在进入工具制作」。

### 第三步：调取成熟组件/素材库、设计视觉元素（Banner/头像/海报）与选对工具（必读 [methods-visual.md](methods-visual.md) `V5/V7/VT` + [methods-tool-routing.md](methods-tool-routing.md)）

成熟设计师做东西**绝不会让 AI 现画劣质图标，也不会拿一个风格词就盲目生图**，而是分清里面有哪些是 UI 组件、哪些是视觉设计（Banner、头像、海报、动效），调取准备好的专业库并选用最合适的工具：

1. **按 V5 分组选择真实资产与组件，拒绝粗糙占位**：
   - **图标与表达小资产**（[methods-visual.md](methods-visual.md) `V5`）：功能图标优先复用适用成品库，表现图形可按本轮主视觉派生取得或生成独立资产，核对材质、光影、透视、语义和最小尺寸。实际库文件或生成文件与来源、参考和落位相对应，不以形式调库或简陋占位代替设计；Lottie 等正式动态格式仍按原工具合同。
   - **真实世界摄影（风景、城市地标、建筑、人文生活）**（[methods-image.md](methods-image.md) `IM`）：一律先运行 `python3 scripts/real_image.py search "<主题>" --role hero|card|background|place` 从 Unsplash / Openverse / Pixabay / Wikimedia 检索并 `get` 真实摄影（作者与许可证只记入资产记录文件，**绝不印在产品 UI 画面上**）。
   - **人物头像（Avatar）**（`V5` 第 7 条）：先搜素材库并过「文化风格 + 同套系判断门」；如果库里搜出来是欧美橡皮泥人、不符合国风或当前产品气质，立即放弃库结果，锁定统一母体风格前缀词成套生成高颜值头像。
   - **成熟组件库与通用配方**（[methods-style-engine.md](methods-style-engine.md) `DS3`）：React 项目调 `shadcn/ui`、`Magic UI`、`Ant Design` 等组件库；跨技术栈或 HTML 原型用 `python3 scripts/component_recipe.py` 调取结构配方。

2. **按最终交付物类型走对应的工具与制作工作流（[methods-tool-routing.md](methods-tool-routing.md) + [methods-visual.md](methods-visual.md) `VT` / `V7`）**：
   - **路线 A｜UI / 产品界面**
     - 先按 [TR0](methods-tool-routing.md) 结合成果、已有主稿与实际能力提出推荐并请人确认。已有明确路线直接复用；没有主稿要求的可操作 Demo 可推荐本地代码，不强制 Figma 或 HTML 优先。
     - 已确认沿用 Figma 时调用同包 [执行工作流](../fusion-figma-workflow/SKILL.md)，在授权目标中设计/精修，并按需要依据同版主稿还原 Demo；已确认代码路线则在目标项目复用组件、主题和素材，实际运行并核验。
     - 本地文件不会自动传入设计软件；按已确认载体传递参数、素材和组件对应关系。转换能力须实际存在并核验可编辑性，不以整屏图片冒充可编辑稿。
   - **路线 B｜产出本身是一张图（概念图、插画、角色立绘/头像、局部材质/背景图等纯图片交付）**
     - **标准动作**：先按 TR0 确认适合本次成果的制作组合；已选择图片生成时，**Codex 负责产出结构化提示词（Prompt）+ 准备参考垫图（`reference_image_paths`）→ 直接调用生图工具（`GenerateImage` / Figma `generate_image`）生成图片**。
   - **路线 C｜产出是海报 / 运营图 / Banner / 主视觉 KV（[methods-visual.md](methods-visual.md) `V7 路径 B`）**
     - 先定图文占比与**版面结构草图（`layout_sketch`）**，按场景二选一：
       1. **搜索素材去 Figma 拼装**：从 IconScout 搜索透明底 3D/插画素材、从 `real_image.py` 搜索真实摄影，带进 Figma 配合 Figma AI / 版式底板与清晰矢量文字拼装成稿；
       2. **垫图 + 提示词调生图工具**：独立成品无适用参考时先展示参考选择；DS1 主视觉样张引用本轮 AI 推导与参考，不重复审批。按 V7 产出结构化提示词和实际可用参考，调用已确认的生图工具。
   - **动效判断（[methods-motion.md](methods-motion.md) `D8` / `TR5`）**：
     - **UI 交互动效（`TR5-A`）**：从动效组件库（`MI`：React Bits / Aceternity UI / Motion Primitives / Uiverse / 21st.dev）检索源码集成到可交互 Demo；
     - **轻量矢量动画（`TR5-C`）**：从 IconScout 拉取真 `Lottie (.json)` 或基于专业矢量图标加动画；
     - **动态海报 / 视频（`TR5-B`）**：独立海报交付且场景支持动图时按原范围询问；DS1 主视觉样张不追加未委托的动效升级。已确认动态制作后再拿静态图做【首帧垫图】+ 运动提示词调生视频模型，转码为 `GIF / 动态 WebP / 循环 MP4`。

### 第四步：模拟「设计总监」做交付前全面终审（必读 [methods-close.md](methods-close.md) `QA0`）

所有内容做完后，**绝不能做完就交**！必须切换成**设计总监（Design Director）**视角，用 `Read` 打开成品图并运行验证脚本，从三个核心维度把关：

1. **一审：有没有达到最初的设计目标？所有功能与交互是不是完备、合理？（`QA0` 维度一 + A–D）**
   - 放到真实用户场景里检查：页面类型、内容、对象识别与操作覆盖是否符合已定职责和实际展示尺寸，不能用局部内容或未经验证的缩略表现替代完整任务。
   - 交互形式合不合理？用户进来第一眼看什么、怎么点选、下一步去哪，3 秒内能不能看懂？

2. **二审：好不好看？视觉风格、质感与细节到没到位？（`QA0` 维度二）**
   - 仅为 DS1 主视觉样张时，按 QA0/DS1 使用适用的主视觉或编辑表达参考自审，不把它称作整页界面验收；完整代表页仍以真实界面参考核对。
   - 运行 `python3 scripts/side_by_side.py --shot <成品图> --width <宽> --height <高> --refs <refs下同方向真实竞品截图> -o compare-r1.png`，用 `Read` 打开并排对比图：
   - 和成熟竞品放在一起，我们的构图张力、留白呼吸感、60-30-10 色彩比例、容器与按钮材质能不能打？
   - **零 AI 廉价感检查**：有没有一眼假的 AI 生成图标？有没有红底黑字等低级对比度错误？有没有把 `Photo: / CC BY` 版权字印在界面上？人物头像是不是符合产品文化且同屏统一画风？

3. **三审：组件库/素材库真调核验与工程规范准不准？（`QA0` 维度三 + `VE` 脚本）**
   - **按制作载体核验真实调库（防止“只看不用、自己瞎画”）**：
     - 本地组件代码路线运行 `python3 scripts/verify_library_usage.py <任务目录> [--require-avatars N] [--require-photos]`，按 QA0 维度三核对原始报告与实际采用的组件/资产；适用失败修正，仅提供方文件名项的覆盖局限按其限定规则逐资产核验，不改名凑文件或伪称脚本通过。
   - Figma 原生稿核对实际组件实例、Variables / Styles、字体、真实素材及同版截图，记录证据；CSS 文件不作为原生设计稿的门槛。按稿还原复用既有项目组件时，核验真实组件/Token映射，不强造配方 CSS。
   - 凡产出 HTML/代码界面，交付前还必须运行适用的检查，工具不适配时用等价实测并记录原因，不能把未检查写成通过：
     - `python3 scripts/ui_geometry_audit.py <html文件> --width <宽> --height <高>`（按准确目标尺寸检查分区、对齐、图标来源、跨区内容碰撞及脚本实际覆盖的页面完整性，保留原始结果和覆盖限制）；
     - `python3 scripts/color_intelligence.py contrast --css <主题CSS>`（检查实际对比度）；
     - 按 DS5 的实际规格来源运行 `python3 scripts/style_consistency_audit.py <页面> --preset <实际预设编号>`；主视觉推导规格不带 `--preset`，另补 DS2 颜色/字体/圆角及相关状态的逐项实际值核对，两部分均须通过，不声称脚本覆盖未检查的任务规格；
     - `python3 scripts/a11y_audit.py <html文件>`（检查无障碍）。

> **设计总监打回机制**：只要上面三审中有任何一项不达标（功能残缺、交互生硬、质感不如标杆、有 AI 塑料感或脚本报错），**严禁交付给用户**！立即按 [methods-close.md](methods-close.md) `0.2 回炉路由表` 退回对应环节重改，改完再次终审，直到真正达到高水准才交付。

## 三、向用户提问与沟通的纪律

1. **产品目标与范围已有有效依据后，0→1 设计怎样汇报与确认方向**：
   - 产品目标或核心范围未校准时先回产品主线，给出有依据的推荐与关键问题；只有名称或自行推导的候选不算有效输入。输入充分后再开展设计判断和方向样张，不重做已有研究，不直接宣布风格。
   - 先完成并简洁汇报 **【① 使用者、任务与预期及依据，② 必要研究/竞品结论或复用依据，③ 相关流程与具体交互方案】**；关键事实或业务取舍未清时先提问，不虚构结论。达到原方向确认条件后，用提问工具提出下列适用问题，最多 3 道：
     - **第 1 题（选定整体视觉风格方向）**：普通分支按 DS1 展示实际方向样张并推荐；主视觉引领分支完成推导后直接制作主视觉，自审后请人看图选择准确版本，不叠加普通分支的整页方向选择；
     - **第 2 题（选定人物头像画风，当界面有玩家/用户头像时必问）**：让用户选择想要 **3D 潮玩/Q 版卡通头像**、**国风/精致插画头像**、还是 **写实人物头像**；
     - **第 3 题（确认交互方案与交付载体）**：确认设备场景与交互控件方案，以及直接出浏览器高保真组件预览/可交互 Demo 还是先在 Figma 完成设计后还原 Demo。
   - **先完成专业前置，再制作并自审方向样张供人看图；发出方向选择问题后停止等待。收到明确选择后才正式应用风格，样张选择不等于正式代表页批准。**
2. **其他情况什么时候征求用户意见**：
   - **独立海报 / KV 走 AI 生图且无适用参考选择时**：按 V7 展示参考让人选择；DS1 主视觉样张引用该分支的方案推导和参考，不重复同一方向审批；
   - **独立海报交付静态版后且场景支持动图时**：按范围询问动态版；仅为 DS1 主视觉样张时不追加升级询问；
   - **发现产品经理给的交互/字段安排不合理，需要较大删改或分步时**：把设计师优化后的交互方案放在第一项，征求用户确认。
3. **汇报语言干净自然**：像真实设计师一样用直白的视觉和交互语言交流，不把 `D1–D9`、`V0`、`U0`、`CT9`、`QA0` 等内部方法代号直接甩给用户。
