# 设计师端到端工作框架

状态：`DRAFT v0.1`  
用途：描述设计师接到上游任务后，怎样理解、分析、选择方法、形成方案、验证并交付。  
本文件是协作审阅用的总框架；具体方法由各 `methods-*.md` 提供。

## 1. 这套流程解决什么

上游产品流程通常给出目标用户、核心问题、产品价值、业务目标和约束。设计流程不重复发明这些事实，而是完成三次转换：

1. 把产品事实转换成对用户行为、情境、心智模型、风险和信息判断的理解。
2. 把这些理解转换成可执行、可验收的设计原则和设计决定。
3. 把设计决定转换成流程、交互、UI（含全部界面视觉）、非界面视觉资产、动效、原型和验证证据。

总链路：

```text
接收上游任务
→ 保留来源并检查可用性
→ 判断本次需要怎样的设计支持
→ 将产品信息翻译成设计语境
→ 形成设计目标、原则、矛盾与风险
→ 扫描 D1–D9，形成候选决定缺口
→ 确定本轮终点、目标决定和必要依赖，生成最终设计起点
→ 按「决定缺口 × 语境要求」选择方法
→ 按最终产物选择 Figma、视觉或动效工具
→ 执行所需的设计工作包
→ 验证或验收
→ 交付并把新结论回传上游
```

这不是固定的“用研→流程→交互→UI→视觉→动效”流水线。只有当前任务需要时才进入对应能力区；已确认或冻结的决定直接复用。

## 2. 产品流程与设计流程的边界

### 上游产品流程负责

- 产品为什么值得做、优先级和商业边界。
- 目标用户、核心问题、价值假设及其证据。
- 业务目标、成功指标、合规和资源约束。
- 已确认、已冻结和明确不做的产品决定。
- 希望设计支持的任务及交付时间。

### 设计流程负责

- 判断上游信息是否足以支持本轮设计，而不是默认全部重新研究。上游需求写得具体，也不等于这一屏的信息层级、页面职责和输入方式已经设计完。
- 从用户完成任务的顺序，重新组织这一屏先看什么、这一屏负责什么、哪些让用户点选而不是照着需求清单填。业务事实不改；安排对用户不合理时，回传上游，不在界面里硬摆。
- 将用户、行业、情境和目标翻译成设计可使用的约束。
- 找出需要补证、设计或验证的最早决定。
- 选择并执行恰当的方法，不按关键词套固定流程。
- 形成可走通、可理解、可实施、可验收的设计方案。
- 将设计中发现的产品缺口、证据和风险回传上游。

### 设计流程不得

- 擅自改写上游产品事实或业务优先级。
- 把人口属性、行业标签或审美偏好直接当作设计结论。
- 把推断写成“用户研究表明”。
- 用精美界面掩盖未解决的价值、流程或交互问题。
- 因发现一个缺口就无条件重启全部产品研究。

## 3. 全程信息标签

设计分析中的每一条信息必须标来源性质：

- `INPUT_FACT`：上游提供且有来源的事实。
- `DESIGN_INFERENCE`：从事实推导出的设计含义；必须保留推导链。
- `ASSUMPTION`：当前可暂用但尚无证据的判断；必须写若错会怎样。
- `MISSING`：缺失且不同答案会改变本轮产出。
- `USER_DECISION`：需要产品负责人或用户做取舍，设计 Agent 无权代决。

信息性质与 D1–D9 状态不同：前者说明一条信息从哪里来，后者说明一个设计决定当前是否可用。

## 4. 上游输入合同

设计 Agent 先尽量从已有任务、文档和对话中填写，不要求上游重复回答已经提供的内容。

```text
原始任务：
期望结果：
目标用户：
核心问题与用户价值：
业务目标：
用户/产品结果与成功指标（D3）：
计划采用的验收或验证程序（D9）：
已有证据及适用范围：
当前方案、页面或流程：
平台、设备与使用环境：
行业、合规、安全和品牌约束：
已确认决定：
已冻结决定：
明确不做：
正式主稿、设计系统和资产：
期望设计交付物：
时间、研发和资源约束：
```

缺失内容不自动阻断。只有“不同答案会实质改变本轮产出”时，才标 `MISSING` 或向人提问。

## 5. 工作节点

### N0 接收与来源保全

**目的**：先弄清上游实际上交付了什么，不急着解释或设计。
执行方法见 [methods-context.md](methods-context.md) `CT0`。

**动作**

1. 保留用户原话、原始文档和版本。
2. 将事实、请求的手段、约束、偏好和期待交付物分开。
3. 记录每项信息来源、时间、用户群和适用范围。
4. 发现冲突时并列记录，不自行选择“看起来合理”的一项。

**产出**：上游任务卡、来源清单、冲突与缺口。  
**通过条件**：第三人能区分“上游确认了什么”和“只是要求采用什么手段”。

### N1 设计支持模式判断

**目的**：判断真实设计师应该怎样支持，而不是所有任务都先研究。
执行方法见 [methods-context.md](methods-context.md) `CT1`。

主模式只能选一个：

- **直接制作**：只替换已批准文案，或在既有组件里改已定内容；层级、职责和输入方式已经设计过，本次不变。
- **局部优化**：问题位置已知，但具体设计解法未确定。上游事实已确认、要设计新的一屏也归这里。
- **问题探索**：问题、用户、情境、价值或成功判断会改变方向且尚未解决。
- **方案验证**：已有概念、流程或原型；“验证准备”只形成测试就绪载体和延期合同，“验证执行”实际取得证据并更新判断。
- **设计还原/交付**：依据正式主稿、规范或版本做高保真实现、对照或交接。

**跳过深度分析的条件**

- 任务是低风险、可逆的直接制作（只换已批准文案或既有组件内的已定内容）。新的一屏不在此列。
- 任务是严格还原，且正式来源、资产和行为规格完整。

即使跳过，也要确认本次修改不会无意改变上游决定。

**产出**：工作模式、初步范围、是否进入 N2。  
**通过条件**：能说明为什么需要或不需要进一步设计分析。

#### N1.5 D1–D3 预扫描

进入完整语境翻译前，先检查问题与价值、用户与情境、结果与成功指标是否足以支撑本轮设计。缺口可由现有材料或研究解决时，先调用相应研究方法；必须由业务、合规或外部事实决定时标 `BLOCKED`。补齐后再完成 N2–N3，不为保持顺序虚构设计原则。

### N2 设计语境翻译

**目的**：把产品语言转换成设计可使用的行为、认知、风险和表达约束。
执行方法见 [methods-context.md](methods-context.md) `CT2–CT9`；缺真实行为证据时按触发条件调用研究方法。

只有需要设计判断的任务才展开。按相关性扫描下列维度，不要求每次全部研究。

#### 2.1 用户能力

分析：

- 任务熟练度和领域知识。
- 数字产品熟练度。
- 阅读、认知、视听和精细操作能力。
- 是否依赖辅助工具或他人协助。

纪律：年龄只能触发能力检查，不能直接推出“大字、简单、保守”。

#### 2.2 项目上下文与内部复用

分析：

- 当前设计在整体项目中的位置、上下游入口与关联模块。
- 共享对象、状态、术语、权限、导航、反馈和凭证模式。
- 设计系统组件、变量、布局、内容模板和真实资产。
- 哪些可以直接复用、受控扩展、仅作参考或必须新建。

项目内部复用必须核对意图、语义、状态和权限是否一致；共享组件需要扩展或新建时，不得静默修改全局版本，并记录本地/全局范围、相邻模块影响、责任人、授权状态和 D9 回归范围。未授权的共享变更标 `USER_DECISION/BLOCKED`。

#### 2.3 竞品与类比样本

竞品独立分三类调用，不与用户研究或内部复用混写：

- 行业竞品：分析类别门槛、替代方案、信任模式和差异机会。
- 同类操作竞品：跨行业分析相同操作的流程、反馈、异常和恢复，严格说属于类比样本。
- 服务同类用户的竞品：基于真实用户—产品关系，分析已培养的术语、导航、信息和操作习惯。

执行方法见 [methods-competitive.md](methods-competitive.md) `CMP1–CMP3`。竞品只能产生候选模式和待验证假设，不能证明用户需求或方案有效。

#### 2.4 使用情境

分析：

- 触发事件、地点、时间和时长预算。
- 设备、网络、单手/双手、移动/固定状态。
- 注意力、情绪、是否会被打断。
- 是否多人协作、是否需要切换渠道。

#### 2.5 任务特征

分析：

- 任务频率、复杂度、熟练后是否重复。
- 探索、比较、创建、监控还是高后果决策。
- 成功前需要哪些判断和信息。
- 失败成本、可逆性和恢复方式。

#### 2.6 行业风险与信任

分析：

- 金钱、健康、隐私、身份、法律或声誉风险。
- 数据是否需要来源、时间、精度和解释。
- 哪些操作需要确认、审核、撤销或留痕。
- 用户凭什么相信结果、机构和下一步行动。

纪律：“金融”可以推出准确、透明、可追溯和错误保护要求，不能直接推出唯一的颜色或视觉风格。

#### 2.7 信息与内容

分析：

- 用户做决定前必须知道什么。
- 哪些信息需要比较、解释或渐进披露。
- 专业术语、数字、单位和风险文案怎样被理解。
- 内容长度、语言、文化和本地化差异。

#### 2.8 品牌与情绪

分析：

- 品牌在当前任务中应扮演什么角色。
- 用户完成任务前后需要减少或增加什么感受。
- 哪些视觉特征支持任务，哪些会削弱信任或可读性。

情绪词必须继续翻译成可观察规则；“高级、年轻、严谨”本身不能验收。

#### 2.9 技术与运营现实

分析：

- 数据是否实时、完整、可编辑。
- 权限、加载、失败、空数据和人工介入。
- 平台规范、组件能力和研发成本。
- 运营是否能长期提供所需内容和资产。

**单条翻译记录**

```text
上游输入：
来源性质：
它可能影响的用户行为或判断：
已有证据：
设计含义：
若错会造成什么：
影响的决定：D1–D9（可多选）
需要补证吗：
```

**产出**：设计语境卡。  
**通过条件**：每条设计含义都能追溯到输入或明确假设；没有从标签直接跳到样式。

### N3 形成设计任务定义

**目的**：将语境翻译收敛成下游能够执行和验收的设计要求。
执行方法见 [methods-context.md](methods-context.md) `BR1–BR2`。

#### 3.1 设计目标

设计目标写用户在特定情境下应更容易完成、理解或判断的事情，不写“做一个页面”。

```text
在【情境】下，帮助【行为群体】完成【任务结果】，
减少【关键阻碍或不确定】，
同时满足【业务、风险或技术约束】。
```

#### 3.2 设计原则

每条原则必须是能改变方案选择的规则：

```text
因为【事实/证据/明确假设】，
设计必须【可观察的规则】，
不得【具体反模式】，
通过【检查或行为】验收。
```

不合格：`界面要严谨、体验要顺滑、符合年轻人习惯。`  
合格：`高后果操作提交前必须同时显示对象、金额、费用和不可逆后果；不得只用“确认”概括。`

#### 3.3 关键矛盾与优先级

记录必须取舍的冲突，例如：

- 信息完整与快速完成。
- 熟悉模式与新的产品差异。
- 业务转化与用户审慎判断。
- 品牌表现与高密度任务效率。

优先级顺序由任务决定，但不得牺牲任务可完成、安全、合规和基本可访问性。

**产出**：设计任务句、3–7 条设计原则、关键矛盾、风险与待决策项。  
**通过条件**：这些内容足以判断两个候选方案哪个更适合。

### N4 决定链与方法路由

**目的**：决定从哪里开始、调用什么，而不是把全部方法跑一遍。
执行 [methods-routing.md](methods-routing.md)：先确定本轮主终点和产出合同，再建立目标决定、必要依赖、决定工作集、制作动作集和证据动作集，确定最终设计起点与风险深度；最后用 [methods-dispatch.md](methods-dispatch.md) 为未解决决定选择具体方法。

扫描：

```text
D1 问题与价值
D2 用户与情境
D3 用户/产品结果与成功指标
D4 任务流程与范围
D5 交互规则、语义反馈与状态
D6 UI 信息层级与内容
D7 界面视觉系统与资产
D8 UI 动效表达
D9 验收或验证程序
```

D3 说明最终希望发生什么用户/产品结果、用什么指标判断；D9 说明用哪个版本、对象、样本、步骤、阈值或对照取得证据。稿件一致性检查不能冒充 D3 的结果成立。

状态使用 `CONFIRMED / FROZEN / TEST_INPUT / ASSUMPTION / MISSING / BLOCKED / N/A`。  
每项另标本轮动作：`REUSE / RESOLVE_NOW / ACCEPT_FOR_NOW / TEST / WAIT_EXTERNAL / SKIP`。

候选起点是最早一个同时满足以下条件的决定：

1. 状态为 `MISSING`，或是 `ASSUMPTION/RESOLVE_NOW`。
2. 不同答案会实质改变本轮产出。

`ASSUMPTION/ACCEPT_FOR_NOW` 是本轮接受的临时输入，只进入风险和后续验证，不在同一工作包内循环触发。`BLOCKED` 表示必须等待外部事实、资产、权限或授权；受影响部分不得用下游设计填空。

#### 状态转换

- 方法产生足够证据或得到有权确认：`MISSING/ASSUMPTION → CONFIRMED`。
- 安全地暂用一个答案：`MISSING → ASSUMPTION/ACCEPT_FOR_NOW`，并记录失效影响和补证。
- 选为本轮验证对象：对应决定 `→ TEST_INPUT/TEST`；测试载体的其他决定保留原状态或按范围 `FROZEN`。
- 测试支持且证据范围足够：`TEST_INPUT → CONFIRMED`，记录适用人群、情境和版本。
- 测试证伪：`TEST_INPUT → MISSING`，回到受影响的最早决定。
- 测试无结论：`TEST_INPUT → ASSUMPTION` 或 `BLOCKED`，不得写已验证。
- 外部输入补齐：`BLOCKED → MISSING/ASSUMPTION/CONFIRMED`，再重新路由。
- `FROZEN` 只有得到原授权方同意才能重开；`N/A` 只有范围变化才重评。

方法选择使用两个轴：

1. **决定轴**：当前要解决 D1–D9 中哪一个决定。
2. **语境轴**：用户能力、心智模型、情境、任务风险、信息、品牌或技术现实对该决定提出什么要求。

例如，同样是 D6：

- 扫读困难可调用信息分级和对比/亲密/对齐/重复。
- 高风险金融判断还需内容与信任验证、数字精度和风险说明。
- 高频专家任务还需密度、效率和快捷操作约束。

N4 再依据终点和依赖形成最终起点；无待解决决定但有明确制作动作时，最终起点是制作动作，不得强行调用设计方法。

**产出**：本轮产出合同、任务诊断卡、目标决定与三类工作集、最终设计起点、风险深度、D9 模式与计划、方法工作包和明确跳过项。  
**通过条件**：每个方法回答一个明确问题并有停止信号；直接制作有动作合同；每个跳过项都有复用或不相关依据；知道 D9 本轮执行还是延期，以及完成后怎样更新决定状态。

### N5 执行设计工作包

先执行 [methods-tool-routing.md](methods-tool-routing.md)，按最终产物选择工具并明确职责边界；再执行 [methods-execution.md](methods-execution.md) 的动作合同、输入门、方法记录、产物衔接、停止和重路由规则。只读取并执行工作包点名的能力区。方法和工具产物必须进入明确的下游决定、制作或证据动作，不能只为“流程完整”生成。

#### 5.1 研究与问题定义

用于补足真实行为、情境、心智模型、问题位置和价值判断。  
可调用：证据审计、问题卡、行为分群、情境访谈、观察、同理心地图、证据归纳、旅程、危险假设、价值主张与关键行为。

#### 5.2 流程设计

用于确定范围、场景、任务步骤、干预点和方案深度。  
可调用：范围表、场景卡、主路径、干预点与概念、三档深度。

#### 5.3 交互设计

用于确定页面/节点职责、进出关系、反馈内容与行为、状态和异常恢复。D5 拥有“发生什么、显示什么、成功/失败去哪里”。  
可调用：步骤切页、命名与进出、页面职责、结构线框、主行动反馈、异常矩阵。

交互阶段可用 Figma 承载低保真稿，但必须标 `LOW_FIDELITY_INTERACTION` 并与正式 UI 主稿分区；进入 UI 时只复用已确认规则，不把低保真表现自动升级为正式设计。

#### 5.4 UI 设计

用于把已知职责变成可扫读、可操作、状态完整的界面。  
可调用：UI 落地前置分流（存量延展 / 纯 B 端连接公开组件库快搭 / C 端 0→1 视觉决策）、信息分级、单一主行动、对比/亲密/对齐/重复、组件、状态、界面文案。

#### 5.5 UI 界面视觉与生图

属于 UI 设计并在 Figma 正式主稿中完成，用于在不改变任务含义的前提下形成可追溯的界面视觉表达。  
可调用：0→1 视觉风格库与 6 维决策漏斗、视觉依据、语义色、字体与密度、气质句、图标与图片、真实摄影素材库、同结构候选、图片生成双路径协议。

界面中的颜色、字体、图标、插画、图片和品牌表达都在 Figma UI 中完成。图标/3D/插画走 IconScout；真实场景、地点、生活、自然摄影先走 Real Image Library；只有图库无匹配或必须虚构时，才由 Codex / Agent 调用 Figma 内置生图或插件在目标图层原位生成。只有最终交付本身是非界面视觉成品（如运营海报/KV），或用户明确把某项资产拆成独立视觉委托时，才按工具路由走「图文角色占比判断 → 版面结构草图 → 能快拼则快拼 / 能用真图则用真图 → 必要时才双垫生图」分支；确认后的独立资产可再导入 Figma。D7 不意味着所有任务都必须在 UI 后追加一个视觉阶段。

#### 5.6 UI 动效设计与动态成品

只用于运动表达已经由 D5 定义的反馈、状态转换或空间关系。D8 不重新定义反馈含义；静态状态已足够时跳过。Figma 原型只可作预览或预测试，正式 UI 交互动效必须通过写代码实现（CSS / JS / GSAP / 客户端代码）。  
可调用：反馈动效、状态转换、空间关系。

代码写不出的复杂 3D/光影/流体动态图与宣传视频走「首尾关键帧垫图 → 生视频模型 → 转码 `MP4 / WebM / GIF / 动态 WebP`」（不得将视频序列帧位图伪装成矢量 Lottie）；其中出现任何产品 UI 画面时引用已定稿 UI，只有运动表达 UI 反馈、状态转换或空间关系的片段才关联 D5 与 M1–M3。SVG、真 `Lottie (.json)`、图标等轻量矢量动画先从 IconScout 取现成素材，库里没有再基于专业矢量源用代码生成（不手画简陋图形）；只有运动表达 UI 反馈、状态转换或空间关系时才关联已定稿 UI、D5 与 M1–M3。

**依赖规则**

- D4 未解决时，不用页面排版替代流程。
- D5 未解决时，不用组件或动效替代交互规则。
- D6 未解决时，不用界面视觉风格替代信息层级。
- 正式主稿已冻结时，不重开上游，只做还原和一致性验收。
- 后续证据推翻上游判断时，只回到受影响的最早决定，不自动从头重来。

### N6 原型、验证与收敛

**目的**：判断方案是否解决当前问题，而不是只证明“已经画完”。

N6 不建立第二套证据执行。所有证据只从 [methods-execution.md](methods-execution.md) `EX6` 进入，并共用同一个动作 ID、生命周期和步骤账本；N6 读取记录，负责原型/验证的专用规则、证据解释、决定状态和收口。`CORE_EVIDENCE` 随研究/测试产生，`POST_ARTIFACT_ACCEPTANCE` 在成品冻结后运行，`DEFERRED_NEXT_ROUTE` 本轮只准备条件；已有同版本 `EXECUTED` 记录不得在 N6 重跑。

当本轮要准备或运行的证据需要用户阅读、判断或操作方案时，先调用 [methods-prototype.md](methods-prototype.md) 的 `PROTO1`：

1. 选择刚好能回答当前判断的载体和保真度。
2. 准备代表性内容、被测主路径、关键失败、返回和结束态。
3. 用测试脚本预测试，修复断链和必须靠主持人解释的问题。
4. 冻结原型版本后按子型分支：
   - 验证准备：执行原型完整性验收，填写 `DEFERRED_NEXT_ROUTE` 的责任人、触发条件和程序，到“测试就绪 / 修正载体 / 阻断”即停止。
   - 验证执行：进入正式验证并取得观察证据。

只做无载体研究、人工价值交付或正式规格一致性验收时，可按方法条件跳过。

每个待证明或验收事项选择一种主要证据；同一工作包可有多个事项，但不得用其中一项代替另一项：

- 概念理解：用户是否理解它解决什么。
- 任务走查：用户是否无需教学完成关键任务。
- 内容与信任：用户是否理解关键信息并有足够证据做决定。
- 人工价值交付：重开发前，目标结果是否真的被使用。
- 局部优化回归：修改是否解决点名问题且未破坏关联路径。
- 精确还原验收：是否与正式主稿、资产和行为规格一致。

只有方案验证—验证执行取得证据后，学习决策四选一：

- 继续投入。
- 修正方案，保留问题定义。
- 重写问题定义。
- 停止。

验证准备产出冻结版本、预测试/完整性验收和延期合同；不产出学习结论。其他工作模式按 [methods-close.md](methods-close.md) 的对应分支决策。

**产出**：与证据动作匹配的冻结版本、样本或验收范围、记录、结论或延期合同。  
**通过条件**：本轮运行的结论有行为或逐项对照证据；延期项明确写未验证。“喜欢、好看、感觉顺畅”不能单独通过。

## 6. 协作填写规则

本框架允许不完整，但不允许假完整。

1. Agent 先读取已有信息并自动填写能确定的部分。
2. 无证据推导必须标 `DESIGN_INFERENCE` 或 `ASSUMPTION`。
3. 只有会改变范围、产生明显返工或需要业务授权时才问人。
4. 用户修改某一项后，只更新受影响节点和下游，不重问无关内容。
5. 每轮保留：
   - 已确定内容。
   - 本轮新增或修改。
   - 仍缺什么。
   - 下一步准备处理哪个节点。
