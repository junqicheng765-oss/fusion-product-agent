# 设计产物与工具路由

目的：根据本轮最终产物选择合适工具。工具不决定流程，阶段名也不自动触发工具；先确定要交什么、需要什么证据，再选择能产生该成品的工具。

## 工具选择的前置条件

先由 [成果、环节与子任务目录](methods-deliverable-routing.md) 明确主成果或独立环节、本轮工作范围与起止、子成果及依赖，再确定适用的专业路径与必要前置，使用本文件选择工具。“流程、交互、UI 可选”表示任务可委托不同范围，不表示正式界面可略过必要上游判断。已有方案先核对，研究、流程、图表、图标等独立委托不扩成 UI 或上级项目；格式不决定专业路径。下面的页面组件及 UI 工具要求只作用于适用分支，其他成果依自己的内容、结构和制作依据建立工具合同。

## 核心规则

1. 专业设计路径、工作方式和交付要求先成立，再判断制作工具；纯研究或对话分析不强制进入视觉工具。
2. 工具路线的判断、推荐、人工确认与变更以本文件 TR0 为唯一依据；其他方法说明所需能力、参数或执行细节，不另设强制先 HTML / 先 Figma 的总路线。
3. 一个任务可包含多个有依赖的工具分支，说明整合后的成果与交接；工具返回成功不等于设计或有效性验收通过。
4. 本轮实际制作、修改目标成品、生成方向样张之前，先提交有理由的路线推荐并取得人的明确确认。已有覆盖本轮的明确路线决定直接引用，不对同一路线的每个操作重复询问。
5. 已有正式稿与资产优先作为来源和延续依据；已有文件不自动证明允许编辑，登录或连接成功也不构成本轮路线决定。
6. 已确认路线不可因工具缺失、方便或默认偏好静默更换；影响成品格式、主稿位置、编辑方式或能力边界时说明替代方案并重新确认。必要工具/事实未具备时暂停依赖制作，独立分析继续。

已明确选择 Figma 或已授权在本产品主稿继续设计时，直接沿用该决定；先完成本轮可编辑主稿，再按同版上下文还原正式 Demo。工具缺失先引导恢复，B 端、只改文案或局部任务不自动改变载体。已有文件只作为来源时仍需核对授权范围。

## 补充：互动活动页的混合实现

按 [methods-creative-concept.md](methods-creative-concept.md) CC4 分别记录设计性质和技术载体。HTML/Figma 活动页可同时需要运营 KV、交互参与区与标准组件；依照上述既有路线为各部分建立依赖和验收，再集成页面，不因为最终交付 HTML 就只走普通卡片拼装，也不将活动整页交为不可操作位图。不新增独立资产委托或绕过原工具权限、风格确认与调库要求。

## TR0 工具路线判断与人工确认（唯一规则入口）

### 先判断，再给人可理解的推荐

完成本次制作动作所需的设计前置后，AI 根据成果、编辑/交接要求、已有主稿与项目、实际工具能力和成本作专业推荐。读取现有文件、核对非敏感配置、查看可用能力与只读定位可以先做；为验证能力而创建页面、提交生成、修改成品或安装配置不属于只读。

工具确认跟随制作动作，不是固定排在全部交互设计或视觉结束后的全局步骤。产品界面与网站按 [详细流程](workflow-product-interface.md) 在前期确需原型时，先明确待验证判断、满足 PROTO1 的最低输入，再推荐并确认原型路线后制作；不要求先完成与该验证无关的正式 UI。方向样张和正式页面同样各自遵守必要前置及路线确认，已有有效选择覆盖本轮则直接引用，内部实现细节不逐项重问。

| 本次成果与现状 | 推荐时应判断的内容 |
| --- | --- |
| 浏览器中真实可操作的界面或 Demo | 需要代码与运行验证；已有设计主稿作为还原依据时保留同版对应。没有设计主稿要求时，可推荐直接在现有项目或本地实现，不强制先做 Figma。 |
| 已有正式设计稿，需要继续编辑或扩展 | 优先推荐沿用原文件、组件和样式，说明本次编辑目标与范围；已有明确选择则复用，没有则让人确认。参考链接不能当编辑授权。 |
| 从零形成可编辑设计稿 | 根据需要的可编辑性、后续协作与当前可用工具推荐设计软件或其他合适载体；Figma、代码及转换方案均需核对实际能力，不承诺未验证的一键转换。 |
| 海报、图片或独立图形资产 | 依据内容/构图、尺寸、文字可编辑性及格式，推荐拼装、矢量编辑、排版或图片生成的适用组合；单张位图不能冒充可编辑源文件。 |
| 视频、动效、演示、文档或其他类型 | 根据脚本/结构、交互性、格式、后续编辑和播放/导出要求，推荐具备相应能力的工具；不按文件扩展名把所有任务归入 UI 或生图。 |

通常给出一条推荐，存在实质取舍时再附必要备选。对人简述：**“我判断本次需要……；建议用……，因为……；会在……制作/修改，最终交付……；当前能力/缺项是……。是否按这条路线开始？”** 由 AI 负责判断和解释，不让使用者先解答一串技术选型题。只展示消息或写入记录不代表已经获得同意。

### 明确确认后才开始制作

- 使用宿主可用提问机制收集选择；提问发出后停止依赖该路线的制作，包括方向样张。未回复、预选项、工具已连接、仅批准业务方案，均不视为路线同意。
- 用户已明确点名工具/已有稿及本次动作，或此前已确认同一任务的完整路线时，核对范围后引用该来源即可；无需再问相同问题。笼统委托设计不等于用户已经看过一条尚未提出的工具方案。
- 路线确认可与已有交付/方向讨论中的同一具体问题合并，不额外设一轮固定审批；但不能先制作样张，再补问其制作路线。路线确认、视觉方向选择、正式代表页批准和最终确认各有用途，不能相互代替。
- 确认后仅在该范围内执行，内部组件、技术参数及同等实现细节由 AI 判断，不为每个命令再问。新增安装/账号授权等仍遵守宿主与已有授权，不把工具推荐或登录状态当全局配置许可。
- 记录推荐、理由、可用能力、修改目标、输出、取舍及人的选择来源和适用范围。沿用原 `PENDING_CONFIRMATION / CONFIRMED / BLOCKED` 等记录方式，不新建状态机；必要条件变化时只重开受影响路线。

同一任务需要多个工具时，每个工具建立独立动作 ID，并写清依赖和交接文件，不能把多个工具的中间结果统称为“设计完成”。

## TR1 流程与问题分析

适用产物：

- 问题诊断；
- 用户和语境材料；
- 任务流程、旅程、决策图；
- 方法记录和设计原则。

工具要求：

- 使用能保留结构、来源和可编辑关系的文档、表格或图表工具。
- 流程图必须表达用户行为、系统响应、分支和结束态，不以页面截图代替。
- 不因最终可能进入 UI 就提前创建 Figma 主稿。

Figma 不是这类产物的默认工具。若只是为了在团队已有文件中展示流程，必须标为参考材料，不能把它当作 UI 已开始。

## TR2 交互设计

适用产物：

- 页面职责与进出关系；
- 状态、反馈、异常和恢复规则；
- 结构线框；
- 用于验证操作逻辑的最小原型。

默认工具选择：

1. 只需说明规则：使用结构化文档、状态表或图表。
2. 需要走查行为：使用能表达真实状态和分支的最小原型工具。
3. 需要低保真界面承载：允许使用 Figma，但必须标 `LOW_FIDELITY_INTERACTION`。

低保真 Figma 合同：

- 只表达结构、职责、内容顺序、行动和状态。
- 不建立未经确认的正式颜色、字体、间距、品牌视觉和资产。
- 与正式 UI 页面、组件和变量分区存放，名称中标明低保真和版本。
- 进入 UI 设计时只复用已确认的交互决定，不自动把低保真表现升级成正式主稿。
- 低保真通过只能证明交互载体符合当前规则，不能证明正式 UI 或行为效果。

## TR3 UI 设计：按已定路线制作与核验

适用产物：

- 页面与响应式布局；
- 组件、变量、状态和真实文案；
- 信息与行动层级；
- 所有界面内的颜色、字体、密度、图标应用和视觉表达；
- 正式 UI 主稿、可测试 UI 原型和开发交付。

### UI 内部范围与三路落地分流

内部决定链中的 D6 和 D7 都属于 UI 设计：

- D6 决定信息、行动、组件、状态和文案怎样呈现。
- D7 决定这些内容在界面中的颜色、字体、密度、图标、图片和视觉系统应用。

进入 UI 制作前先按 [methods-ui.md](methods-ui.md) `U0` 与 [methods-visual.md](methods-visual.md) `V0` 执行三路分流：

1. **有本次要求沿用的已批准页面或设计规范（存量延展模式）**：提取适用基线的色板、背景与卡片层级、圆角、字号阶梯和图标风格，复用既有组件，不重新选风格。待优化 Demo 不自动视为规范，按 U0 核对可复用约束与本轮范围。
2. **0→1 纯 B 端 / 企业中后台（公开组件库快搭模式）**：直接连接成熟公开组件库（`Ant Design` / `Arco Design` / `TDesign` / `shadcn/ui` / `MUI` / `Fluent UI`），制作路线按 TR0 推荐并确认后，由 Agent 在该路线内按技术栈与场景决定组件库、主色与密度（Default / Compact），不逐项询问技术参数。
3. **0→1 C 端 / 游戏 / 强品牌差异化产品（风格库 + 6 维视觉决策模式）**：完成并汇报使用者与任务理解、必要研究/竞品结论或复用依据、相关流程与具体交互方案后，由 AI 推导候选，按 DS1 的适用分支和 TR0 制作、自审实际样张，再供人看图选择；不先设无图文字风格的必经审批。用大白话说明感受、差异与推荐，选定后由 Agent 配齐具体视觉参数与适用资源。主视觉引领分支从确认 KV 推导 DS2 规格，不强制套入近似预设。

三条路线选定风格或组件库之后，都按 [methods-style-engine.md](methods-style-engine.md) 落地：
- 从 `style-presets/` 取整套 token 和规则。
- Figma 里绑定为 Variables / Styles；代码里写进一处全局 token，用 `scripts/style_preset.py` 导出或应用。
- 多页面交付前跑 `scripts/style_consistency_audit.py`。
- 用户要求给已有产品换风格时，先探索、后确认、再批量应用。

主视觉引领任务由 AI 完成方案推导，按 DS1 直接制作主视觉、自审后供人看图选，再进入 DS2；上方预设只作实际采用的功能底座。主视觉作为页面子资产继承 TR0，必要时将图像与界面制作组合说明并一次确认；实质变更再确认，不自动获得工具或外发权限。

D7 不是“离开 Figma 去做视觉成品”的固定下一阶段。TR4 的独立成品分支仅用于非界面交付或独立资产委托；下述 DS1 主视觉及 V3 标题可以作为所属页面子资产，不要求另开独立委托。

### Figma 合同与 UI 内原位生图

- 已选择 Figma 或已有本产品设计主稿时，以指定文件、页面、Frame/组件/变量和准确版本为主稿；本地路线记录对应代码与预览版本。
- 先搜索并复用现有设计系统或已绑定的公开组件库；共享扩展或新增必须有所有者授权。
- 页面、组件、状态、响应式、真实文案和真实资产必须在主稿中对应。
- Figma 路线在主稿完成颜色、字体、间距、密度、图标、图片裁切及状态；已有页直接精修，新增整页按需生成后精修，再还原 Demo。具体执行、配置及授权见同包 工作流（技能 `fusion-figma-workflow` 内的 `SKILL.md`）。本地路线沿用组件与素材要求。
- **IconScout 双通道真实资产调取（优先官方 MCP `https://mcp.iconscout.com/mcp` + 内置 v3 API 脚本自动兜底，覆盖 `icon` / `3d` / `lottie` / `illustration`）**：
  1. **通道 A（MCP 优先）**：先用 `GetDynamicTools` 检查当前宿主是否已连接 `iconscout` MCP（端点：`https://mcp.iconscout.com/mcp`，指南：`https://iconscout.com/mcp`）。若已连接，优先调用 MCP 工具用自然语言按风格与色板检索同系列 Pack，并直接下载 `SVG`、`PNG`、`Lottie JSON`、`GIF` 或 `MP4`。
  2. **缺失能力与备选渠道**：未连接 MCP 时，先按 TR0 核对本轮可用替代渠道或配置需求；已有适用授权直接复用，未经覆盖该动作的授权不改全局配置。采用 `scripts/iconscout.py` 时继承 V5 已形成的图标组和检索规格，只传当前渠道真实支持的资产、风格及适用网格参数；源网格不等于显示尺寸。集合身份、文件格式、透明性及许可分别核验，不承诺脚本未提供的整组检索或下载能力，不以粗糙占位替代成品。
- **UI 界面内配图（`V7 路径 A`）**：功能图标优先复用适用的成品库；表现图标、字形及局部图形按 V3/V5 判断可用资源或本轮主视觉派生制作。真实摄影仍先按 [methods-image.md](methods-image.md) 检索并导入。图形/字形生成沿 TR0 已确认的实际能力与工具组合执行，再导入所属主稿或代码，不因它位于 UI 中强制切换 Figma 工具。引用准确方向及版本、材质/光影/比例与落位，不擅自锁成另一套风格。
- 已有外部正式资产只有经过来源、授权和版本确认并以真实文件导入后，才能进入正式 UI；通用素材缺失时按 IconScout、Real Image Library 或（最后）生图补齐；只有用户方才有的素材缺失时才阻断并向用户要，不自动调用外部视觉工具扩张范围。
- 正式主稿与低保真交互稿分开；不得在低保真页面上直接覆盖视觉后称正式完成。
- 交付时记录准确节点、版本、覆盖、未覆盖、差异和验收证据。

若任务是按正式 Figma 还原代码，Figma 是 UI 来源，代码工具负责实现；实现后必须与同一版本主稿做动态和数值对照，不能把截图近似称为还原。

## TR4 非界面视觉成品与外部视觉资产

**主视觉引领页面的子资产**：适用 DS1 时，按 AI 的方案推导与参考制作样张，自审后让人看图选择，由 DS2 推导整页规格；不强制先过文字审批或已锁定 UI 预设。工具仍按 TR0，真实来源/授权及主稿导入证据保留。正式制作按 V7 分层规划图像、独立标题与程序信息，适用工具须支持所需透明资产、编辑和合成，不能承诺未验证的分层导出。已有适用路线复用，实质能力变化再确认；不重复垫图审批或未委托动效升级。

**界面中的表达子资产**：主副标题、眉题等静态表达字形及表现图标/装饰，按 [V3/V5](methods-visual.md) 在所属页面范围内判断排版、矢量/图像制作或生图，不要求使用者另立独立委托。继承 TR0 对当前动作有效的路线；能力、输出或修改范围实质变化时再解释和确认。采用位图须说明编辑限制，动态图文及真实控件保持程序语义与可操作性；独立成品的海报步骤不反过来阻断页面内的局部表达设计。

以下条件用于确认视觉产物分支；具体工具仍按 TR0 推荐并取得明确选择后调用：

- 最终交付本身是海报、运营图、KV、品牌图形、营销图片、插画、独立图标集或其他非界面视觉成品；
- 用户明确把某项图片、插画、图标或图形拆成独立视觉资产委托，并要求独立源文件、审核和交付；即使它以后进入 UI，也先作为单独成品管理；

上方 DS1 主视觉及 V3/V5 表达子资产沿所属页面范围与 TR0 执行；其他特定可编辑矢量、分层源文件、图片处理或生成需求须先核对本轮独立成品合同，不能仅因工具具备能力而扩大委托。

### 独立海报 / 运营图 / 主视觉 KV 的「IconScout 快拼 / 真实摄影 / 必要时才 AI 生图」与动图升级链路（`V7 路径 B`）

当任务是生成独立海报、运营图或活动主视觉（KV）时，严禁跳过版面分析直接盲写提示词生图，必须按以下 5 步执行：

1. **确定图文职责与主导关系**：按 [V7 路径 B](methods-visual.md) 判断焦点、主辅及视线，不套固定图文面积比。
2. **形成可查看的组合稿并选择来源**：先决定完整画面的空间、层次及接合，再判断适用素材、真实摄影或所需定制资产；具体判断以 V7 为准，不以取得速度代替表达质量。真实摄影仍按 IM，已明确的独立字形/图像要求按 V3/V5 执行。
3. **按判断问题取得实际参考**：V7 风格表仅作可选检索语汇，内容与质量依据分开。独立成品的参考选择沿 V7，页面主视觉沿 DS1，不重复确认，不用参考审批替代实际方向样张。
4. **在真实工具能力内制作及合成**：把同一构成决定转成各层的实际提示、参数、参考和边缘接法，保留要求的独立文件与真实动态文字/控件；按 V7 的准确成品证据检查，不假定双图输入或强制整屏位图。
5. **主动判断场景是否支持动图，并用提问工具问用户要不要动效版（含效果预期说明）**：
   - 若投放场景为 App 开屏/弹窗/Banner、网页 Hero、社媒动态封、公众号/朋友圈 GIF 等支持动图的渠道，在交付静态图后**用提问工具明确问用户是否生成动效版本**；用户原话已要求动图时直接做，不再问；
   - **若走方式 1（素材快拼）**：可直接从 IconScout 检索替换或嵌入同主题 `--asset lottie` 动态元素，一键导出高清动态海报；
   - **若走方式 2a / 2b（真图底图或 AI 生图）**：明确告知生视频模型擅长做「光影折射流转、3D 主体轻微悬浮/自转、粒子/水波/热气微动、镜头缓推」等微动氛围 Loop，并用无字/少字主体底图当 **【首帧垫图】** 送入 `TR5-B` 生视频模型（保持文字层清晰稳定），最后导出为高清 `GIF` / `动态 WebP` / 循环 `MP4`。

视觉工具按最终格式选择，不按“视觉阶段”选择。动作合同必须说明：

```text
资产或成品 ID：
用途：非界面独立成品 / 独立资产委托（可供 UI 使用）
使用场景与是否支持动图：
图文职责、主导关系、主辅权重与阅读路径：
组合稿及版本、层次/疏密/背景与相邻区域接法：
实际视觉/工艺参考、借鉴边界和选择来源（编号仅在采用时记录）：

尺寸、比例、格式、透明度、分辨率或矢量要求：
是否升级生成动效版及预期效果说明：否 / 是（转入 TR5-B 首帧垫图生视频并转码 MP4·GIF·动态WebP）
可编辑源文件要求：
```

独立视觉资产需要进入 UI 时：

1. 先验收内容、风格、技术格式和授权。
2. 确认后再导入 Figma。
3. 在 Figma 中完成 UI 内的尺寸、裁切、布局、状态和响应式应用。
4. 未确认资产不能用占位图、表情或近似素材代替后称 UI 完成。

独立视觉成品不要求经过 Figma；其专业视觉工具输出就是主交付。

## TR5 动效规格、预览与正式成品（三条实现链路）

以下为与成果相匹配、且按 TR0 已确认路线的执行细则，不因复杂度标签自动替人决定用代码、模型或特定软件；不具备实际能力时说明限制并确认替代路线。

先按动效性质与画面复杂度分为三条实现链路，三类输入合同与实现工具不能混用。

### A. UI 交互动效与组件状态过渡（纯代码实现路线）

适用：界面点击/按压反馈、状态转换、弹窗/抽屉展开、页面层级转场、列表增删、返回和可操作空间关系。

决定方法：M1–M3。

正式输入：

- 已批准的 Figma UI 节点和版本；
- D5 状态、反馈、导航和异常规则；
- M1–M3 规格；
- 界面真实资产及版本；
- 目标设备、平台、运行环境和性能要求；
- reduced motion 或等价替代要求。

实现方式与边界：

- Figma 原型可以使用已批准 UI 和组件状态，表达关键触发、起止帧、页面关系和大致方向，用于评审或预测试；必须标 `FIGMA_MOTION_PREVIEW`。
- Figma 原型不能证明最终 easing、时间、打断、代码行为和性能已实现，也不能替代 reduced motion、中断、返回、快速重复触发和资源释放验收。
- **正式 UI 交互动效最终必须通过写代码实现**（如 CSS / JS / GSAP / Motion / Anime.js / SwiftUI / 原生客户端动效代码），确保与真实 UI 组件、实时手势和异步状态绑定，并在目标运行环境完成测试。
- **写代码前先检索现成组件**：规格定好后，按 [methods-motion.md](methods-motion.md) `MI` 去 React Bits、Aceternity UI、Motion Primitives、Uiverse、21st.dev 找可直接取源码的组件。先审源码，再安装或复制，然后改成规格数值和设计 token，并记录来源与许可证。没有合适的，才用项目已有引擎自写。不引入付费组件、不运行未审的安装命令、不编造来源。

### B. 复杂视觉动效、3D 流体光影、运营动态图与宣传视频（首尾帧垫图 → 生视频模型 → 转码 MP4 / WebM / GIF / 动态 WebP 路线）

适用：纯代码写不出来的复杂 3D 材质旋转开箱、AI 能量球流体变形、液态玻璃折射流动、电影感动态背景、运营动态海报，以及宣传片、TVC、片头等视频成品。

这类任务不默认需要 Figma，也不默认调用 M1–M3。正式输入按产出合同至少包括：

- 传播或视觉目标、受众、使用场景、时长和画幅比例；
- 核心信息、脚本/旁白或分镜/镜头运动方式（推拉、自转、光影流淌、粒子耗散等）；
- **经确认的首帧静帧垫图（及有明确落位要求时的尾帧垫图）**；
- 品牌规范、已批准视觉/视频/音频素材及授权；
- 字幕、语言、音频和可访问性要求（视频类）；
- 目标导出格式（`MP4` / `WebM` / `GIF` / `动态 WebP`）、编码、分辨率、帧率、文件大小预算和源工程要求；
- 审核节点和确认人。

实现步骤与格式技术边界：

1. **先锁首尾关键帧垫图**：已交付的静态图直接作为【首帧静帧图】，不再重复确认；没有现成静态图时，先按 `TR4` / `V7` 生成首帧并自检构图、主体和文字区后直接进入生视频（需要固定落幅时再生成【尾帧静帧图】）。
2. **调生视频模型**：将【首尾帧垫图 + 镜头与主体运动提示词】传给生视频模型（如 Seedance、Kling、Veo、Figma Weave 视频模型等）或专业视频合成工具生成视频流。
3. **按场景转码导出**：
   - 独立宣发视频 → 导出标准 `MP4` 成片；
   - App 开屏、运营弹窗、网页 Hero 区或活动页局部动态图 → 使用视频处理工具（如 `ffmpeg`）截取无缝循环片段，转码为轻量循环 `MP4` / `WebM`、高清 `GIF` 或 `动态 WebP`。
4. **Lottie 边界硬规则**：生视频模型产出的是像素画面，**可以转成 `MP4`、`WebM`、`GIF`、`动态 WebP` 或 `APNG`**，但**不能直接生成真正的矢量 `Lottie (.json)`**。严禁将视频拆成数十张位图序列帧塞进 Lottie 冒充轻量矢量动画（会导致包体积暴涨与运行卡顿）；若必须交付真 Lottie，必须改走 `TR5-C` 矢量与代码生成路线。
5. 视频中出现任何产品 UI 画面时，该画面必须引用已定稿 UI 的准确节点、版本和适用片段；只有画面中的运动实际表达 UI 反馈、状态转换或空间关系时，才再引用对应 D5 与 M1–M3。静态 UI 展示不触发 M1–M3，也不能把整支视频强行套入 UI 动效合同。

### C. 轻量矢量动画：SVG、Lottie (.json)、图标或徽章微动效（IconScout 现成素材优先，矢量与代码生成兜底）

适用：导航栏图标切换、完成打勾、点赞爆花、加载指示器、空状态轻量矢量微动等，要求体积小（KB 级）、无限缩放边缘清晰、支持透明背景和动态改色。

正式输入按产物性质包括：

- 可编辑矢量源（SVG / Figma 矢量图层）、图层/路径命名和准确版本；
- 动画对象、起止状态、循环或一次性行为；
- 目标格式（动态 `SVG` / `GSAP` 矢量动画代码 / 标准矢量 `Lottie .json`）、尺寸、运行环境、交互触发和兼容约束；
- 颜色、透明度、混合、资源与授权；
- 时间、性能、文件大小及导出要求；
- 验收对象和确认人。

实现方式与边界：

- **先从 IconScout（官方 MCP 或 v3 API）检索现成 Lottie / 动态图标**，按需改色、改时长后使用；库里没有合适的，再基于 IconScout 或成熟图标库的专业矢量图标用代码/专业矢量动画工具加动画。不得临时手画简陋 SVG 图形充当动效主体，也不得调用像素级生视频模型。
- **IconScout 双通道 Lottie / SVG 支持**：
  1. **通道 A（MCP 优先）**：若已连接 IconScout MCP（`https://mcp.iconscout.com/mcp`），直接通过 MCP 检索并下载 `Lottie JSON`、`GIF` 或 `MP4`。
  2. **通道 B（内置 API 脚本兜底）**：若未装 MCP，直接运行本 Skill 目录下的 `python3 scripts/iconscout.py search -q "<keyword>" -a lottie` 检索现成高质量 Lottie 动画（获取预览 `MP4/PNG` 或在配齐 `Client-Secret` 后下载 `.json / .lottie` 源文件，及调用 `/v3/convert/svg-to-lottie`、`lottie-optimize`、`lottie-to-gif`、`lottie-to-webp`、`lottie-to-mp4`）。
- 若该动画的运动表达 UI 反馈、状态转换或空间关系，必须再引用已定稿 UI 的准确节点/版本、对应 D5 与 M1–M3；若是独立装饰或非 UI 动画，则按独立产出合同执行，不要求 Figma UI 输入。

### 正式交付边界

三类正式成品都必须由匹配目标实现路线的工具交付（`TR5-A` 交前端/客户端动效代码；`TR5-B` 交生视频模型产出及转码后的 `MP4/WebM/GIF/动态WebP`；`TR5-C` 交动态 `SVG` 或标准矢量 `Lottie .json`），包含可运行成品、准确版本，以及合同要求的可编辑源文件或代码和对应动态/技术验收。只有 Figma 预览时，动作状态只能是预览或测试就绪，不能标正式成品完成。
