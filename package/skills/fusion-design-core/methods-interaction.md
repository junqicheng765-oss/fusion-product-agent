# 交互方法库

只执行工作包点名的方法。已确认的职责、状态或路径不得在下游“顺手改”。
需要查看其他产品的交互行为时，单独调用 [methods-competitive.md](methods-competitive.md) 的 `CMP2 同类操作竞品`，再将适用条件带回本文件；不把竞品截图直接当成交互规则。

## I1 步骤切页

**触发问题**：哪些任务步骤应在同页，哪些需要分开？  
**最低输入**：主路径或受影响步骤。  
**跳过**：页面边界已由设计确认且本轮不改变职责。上游页面清单不算。

**步骤**

1. 决策对象变化、身份变化或不可逆提交时倾向切页。
2. 连续步骤围绕同一对象时可同页。
3. 一页出现两个同等主行动时拆分或降级。
4. 建立 `步骤｜页面｜理由` 对照。

**产出**：步骤—页面对照。  
**完成证据**：没有孤儿页面或无落点步骤。  
**不得替代**：用一个步骤对应一页的机械切法。

## I2 命名与进出

**触发问题**：用户如何找到、进入、返回和理解对象？  
**最低输入**：对象、角色、入口或现有导航。  
**跳过**：局部控件任务不改变命名和导航。

**步骤**

1. 对象优先使用用户语言，全程一名。
2. 导航使用任务而非组织部门。
3. 写每个角色从哪进、怎么回、怎么放弃。
4. 返回不得无提示清空有价值内容。
5. 页面栈超过 3 层时说明为何不能合并。

**产出**：词表、入口/返回规则。  
**完成证据**：同一对象无异名；返回结果明确。  
**不得替代**：品牌命名或业务术语拍板。

## I3 页面职责

**触发问题**：每页到底帮助用户完成什么？  
**最低输入**：路径或明确的局部任务。  
**跳过**：职责已由设计确认，且本轮仅修改职责内表现。上游只给了字段或页面清单，不算职责已确认。

**步骤**

1. 每页写“进来完成什么”，禁止“展示列表”式描述。
2. 先写页面类型，再写职责。类型只有这几种：首页、列表、详情、流程中的一步、工具页。任务点了「首页」或「打开后的第一屏」，类型就是首页，不能改写成某一个对象的详情。
3. 写一个主行动、下一状态、进入条件。
4. 列完成任务的最少信息；过多时拆分或分步。
5. 无职责页面删除或合并。
6. 用类型核对职责，对不上就改职责，不许进入线框、Figma 或高保真：
   - 首页：帮人开始或继续他自己的事，并看见这个产品能做什么。可以有主视觉，但不能只有一个对象加上「就这个」的按钮。行程类首页要把例子里的每一天或每一个地点标成 `data-stop`，至少 3 个，否则几何脚本报 `HOME_IS_ONE_OBJECT`。
   - 详情：决定眼前这一个对象。一张图、一个名字、一颗「开始这一个」的按钮，是详情，不是首页。
   - 列表：在多个同类对象里挑。
   - 流程中的一步：收集这一步的决定，不承担首页的入口。

**产出**

```
页面 | 类型 | 完成什么 | 主行动 | 下一状态 | 进入条件 | 对应步骤
```

**完成证据**：一页一个主任务；页面类型和职责对得上；全部页面可回溯路径。任务是首页时，职责里写得出「开始或继续自己的事」和「看见产品能做什么」。只有一个对象的名字，证据不算齐。  
**不得替代**：页面清单、站点地图、画面级配方。配方不能把首页改成详情。

## I4 结构与区块规格

**触发问题**：在不讨论视觉时，信息和行动如何组织？  
**最低输入**：页面职责、最少信息、关键规则。  
**跳过**：有有效结构主稿，任务只做视觉或还原。

**步骤**

1. 先按本轮产出合同确定载体：只有用户明确要求交付“低保真线框/灰框”时才画灰框；**若本轮目标是高保真 UI 设计稿或可交互 Demo，直接在 `design-decisions.md` 中写清区块结构与尺寸预算，严禁先在 Figma 里用 `use_figma` 画一遍简陋灰框再去给灰框填色充当高保真！**
2. 按阅读和任务顺序编号所有区块。
3. 每个区块逐项记录：顺序、职责、真实内容与数量（如 27 张手牌、4 张城市卡）、主行动、次行动、默认值及来源、隐藏规则及影响、适用状态。
4. 核对区块职责合起来能完成页面职责，主次行动与路径一致，默认值不替用户作高后果决定。
5. 摊开自动过滤、排序、权限等隐藏规则；不靠颜色表达顺序或状态。

**产出**：区块结构与规则标注表（含每个区块的顺序、职责、真实内容数量、主次行动、默认值与状态）。  
**完成证据**：不靠颜色也能按顺序理解并完成任务；每个区块字段齐全，无占位文案。  
**不得替代**：高保真视觉或已确认主稿。

## I5 主行动反馈

**触发问题**：何时可操作，操作后立即、成功、失败分别发生什么？  
**最低输入**：一个明确动作及其结果。  
**跳过**：纯静态内容，无用户动作。

**步骤**

1. 选择最简单控件；能选择就不强迫输入。
2. 写可用/禁用条件和原因。
3. 写操作后 0–2 秒内的反馈。
4. 写成功去向、失败去向、可否撤销。
5. 不可逆动作分离确认并写明后果。

**产出**

```
控件 / 可用条件 / 禁用原因
即时反馈 / 成功 / 失败 / 撤销
```

**完成证据**：用户无需猜测操作是否生效。  
**不得替代**：仅靠动效弥补缺失反馈内容。

## I6 异常矩阵

**触发问题**：主任务在空、慢、错、无权限或冲突时如何继续？  
**最低输入**：受影响页面或动作。  
**跳过**：展示性静态资产且没有运行状态。

**步骤**

1. 检查空、加载、校验、权限、网络、冲突/过期、部分成功。
2. 每项写触发、可见文案、用户行动、是否阻断、对应步骤。
3. 阻断必须提供重试、返回、保存、换路或清楚退出。
4. 保留已填内容，防止重试重复提交。

**产出**：异常矩阵。  
**完成证据**：主路径上的每个阻断都有可执行出口。  
**不得替代**：用“出错了”或一张插图表示错误设计。

## 交互交接

只要修改了职责、主行动或异常，就记录：

```
改什么 / 为什么 / 影响页面 / 需回归的路径步骤
```

给研发的交付至少包含：主路径、状态、校验、异常、隐藏规则和可后补项。
