# 设计风格引擎（Design Style Engine）

风格引擎负责把一整套设计风格识别出来、选定、落成可执行的规格，并批量应用到整个产品，最后检查各页面风格是否统一。它不只找组件，而是把颜色、字体、圆角、间距、导航、卡片、交互和动效规则作为一个整体来处理。

它和其他方法的分工：
- [methods-visual.md](methods-visual.md) `V0` 负责按语境**选**风格（26 种风格 + 6 种质感手法的参数字典）；
- 本文件负责把选定的风格**落到代码和设计稿上**：找到对应的设计系统和组件、映射到项目的技术栈、批量应用、验收一致性；
- 动效组件检索走 [methods-motion.md](methods-motion.md) `MI`，本文件只在资源层里引用它。
- 配色的检索、语义化和实际对比走 [methods-color.md](methods-color.md) `CI`：DS1 方向已有依据时先形成候选整体色彩框架，再制作/适配各元素；选定后由 DS2 校准固化，不另起一套选色逻辑或独立审批。

## 批量应用前的代表页门禁

本文件的“批量应用/统一全站”须遵守 [methods-close.md](methods-close.md) 0.4：多页先在一个完整代表页落实风格、组件与关键状态，真实渲染后运行 QA0、审美并排对比及修正，用户明确确认该版本后再扩展。风格词或参数方案获批不等于代表页获批。全部页面完成后重新终审并请求最终人工确认。

## 资源能力边界

| 类型 | 是什么 | 能不能自动化 | 可用资源 |
| :--- | :--- | :--- | :--- |
| 可复制的 UI 组件 / 页面区块 | 能直接拿到源码 | 能：按命令安装或复制，再改成项目的 token | shadcn/ui 组件与区块、Magic UI、Origin UI、Float UI，以及 `MI` 里的动效库 |
| 主题预设 | 提供实际存储的颜色、字体、字阶、几何和表面参数；个别条目另含规则，以文件为准 | 能导出和应用参数；不能自动提供页面构图、领域对象或完整组件 | `dto/`、Tweakcn 主题及 shadcn 的 theme 输出 |
| 设计系统及其实现 | 提供实际存储的组件、导航、状态、排版与交互规则；源码和平台覆盖分别核对 | 能应用已支持的 token 与组件；规范文档不等于现成实现 | `systems/`、Material 3、Ant Design、Apple HIG 及对应实现 |
| 视觉参考 | 提供整体或局部的构图、字形、图文关系、材质与工艺依据；不自动带可用控件 | 需看实际画面并转译；不能把读图或提取参数称为应用完成 | 随包全局视觉库、Awwwards、Dribbble、设计参考套件 |

主题应用、结构/组件复用、视觉参考转译分别记录；其中一项成立不代替其他项。视觉参考里的东西不能仅凭读图写成“已应用某某风格”；提取和改造须标来源，并在实际组合中验收。

## 四个资源层与风格适配器

| 资源层 | 作用 | 本地已打包 | 线上补充 |
| :--- | :--- | :--- | :--- |
| 风格库 | 选整套视觉语言 | `style-presets/systems/`（Apple、Material 3、Ant Design）、`style-presets/dto/`（V0 的 26 种风格）、`style-presets/themes/tweakcn/`（42 个主题） | [Tweakcn](https://tweakcn.com) 新主题、[shadcn 预设](https://ui.shadcn.com/create)、[Material Theme Builder](https://github.com/material-foundation/material-theme-builder) |
| 设计系统库 | 统一组件、token、交互规则 | 三套系统预设里的组件规则、字阶、圆角阶梯、实现方式 | [shadcn/ui](https://ui.shadcn.com)、[Ant Design](https://ant.design)、[Material 3](https://m3.material.io)、[Apple HIG](https://developer.apple.com/design/human-interface-guidelines) |
| 页面区块库 | 拿页面结构与模板 | `registry.json` 里每个风格族绑定的区块库 | [shadcn Blocks](https://ui.shadcn.com/blocks)、[Magic UI](https://magicui.design)、[Origin UI](https://originui.com)、[Float UI](https://floatui.com)、[Shadcn Studio](https://shadcnstudio.com) 免费部分；[Tailwind Plus](https://tailwindcss.com/plus) 仅限用户已购买许可证 |
| 动效库 | 交互反馈与动态表现 | 风格族绑定的动效库 | 见 `MI` |

**风格适配器**连接这四个资源层：
1. 从有效方向提取所需的视觉语言与规则；
2. 按项目技术栈核对组件、主题与资源的适用性；
3. 统一应用 token、组件规则和页面规则，并验证实际表现。

**技术边界**：
- shadcn/ui 或 Tailwind 项目换主题比较容易，改 CSS 变量即可。
- 已经开发好的 Flutter、SwiftUI 或复杂 React App，不可能只靠复制 CSS 完成全站换肤。必须先清点写死的样式值，再做组件映射和代码改造（见 `DS3`）。

## 本地预设库：先用本地，再去线上补

预设存在 Skill 里，不现查：
- `style-presets/registry.json`：总索引，包含三类资源的定义、12 个风格族、全部预设和线上库清单（含许可证与是否付费）。
- 预设文件使用 shadcn 的 `registry:theme` 格式，可用 `npx shadcn@latest add ./<文件>.json` 导入已支持的主题值。`meta.dto` 是额外指导，不会因导入主题而自动执行；以下字段仅部分条目具备，读取实际文件及关联资源，不能以一个薄主题代表整个库：
  - 字阶、间距、圆角阶梯；
  - 组件规则、导航、动效策略；
  - 适用与不适用场景；
  - 各技术栈的实现方式；
  - 来源和许可证；
  - 可安装资源。
- `scripts/style_preset.py`：
  - `list`：按风格族列出；
  - `show`：查看实际规格及风格族关联的系统、配方、区块和动效入口；`--json` 同样返回 `related_resources`。这些入口仍需按本轮职责与缺口筛选，不是自动采用清单；
  - `export`：导出 CSS、Tailwind v4、shadcn 或 antd token；
  - `apply`：写入项目的全局 CSS，可重复执行。
- `scripts/style_consistency_audit.py`：跨页一致性验收（见 `DS5`）。

**风格族**把同一种观感的本地预设和线上资源归在一起，用户点名的风格名、Agent 推荐的方向都先映射到风格族。现有 13 个：
- 苹果原生
- 安卓原生 / Material
- 企业中后台
- 极简 SaaS
- AI 产品（只用于 AI 对话、生成工具本身；AI 只是交互方式时按行业选）
- 编辑式 / 强排版
- 柔和 Soft UI
- 玻璃拟态
- 科技感 / 未来暗色
- 内容 / 电商信息流
- 大字普惠
- 游戏与互动娱乐
- 旅行与目的地

从任务的行业对象、操作与表达问题检索相关风格族，再比较能够支撑它的视觉语言；预设名称、所属族或“AI 产品”等题材标签不构成方向适配依据。DS1 候选记录需要回答为何保留该表达，并接上关键内容区所需的实际规则/参考；只有主题参数时继续查相应组件、构图和工艺来源，不能因此收口。检索无匹配或有明确冲突时按原 DS2/DS6 补足，不要求所有资源各用一次。

每个风格族有两类组件来源：
- `recipes`：通用组件配方的标签，见 [component-recipes/](component-recipes/registry.json)。纯 HTML、React、Figma 可按实际缺口复用其结构、交互和状态；项目已有适用正式组件时先复核沿用，不另拷结构。采用配方后仍按本轮视觉依据设计文字、图像、容器及细节，不能以默认外观代替表达完成。
- `layout`：React + Tailwind 区块库（shadcn Blocks、Magic UI 等）。只在 React 项目里补配方库没有的零件。它们以后台、官网、表单为主，不提供手机消费产品的页面构图；构图按 `RR` 看同类真实页面，结构用下面的画面级配方。

**画面级组织须有依据。** 本轮需要新建整体构图且采用配方时，先选适用的画面级配方再补零件；已有有效构图或限定局部修改时引用准确基线。零件拼装不能替代整体判断，配方不能覆盖本轮已成立的主视觉与页面职责。

| 这一屏是什么 | 先 copy 哪个 |
| :--- | :--- |
| 目的地主题画面 | `destination-hero`；它是局部主视觉，完整页面职责仍按 `I3` 判断 |
| 行程长什么样 | `itinerary-preview-card`、`itinerary-timeline` |
| 地图上选地方 | `map-with-sheet` |
| 内容 / 照片流 | `hero-media`、`feed-masonry`、`photo-card` |
| 游戏场景与对象 | `felt-table`、`playing-card`、`hand-fan`、`seat-nameplate`；对象识别及尺寸分级按 `U7` |
| AI 工具本身的输入页 | `prompt-composer`、`ai-result-card` |

拷进来之后仍按 `VT` 的目标稿改字体、照片处理和材质。配方默认样式拼出来的页面是模板脸。

**线上补充**：本地预设定下来之后，仍然去线上库查本地没有的部分：缺的组件和页面区块、Tweakcn 新主题、对应的动效组件。线上拿到的东西按 `DS6` 审过再用，好用的沉淀回 `style-presets/`。

## DS0 识别现状

**触发问题**：项目现在是什么技术栈、已经有什么风格，样式是集中在 token 里，还是散落在每个页面里写死？  
**最低输入**：项目代码或页面文件；没有代码时用截图或 Figma 主稿。  
**跳过**：从零新建、还没有任何页面。

**步骤**
1. 识别技术栈，看依赖和配置文件：
   - `components.json` → shadcn；
   - `antd` → Ant Design；
   - `@mui/material` → MUI；
   - `pubspec.yaml` → Flutter；
   - `.swift` + SwiftUI → 原生 iOS；
   - `build.gradle` + Compose → 原生 Android；
   - 只有 HTML/CSS → Web 技术实现；目标体验仍按 U0 核对，可能是网页，也可能是 App/小程序的浏览器样张。
2. 识别现有风格：
   - 读全局 CSS 变量、主题文件、Tailwind 配置或 `ConfigProvider`；
   - 再用 `style_consistency_audit.py`（不带 `--preset`）跑几个代表页，看实际用了多少种颜色、圆角和字体。
3. 清点写死的样式值：搜索页面和组件里直接写的颜色（`#xxxxxx`、`rgb(`）、圆角、字体和阴影，记下数量和位置。写死的值越多，`DS4` 批量应用前要做的改造越多。

**产出**：现状记录，包括技术栈、现有 token 来源、写死值的数量与位置，以及最接近的风格族。  
**完成证据**：写死值的清点有文件位置；一致性检查有实际运行结果。  
**不得替代**：`U0` 分流。有本次要求沿用的已批准基线、用户没要求改版时，走存量延展，不重选风格；待优化 Demo 不自动视为规范，先核对可复用约束与本轮范围。

## DS1 方向样张、方向确认与正式应用

**触发问题**：本轮需要通过真实画面确定视觉方向，而不是只凭风格名称选择。
**最低输入**：本轮主成果或子成果范围及必要前置的设计/复核依据、按 TR0 明确确认或已有适用选择的工具路线、同一代表页面或物料、实际内容、适用设备/渠道和硬约束。界面须先有有效流程、架构、内容层级与具体交互；海报须先有传播目标、信息主次、表达与构图；其他成果按 [成果、环节与子任务目录](methods-deliverable-routing.md) 核对相关依赖，不因嵌入项目或采用同一载体而跳过。
制作候选前按 [CT7](methods-context.md) 核对品牌、指定风格、参考、偏好和禁区；关键事实/约束缺失且会改变本轮决定时带推荐追问。仅缺主观偏好不强制文字选风格，可依据任务推导候选并供人看实际画面；不把未知写成“用户无偏好”，前期偏好也不能冒充样张选择。
**跳过**：已有适用且经复核的正式视觉方向、明确委托的方向，或本轮只做研究/流程/交互且不涉及视觉选择；不强制为所有任务新做候选。0→1 界面未指定风格时按主入口给出方向选择。

先判断是否适用下方「主视觉引领分支」：适用时用该分支完成本次 DS1，替代下面的整页候选比较，不重复执行两套探索。普通工具界面、严格还原及限定局部修改不因含一张大图就进入此分支。

营销/活动候选接续 CC3 的传播与参与思路，并继承 CC2「不能丢失的核心关系」，由它组织标题、主体图形、核心参与区和行动表达，再分别选择资产与控件；不能以题材相关、资源齐全或一张主图的完成度替代整案。文案先经 U1/U6 质量判断，必要变更沿原批准点处理，不能用“全部取自原稿”跳过编辑。

制作各候选前按 CI0–CI3 引用有效品牌/系统，或由当前方向推导本轮所需主辅色、中性色、强调及状态关系、纯色/渐变表现，形成临时色彩框架。主图、字形、图标和控件使用这份依据后在真实组合中校正，不让每个元素各自凭默认色选一套；已有有效框架按范围复用。此框架纳入原样张选择，不强制增加色板候选或配色确认。

**先展开表达，再筛方向。** 接续 CT7、CC1–CC3，区分共同固定项与可变表达：真实目标、参与机制、必要信息及有效品牌/阅读约束保持成立；未被确认的场景、物件、媒介、色温、情绪和构图不因先想到就成为共同条件。针对同一任务比较不同的感知侧重与画面组织方式，说明各案希望用户形成什么具体印象、通过什么图文关系建立这种印象，再从 V0、V7、有效系统与适用参考选择支持它的视觉语言。不能先锁定同一母题和氛围，再换渲染技法凑方向；同一个传达目标也不只对应一种情绪或配色。

**共同内容不等于共同表现资产。** 在取得或冻结表现资产前，沿同一候选记录比较关键表达区的“期望印象 → 对象/场景与图文组织 → 所需资产及构成”。承载本案表达的内容入口、对象呈现或行动区也参与判断，不能只比较头图与整体色板。真实内容、正式商品照片、功能惯例及有效系统可共用；其裁切、承托、尺度和上下文仍由各案组织决定。拟共用的物件、插图或摄影母体须说明为何适合各案、由什么关系形成不同选择；“已经做好”“节省制作”“同一任务”不足以冻结它。先判断表达是否成立，再决定复用、改造或另取资产，不为求新强制换媒介、换库或重做全部图片，也不靠添加无关装饰制造差异。

风格池与适用品类是检索入口，不是互斥围栏；跨池比较有依据的表达，不逐条填满全库或用固定分数代替判断。各案分别核对方向参考与工艺标杆，不能只继承首案的图像、色板和提示词后替换媒介词。淘汰须指认具体特征如何违反本轮事实、品牌、理解或操作约束，保留匹配理由、代价与推荐。视觉语言不等于业务机制，缺少某种玩法只能排除相应虚构承诺，不能据风格名称连带排除其色彩、空间、材质和构图语汇；不为视觉比较擅改参与规则。

检索表达和工艺时调用 [随包全局视觉库](visual-reference-library/README.md)，配合 RR 的当前真实参考：先据任务、受众、品牌、内容及实际画面质量确定侧重，近期表达只作有来源的适配依据，不把“流行”当成适合所有任务。目录未命中可在线补充，不逐类生成或为凑数量尝试所有画风。比较两案时，可分别从近期真实案例提炼、从任务背景和审美约束自主构思，再为各案取得适用图片；两案均须实际垫图、自审，起点不同不豁免整组差异判断，也不新增文字方向审批。完整 UI 参考走线上检索，不从包内海报推定控件与状态方案。

**比较完整的视觉提案。** 各案分别设计背景及氛围、主体与空间关系、构图、文字、色彩/材质和主要控件；先决定背景承担的作用、层次与范围，再按 CI/V7 制作。方向依赖场景、空间或光效时须实际呈现，不能省成孤立主体；收敛方向也需有经过设计的底色、留白及空间组织。透明素材是分层格式，不决定最终画面形态；不强制所有方向复杂背景、渐变或立体化。制作前横看候选简报：去掉方向名称与媒介词后，期望印象、主导色彩、空间结构、标题性格和核心图文关系是否仍高度重合，共享项是否确有约束依据。若可选表达已趋同，先回到上段重推受影响方向，再制作资产；不能靠补一张差异很大的低质量陪选图解决。

**单案视觉语言的成立依据。** 从准确画面指认构图、字形、图像、内容组织与适用的主要行动怎样共同形成预期表达：关键区的形态、比例、边缘或空间节奏如何承接、变化或有意对照，而不是仅列颜色、字体和照片处理。不要求各处同材质或重复同一符号。参考须说明支持的是整体图文关系、局部手法还是工艺完成度；局部字形或滤镜的参考不能自动为整案背书，整体关系或完成度缺乏依据时补适用参考或重推受影响部分，不能用方向名称或补写说明代替画面成立。

本轮视觉方向未定且需要比较时，默认由 AI 筛选并制作 2–3 个匹配且有实质差异的方向供人看图选择，主视觉引领分支同样适用。已有适用明确方向、只委托一案或局部精修时按范围复用；硬约束下可行方向不足时说明依据，不制造陪选。此数量只用于本轮视觉比较，不改变 CC2 概念数量的判断方法，也不增加文字方案审批。

1. **建立独立方向样张。** 在 `<任务目录>/explorations/<候选>/` 或明确独立的设计草稿分区制作 2–3 个有实质视觉区别的候选，引用同一代表对象、经 U1 筛选后成立的同一内容基线、信息职责、交互含义和视口/渠道。允许调用预设、组件、素材与该类型适用工具；沿用原来源、授权和资产标准，不启用范围外安装或外发。候选只在隔离位置输出，不批量改正式项目或制作其他页面。
2. **候选用于比较整体方向。** 构图、字形与排版、图像媒介、色彩和材质、适用的运动表达可作为一套方案变化，不要求拆成几十轮单变量试验，也不强求每个维度都变化。各候选承担表达的主副标题、眉题及适用的主要控件需参与其概念，按 [V3](methods-visual.md) / [TY](methods-resource-routing.md) 判断排版或独立字形资产，按 DS2 推导控件外观；不把同一套通用文字和按钮机械套到所有候选。保持已成立的必要内容、职责和行为依据，不暗改业务规则或删除必要条件制造好看。原稿无效文字可按 U1 提出清理建议，展示原文、改法、依据与影响，经人确认后更新共用内容基线；不要求为保持同内容而保留无效文案，也不允许个别候选私删或擅改内容。允许必要的视觉比例与排版调整，记录差异；若涉及架构、流程或创意机制变化，先回相应专业环节复核，不能混作纯风格选择。确需判断单一参数的效果时再用 V6，不把整体偏好归因到某一变量或声称转化提升。
3. **实际渲染、自审后展示。** 每个候选需在真实目标尺寸下可查看并标明探索版本，覆盖足以比较关键表达和实际内容的范围，不用风格词、局部色板或情绪板替代。按上述共同视觉语言与参考支持范围判断单案适配和完成度，另判整组选择的感知跨度，任一项不能由其他项抵消。先看完整画面的第一印象，再指认主导色彩、情绪、空间、标题与图文组织怎样共同形成不同选择；媒介、参数或模块顺序有变化但整体仍属同类感觉，标为同一方向的变体，不能冒称不同方向。遮住主图、隐藏方案名等可辅助诊断，不是固定评分或变化维度数量门槛。需要不同方向却实际趋同时，回到简报、参考和制作输入重推受影响案，不能只换颜色或在说明里强调差异；有依据的品牌约束确实只允许变体时如实说明比较范围，不放宽事实或制作质量凑差异。执行适用 QA0 与审美比较，发现问题先改再审；未覆盖的交互、全页状态或跨页范围如实记录，不能冒充完整代表页或整套通过。并排解释表达、适配理由、取舍与推荐，整组差异未成立不得标为方向比较通过。
4. **请人选择并等待。** 用大白话询问偏好的方向，同时提供“都不喜欢/都需要调整”的出口，不要求勉强选一案。分开记录偏好方向、实际接受范围与未解决问题；相对更喜欢、勉强选择或选后补充否决，不自动转为可复用基线，走下方反馈分支，后续明确反馈更新当前有效状态并保留原记录。保留样张版本、前置依据、差异、自审记录、隔离位置及选择来源，沿用现有 `PENDING_CONFIRMATION` 等状态。发出问题后不得先正式应用、扩展其他页面；沉默、自评或工具成功不构成确认。已有正式方向按跳过条件复用，不重复征求相同决定。
5. **选定后才正式制作。** 将选定方向转入 DS2–DS5 和现有 `design-decisions.md`，完成本轮要求的完整代表页及核心状态。再次自审后按 [methods-close.md](methods-close.md) 0.4 请人确认可否作为扩展基线；该确认之后才制作其余页面，全部完成后整套终审与最终确认。单页省略扩展门禁，仍须最终确认。样张选中不等于完整代表页已批准。

修订样张时回查其成立依据：删改触及主导构成或关键图文关系，须重新组织受影响区域并看整案是否仍成立；原手法不适用时寻找替代表达，不能把删除后的空缺视为设计完成。无新碰撞、模块仍齐全或更符合平台习惯，只证明相应项；重新核对单案完成度与整组差异后才返回看图选择，不增加人工审批轮次。

**产出**：有前置依据和偏好来源的独立候选样张、关键表达区与资产共用/变化依据、实际感受差异及渲染/自审记录、方向选择记录，以及后续正式代表页的输入。
**完成证据**：可查看的准确候选版本、可指认的整体表达差异及标题字形依据、人对方向的明确选择、正式实现未被未批准候选覆盖；代表页和整套确认另有准确记录。
**不得替代**：前置专业设计、必要调库和资产规范、完整代表页审批或成品有效性验证。探索只决定视觉方向，不自动扩大业务范围。

### 候选未接受或选后仍有问题时：具体反馈与定向修订

这是原看图选择中的条件分支，不向每次展示追加问卷或审批。用户否决候选、勉强选中或选后指出质量仍不符合预期时，接续已知原因，保留相对偏好及确已接受部分，将受影响版本记为需修订；不能继续引用早先的选择证明当前整案已接受，也不将其解释为产品目标、业务规则和所有既有设计均被推翻。

1. **承接已说清的反馈。** 先归纳不喜欢的具体位置、已认可或希望保留的部分，以及已表达的倾向。已有原因不重问；AI能明确定位的实现缺陷先自行修正，不能把自己的质量检查转交给用户。
2. **需要补问时给具象、可多项作答的原因选项。** 根据实际样张提供相关维度：画风与气质、主题/创意或主体表达、配色的明暗冷暖与浓淡、构图/背景/空间、字形与排版、精细度、信息与文案等。可同时选多个，也可补充其他原因或表示暂时说不清；只列当前有意义的维度，不要求会设计术语。宿主真实支持多选时用原生多选；不支持时在同题明确可填多个编号或自由描述，不虚构工具参数，不将单选控件称为多选，也不拆成连续多轮单选。
3. **一并了解希望往哪里调整。** 让人用自己的话补充偏好的感觉、倾向、想保留或避开的特征，可提供参考但不强求。只补会改变下一轮决定的缺口，不要求字体文件、色值或完整专业方案；可借当前实际画面说明可观察的差异来帮助表达。用户说不清倾向或明确让 AI 重新推荐时，记录未知和委托边界，由 AI 根据任务、已知否决点与适用新参考提出候选，不把完成偏好问答设为阻断；AI 推荐不冒充人已确认新方向。
4. **按反馈回到受影响方法。** 画风/气质回 CT7/DS1，主题表达回 CC，配色回 CI，构图空间回 U3/DS1，字形回 V3，素材工艺回 V7，信息文案回 U1/U6。多个原因可合并处理，先复核共同依赖，保留已成立的规则、结构和好资产；只在有依据时改变更上游决定。原 TR0 有效路线继续使用，实质变化仍按其规则处理。
5. **实际修订、自审，再回原选择点。** 在同一记录保留被否决的准确版本、用户原因及来源、认可/未认可范围、偏好与未知、修改项和新画面证据。所需答案未到时等待受影响部分，不把沉默补成偏好。反馈足够后制作针对问题的新版本，适用 QA0 通过再展示，说明改了哪里及其依据；不是无目标再抽一批图。新版本仍待人看图选择，未确认不正式扩展。

涉及删除或停用风格/资源时，先核对实际采用的预设、配方、生成提示和自写外观，按用户明确范围处理可定位条目并记录影响；没有对应库条目时说明来源，将被否决的组合及特征记在本轮任务，后续不原样推荐，不能凭相似风格名删除无关库。项目反馈与通用禁用范围分别记录，不将单次失败扩成未经授权的全局禁令。

### DS1 主视觉引领分支（条件使用）

**适用判断**：主题、情绪或品牌识别主要由主视觉的图文构图建立，且页面需要从中延展视觉语言时，说明为什么适用。主视觉可以由标题、图形、摄影或它们的组合承担，不等于必须放大图。它可作为所属页面的子资产，不要求另立独立海报委托。已有有效文字方向、主视觉或规范按准确版本复核后复用；只委托主视觉时到该成果结束，不补做页面。

1. **建立依据。** 引用 CT/BR、RT0、CT7 和 CC1–CC4 的已有结果：产品是什么、服务谁，本次活动/页面服务谁、进入情境、希望传达的信息与感觉、真实规则、品牌/偏好及禁区。信息可推导时标推断，未知且会改变方向时带判断和推荐询问，不让使用者重填已有材料。涉及界面制作仍须具备本轮有效流程、架构、内容与交互依据，不用主视觉替代这些判断。
2. **查适用参考。** 按 [RR 视觉分支](methods-resource-routing.md) 从同题材、主体及实际活动起检索，核对目标市场成熟产品/平台及相关品牌近期案例，再按需要用设计社区扩展表达；方向未定时不先锁定画风再补图。实际看原作/详情中的画面，按 CC4 记录可观察手法、适配与不可照搬部分，共同提供主题、方向与工艺依据，指向具体候选和 V7 的实际图像输入。活动/作品日期、转载更新和查阅日期分开，未核实时不宣称近期或最新；趋势结合受众、品牌、渠道及阅读取舍。普通业务界面不能代替具体媒介的工艺标杆，未通过质量检查的生成母体不能自动成为标杆，参考和前期偏好也不冒充真实用户证据。已有适用依据可按准确版本复用，不按来源名单凑数量。
3. **AI 推导并筛选可成图的方案。** 在 CC2 的同一记录承接有效概念与核心关系，再按上方方向筛选方法比较视觉语言，不从主体物件直接锁定媒介。逐案说明：主视觉主要承担其中什么含义，怎样通过主体的状态、变化、空间或图文关系表达，哪些含义由标题、关键内容或程序信息共同补齐。传播主角、情境背景与表达手法分开判断：主导图文关系须承载本轮要重点传达的含义，不能将辅助情境或单个动作升级成主角，再把主要任务缩成次级说明。先判断主题是否成立，再比较情绪、画风与差异；不能为制造不同方向放弃共同任务。
   - 把核心想法转成可指认的主导关系或视觉事件：首先看到什么，什么比例、空间、形态或图文关系产生预期感受，标题怎样参与，辅助内容各自增加什么。对决定主题的场景或符号，说明它为何适合这条核心关系；“相关、好看、能营造氛围”不能单独证明它应成为主导。若它原样放进无关活动也同样成立，检查是否只剩泛情绪、泛题材或通用动作；有意采用抽象图形或氛围背景时，须在本次可见组合中由明确的图文关系承接核心任务，不能靠设计说明补义。
   - 先删减或降级无助于表达的元素，再确定主体、媒介、材质、色彩和实际参考。不把相关名词逐一翻成物件清单，是防止堆砌，不是删掉核心对象或关系；也不要求每个含义都画成实体、全部塞入主图。参考提供构图或工艺，不自动授权将其题材、情绪或主体替换成本活动主题。
   - 形成同一完整画布的构成输入，引用核心关系及各部分的承载位置，再按 V7 拆出生产提示与接合要求。每项区分用户给定、原始文件、参考和 AI 推导，记录取舍与推荐，不在成图后补造来源。无需先让人从无图文字方案中选方向；需要人补关键事实、决定业务取舍或范围时仍按原规则询问。用户只委托文字方案咨询时到该终点结束，不追加图片制作。
4. **直接制作可比较的完整画面。** 按 TR0 推荐并确认实际制作路线；已有覆盖主视觉与后续界面的明确选择可复用，不逐操作重问。必要输入及路线成立后，按本节筛选结果和适用数量在隔离草稿制作方向样张；页面任务以完整首屏/KV组合呈现，包含该案成立所需的背景、空间氛围、主体、标题、说明与主要操作，不能只交透明物件。只委托独立主视觉则沿其合同，不扩为界面。不强制先过文字方向审批，实际文案变更仍按 U1 批准，也不另凑整页方向。按 V3、V5/V7 与适用 IM 做标题、构图、素材/生成及来源记录。依据来自本轮推导、真实内容与参考，不反向要求先锁定 UI 预设。方向样张可整图展示，已明确要求的分层仍须落实；正式制作按 V7「生产分层与动态合成」拆解，不将样张位图直接当成最终界面。
   - 页面方向样张须合成本次选择需要评估的主图、表达性文字、标签、主要控件及已纳入范围的关键内容区，使人能够判断整体语言。依 CT0/V3 落实明确制作要求，按 U3 的同一记录落实内容组的组织决定与实际位置，所需图形再接 V5；不能只用功能图标证明完成。适用参考须覆盖当前要判断的内容组织或控件问题，只有主图/局部工艺支持时不能为这些区域背书，已有适用依据可复用。候选阶段使用临时 DS2 语言，不等主视觉确认后才设计已纳入样张的内容区。不能把主图做完、其余留成通用默认后宣称方向完成；也不因此扩成全页或补做未委托的控件，剩余范围到原代表页节点验收。
5. **先自审，再请人确认主视觉。** 打开准确版本的实际成图，先逐项对照明确要求与成品证据，再在目标比例/尺寸检查主题是否传达、信息主次、图文关系、标题逐字与可读性、各关键内容区表达、素材风格、裁切和必要适配，并与适用的主视觉/编辑表达参考比较；同时执行上方通用 DS1 第3步的整组感知跨度检查及适用 QA0，问题改后重审。明确要求缺项、表达不足或整组方向趋同时先回炉，不把已知不足标成推荐候选让人代审；失败探索可用于说明问题，但不列为已完成待选方向。说明覆盖和编辑限制，再请人确认可用的准确版本，保留都不喜欢/都需调整的出口并接上方反馈分支；使用既有待确认状态并等待。AI 方案推导、工具成功或自评不能代替这次确认；主视觉自审不称完整界面或交互验收。
6. **确认后延展整页。** 按 DS2 将选定主视觉转为本轮唯一任务规格，结合 U1/U3/V3 的信息作用和交互要求应用到代表页及核心状态，再走原代表页/最终确认。主视觉确认只批准视觉方向，不批准整页或其余页面扩展。方案推导、主视觉、规格、代表页的版本及确认来源写回同一记录，不另开账本。

本分支由 AI 完成必要分析及概念推导，让人依据实际主视觉选择，不设必经文字方向审批；纯文字咨询按其委托处理。主视觉确认、完整代表页和最终确认各有范围，不叠加整页方向、相同参考垫图审批或未委托的动效升级。确需改变已确认方向、范围或工具路线时，解释变化并确认受影响部分。

## DS2 提取风格规格

**触发问题**：选定的风格落到这个产品上，具体是哪些数值和规则？  
**最低输入**：本轮准确的候选/选定方向或有效系统、表达依据、品牌约束及页面信息/交互输入；主视觉引领任务引用准确 KV 版本，采用预设时引用真实 ID。不以必须有主视觉为语言转译的前提，也不将候选写成已确认。

方向样张阶段可先用同一记录承接 CI 的候选色彩与表达参数，标明候选版本和适用范围，不等待最终 KV/DS2 才开始配色，也不将临时规格写成已批准品牌规范。选定后核对真实图像、文字和背景关系，校准并固化为本轮正式规格。

**主视觉引领分支的规格来源**：从已确认主视觉提取可延展的色彩关系、标题字形/排版、图形母题、图文构图、材质及疏密节奏，说明各自如何用于不同信息角色与组件。图中颜色须转换成可读的界面语义色并检查对比，不能机械取色后把整张纹理铺满控件；正文与操作保留清晰语义，日期/倒计时等由真实数据驱动，特殊字形组合按 V7 保留可访问的等价文字与适用状态。结合品牌、内容和交互推导实际值与应用边界，标明来源/设计推导、候选与确认范围，不冒称新品牌规范。主视觉给出方向，整页可用性和完整性仍须验证。

正式页面制作前同时按 V7 规划素材层与动态数据：背景/主体图像、标题、装饰及程序文字/控件分别说明独立替换和动效需要，再单独取得资产、按坐标与层次合成。整图样张只是表达参照，不把倒计时、日期或操作烘焙进不可更新的底图。

**从视觉语言到界面元素（所有视觉路线共用）**：引用 U3 的内容组 ID 与组织决定，从本轮准确的整页方向、主视觉或有效系统提取可见语言，说明顶部、内容入口、图像呈现、背景/承托、主要控件与图标中哪些适用，怎样保留、改造或有意保持中性。文化/主题表达按 CT7 的实际输入与参考确定，不从行业或国别直接套传统符号。需要表达的区域不得以“无 KV”“用了宋体/底色”或“套了成熟配方”省略转译；底纹、装饰、图像框形与留白分别判断作用，不规定装饰数量。核对形态/边缘、比例、空间节奏、表面与光影等本案实际起作用的关系；仅沿用主题色或列出参数不算承接，同一语言也不要求处处透明、同材质或重复同一造型。承接判断先看完整方向中的主导关系，不以次要局部的相似替整体脱节辩护；有意不同须结合具体职责或约束，在同版组合中指认仍成立的共同关系或有意分界，仅称“提高对比”“更有动感”不能代替画面依据。先查已有组件/配方的可用外观与状态，明确保留和改造部分；行为可复用不表示外观已完成。

在同一规格中落实主副标题/眉题的文字角色、更新需求、字形/排版与资产选择；标签的字距、空间和适用图形承托；主要控件的形态、比例、适用表面、文字及图标组合；图标/装饰的作用和取得方式。色彩按 CI/V2 判断纯色、渐变、透明叠层及纹理的适用性，记录实际参数和状态。各项服务同一方向且保持主次，不要求所有参数都变化或所有内容都有装饰。

图标选择和调库统一按 V5 的作用、图文权重、实际尺寸、分组规范与来源规则执行，规格引用同一组 ID。页面可包含不同表现组，组内按用途、权重及视觉变体优先采用同一真实集合；跨组共享本轮适用的色彩、尺度与空间关系。不能把页面含多种图标表现直接判为不一致，也不能凭同一风格标签就认定来自同一套系。

在同一规格中接续本轮相关预制资源的选择与落位：先按成果、方向与技术栈读取相关候选中实际存在的完整规则，区分默认配色/圆角等参数与可复用的组织、排版、组件及状态规则。局部默认值不合适时先判断能否适配，不能仅据此整套排除；适用规则优先复用，需要差异的部分再改造。沿同一内容组记录准确版本、采用/改造的规则、当前任务值、实现位置及成图证据；查阅和未采用另标状态，不把零散图片或字体使用概括成整套风格已应用。确实不适用时说明具体冲突及改造仍不能满足的原因，不要求遍历全库或凑采用数量。已有有效系统或限定局部任务先复核沿用；非 UI 成果按资源真实适用范围取用，不强迫套 UI 预设，非 UI 参考也不冒充完整 App 规范。字体目录仍须核对实际文件或系统命中、语言及字重覆盖。

所有路线先完成上述语言转译与资源适用判断，再取参数。任务推导承接预制规则未覆盖、与有效约束冲突或确需自主表达的部分，继续保留适用规则的来源与采用关系；不能用“任务推导”作为整案跳过资源的标签。全部不适用时可自主设计，但须有上述真实依据与替代方案的表达、制作和验收证据。主视觉引领或非 KV 整页方向采用任务规格时，以下“整套预设”“只允许正式品牌色覆盖”及“页面结构跟风格族”以这份有依据的规格为准；正式品牌和已确认表达优先，不为了采用数量拼接互相冲突的预设，也不强套近似模板。局部改造只写入任务规格，不改全局预设、共享库或默认主题；未采用不强制新建预设 ID。采用部分按下列步骤读取和校验，改造值接回同一任务规格及实际画面验证。

**步骤**
1. 运行 `python3 scripts/style_preset.py show <ID>`，需要机器读取时用 `show <ID> --json`。CSS 语义主题及 DTO 派生输出以当前模式的 `cssVars` 为唯一生效色源；原始设计色只作参考。原生系统导出另依实际平台 token/算法及已支持的映射，按 `platform_export_contracts` 核对传播与未传播字段，不把 CSS 覆盖自动当作原生已应用。整套采用时将所选预设作为整体基线，部分复用只承接选中的规则；任务规格的适用改造仍按上方规则记录与核验。
   - JSON 的 `design_spec.values` 保留实际存储的字阶、间距、几何、组件、动效、实现与来源等设计规则，`registry_entry` 保留目录信息；不存在的项不补造。筛选与改造须读取适用规则，不能只看返回的色板或默认圆角；其中的历史色值和提示片段仍不能覆盖上方生效色合同。读取规则不等于采用、自动导出或已经落地，实际采用与改造继续对应到本轮区域和成图。
   - 在本轮实际采用范围内，常规文字的字体，以及圆角、间距、导航、卡片、交互规则、动效从所选预设取。承担表达的静态文字按 V3/TY 判断合适排版或独立字形资产，将来源、用途、与整体风格的关系及检查结果纳入本轮规格；预设不把主副标题、眉题锁死为同一种排版，也不因局部表达扩大为未授权的全站字体替换。
2. 预设没覆盖的项，按以下顺序补：
   - 先从同一风格族的其他本地预设补；
   - 不够再去线上设计系统的官方规范查；
   - 都没有时，从已有参数推出来，并标“推导”。
3. 品牌色只在用户给出了正式品牌色值时，才替换预设主色。没有正式品牌色，禁止运行 `from-brand`，禁止为了对比度或“像某产品”另造一个主色。替换后检查对比度：正文 ≥ 4.5:1，大字和图标 ≥ 3:1。不够就在同一色相里加深这颗按钮或这块字的底，不换一套色。浅色字对比不够时，改底的深浅，字仍用预设的浅色前景。不要把浅色字改成黑色贴在高饱和底上。
   - 这保护实际采用的预设主色与正式品牌约束，不要求所有文字、业务内容与行动共用主色或色相。按 CI0 分别判断所需内容角色及视觉重量，再映射实际颜色与 V3 排版；任务推导规格仍按上方边界执行，不把新增内容强调角色冒称改造品牌规范。
4. 把规格写进任务包，作为本轮唯一的风格数据源（与 `V0` Step 5.2 是同一份）。写进 CSS 变量只是开始。页面构成按已成立的职责、内容关系与所选语言落实，组件应用适合其角色和状态的表面规则；平面、无纹理也可成立，不为覆盖材质而加效果。只换背景色，规格不算落地。

**产出**：风格规格卡：八类规格的具体数值，每项注明来源（本地预设 / 线上规范 / 推导）。  
**完成证据**：每个数值能对上预设文件、官方链接或有记录的设计推导；关键内容组及主要控件的转译决定能对应实际渲染位置，与 U3 共用证据。V3 标题字形/排版推导须有表达依据、准确版本和真实尺寸渲染检查，不能以“推导”掩盖无依据的随意取值。
**不得替代**：`V0` Step 3 的适用材质检查。规格说明各组件实际采用的表面、状态与边界，不按装饰数量或强制同材质验收。

## DS3 组件映射（风格适配器）

**触发问题**：项目里现有的组件，分别对应到目标风格的哪个组件、哪条规则？  
**最低输入**：`DS0` 现状记录与 `DS2` 规格卡。

采用任务推导规格（含非 KV 整页方向）时引用 DS2；下表的预设导出/配方是适用功能底座的取得方式，项目已有合适组件先复核复用。布局及视觉映射服从已成立的职责、信息表达与确认方向，不能用通用画面配方替代本轮整体构图；涉及结构或行为变化回相应专业环节核对，不擅改业务。

**按技术栈的应用方式**

| 技术栈 | 怎么应用风格 | 注意 |
| :--- | :--- | :--- |
| shadcn / Tailwind（React） | `style_preset.py apply <ID> --css <全局 CSS>`，或 `npx shadcn@latest add ./style-presets/<文件>.json`；线上 shadcn 预设用 `npx shadcn@latest apply --preset <id> --only theme,font` | shadcn 组件自动跟随；自写组件里写死的值要改成 `var(--…)` |
| 纯 HTML / CSS | 采用适用配方时执行 `component_recipe.py copy` 并实际复用；预设基线用 `style_preset.py export <ID> --format css -o theme.css`，任务推导规格按 DS2 落盘 | 无匹配配方时按已成立的整体构图与任务规格制作并核验，不虚构配方或预设 ID。CSS 变量不能代替页面设计；可复用样式集中到实际主题变量 |
| Ant Design | `style_preset.py export <ID> --format antd`，放进 `ConfigProvider theme={{ token }}`；暗色加 `theme.darkAlgorithm` | 组件级差异写进 `theme.components` |
| MUI | 按规格卡写 `createTheme({ palette, shape, typography })` | 圆角、字阶对照规格卡 |
| Arco Design / TDesign / Fluent UI | 用各自官方的主题 token 机制（Arco 主题配置、TDesign CSS token、Fluent `createLightTheme` / `createDarkTheme`），数值从规格卡取 | 本地没有它们的预设，按规格卡逐项对照填写 |
| Flutter | `ThemeData(useMaterial3: true, colorScheme: …, textTheme: …)`；Material 风格用 `ColorScheme.fromSeed` | 自定义组件里的 `Color(0x…)` 要改成 `Theme.of(context)` |
| SwiftUI | 苹果原生风格直接用系统组件和语义色；其他风格用 Asset Catalog 颜色加自定义 `ButtonStyle` / `ViewModifier` | 不嵌入 SF Pro 字体文件到 Web 或非苹果平台 |
| Jetpack Compose | `MaterialTheme(colorScheme, typography, shapes)` | 同上，写死的 `Color(0x…)` 要收进主题 |

**组件映射表**：现有组件逐个列出，标明以下四项：
- 对应目标风格的组件或规则及其适用依据。
- 仅替换 token 是否足够；信息位置、导航关系或行为改变时，列出所需结构改造。
- 组件从哪里来：先核对项目已有适用组件；需要配方时用 `python3 scripts/component_recipe.py list --tag <风格族的 recipes 标签>` 检索，实际采用则执行 `copy` 并复用，不能只查阅后声称已调用。无匹配时按实际技术栈和视觉依据选择区块、系统组件或必要制作，核对源码与来源；整体构图仍依本轮职责与已定方向，不由通用区块代答。
- 选风格时可以先看效果：`python3 scripts/component_recipe.py preview --preset <风格编号> --tag <标签> -o <文件.html>`，截图对比两三个候选预设，比读参数表直观。
- 新写的配方放进 `component-recipes/recipes/<id>.html`（元数据注释 + `<style>` + `<!-- demo -->` 结构 + 可选 `<script>`），只读风格变量和 `base.css` 的 `--r-*` 变量，然后运行 `index`。`index` 会检查标签、依赖、图标文件，以及配方内每个类是否有样式来源。
- 改造涉及的文件。

**产出**：组件映射表与改造文件清单。  
**完成证据**：`DS0` 清点出的每个写死值都有去向；每个现有组件都有映射结论。主屏先说明整屏组织依据与实际实现：适用配方、有效系统或任务推导构图均可，不能让单个字段配方代替完整构图，也不以必须命中某个画面级配方作为完成标准。
**不得替代**：`U4` 的组件功能判断。换风格不改变“用什么控件解决什么任务”。

## DS4 批量应用到整个产品

**触发问题**：怎样一次把风格改到所有页面，而不是逐页手调？  
**最低输入**：`DS3` 映射表；改已有产品时还需要 `DS1` 的用户确认。

**顺序固定**：先 token，再组件，最后页面。
1. **token**：用 `DS3` 的方式写入一个集中位置（全局 CSS、主题文件或 `ConfigProvider`），全产品只有这一处定义颜色、字体、圆角、间距和阴影。
2. **写死值收口**：按 `DS0` 的清点，把页面和组件里写死的值替换成 token 引用。
3. **组件**：按映射表改组件本身，包括结构改造和材质规则；从区块库补进来的组件同样改成用 token。
4. **页面**：只处理页面特有的布局问题。页面里不再出现新的写死样式值；确实需要例外的元素加 `data-style-exempt` 并写明适用范围与理由。

**不允许**：
- 逐页手调颜色和圆角；
- 同一个组件在不同页面各改一套；
- 改风格的同时顺手改布局、业务逻辑或事件行为。

**产出**：修改文件清单，以及 token 所在位置。  
**完成证据**：搜索写死的颜色和圆角，结果只剩加了豁免的元素。  
**不得替代**：`U3` 的对齐与防碰撞检查。换完风格仍要重跑 `ui_geometry_audit.py`。

## DS5 跨页一致性验收

**触发问题**：所有页面是否都在同一套风格里，没有漏网的旧样式和页面间的差异？  
**最低输入**：应用后的全部页面，至少覆盖每类页面各一个。

**步骤**
1. 预设分支运行 `python3 scripts/style_consistency_audit.py <所有页面> --preset <ID>`。采用任务推导规格时，该脚本尚不接受任意任务规格：不带 `--preset` 运行其可覆盖的一致性检查，并将实际样式逐项与 DS2 的色彩、字体、圆角和组件/状态规则对照，保留数值核对证据。不能传虚构 ID、用近似预设覆盖确认结果，或把无预设的 `passed` 称为任务规格已全量验证。
   - 线上或开发服务器页面：用 `--probe-js` 取出探针脚本，在浏览器里执行，把结果存成 JSON，再用 `--from-json` 一起检查。
   - V3/DS2 已记录并采用的专门标题字体或字形，可对准确标题元素沿用 `data-style-exempt`，写明来源、用途及依据；不对整页或含常规文字/控件的父容器豁免。脚本会跳过该元素的样式检查，因此必须人工补查其字体/字形、颜色、形状及跨页用法，连同逐字、可读性和真实尺寸结果写入同一报告；不能为了消除报错直接加标记，也不能把脚本通过当作标题已通过。
2. 下列问题在各自检查范围内须解决；预设分支由脚本校验色彩/圆角/字体，任务推导分支由前述逐项核对补齐，跨页漂移继续检查。不用整页 `data-style-exempt` 绕过：
   - `OFF_TOKEN_COLOR`：颜色不在色板里；
   - `OFF_SCALE_RADIUS`：圆角不在阶梯里；
   - `OFF_TOKEN_FONT`：字体不在字体栈里；
   - `CROSS_PAGE_DRIFT`：同一类组件在不同页面长得不一样。
3. 每类页面各截一张图并排看，找全产品做得最弱的那个组件，它也必须达到风格参数（与 `V0` Step 3 同一检查）。
4. 不通过就回到 `DS4` 改，改完重跑脚本、重新截图。

**产出**：一致性检查报告与并排截图。  
**完成证据**：适用脚本通过，任务推导规格另有逐项数值及状态核对证据；并排截图里找不到无依据的同类风格漂移。不同语义角色/状态按 U3 区分，不将合理变体强行改成同款。
**不得替代**：`QA0` 终审。本检查是终审 F 层的一部分。

## DS6 线上补充与沉淀

**触发问题**：本地预设缺的东西怎么补，补到的好东西怎么留下来？  
**最低输入**：`DS2` 规格卡里缺的项，或 `DS3` 映射表里需要补的组件。

**步骤**
1. **检索**：按风格族绑定的资源检索：
   - 组件与区块：
     - `npx shadcn@latest search @magicui -q "<关键词>"`；
     - shadcn Blocks；
     - Origin UI；
     - Float UI。
   - 主题：Tweakcn 新主题、shadcn 预设。
   - 动效：走 `MI`。
2. **审查**，规则同 `MI` 第 4 步：
   - 先读源码和依赖；
   - 不运行未审的安装命令；
   - 付费、需要授权 token 或登录的资源不用；
   - 用户已购买许可证的（如 Tailwind Plus）由用户提供代码。
3. **记来源**：每个拿进来的组件和主题都要记录：
   - 来源 URL；
   - 许可证。
   - Float UI 和 Shadcn Studio 免费部分的限制（不得单独再分发、不得做成模板或建站器）也要写明。
4. **沉淀**：验收通过、可复用的新主题或新风格，存进 `style-presets/`：
   - 主题文件放 `themes/` 或 `dto/`，并在 `registry.json` 登记：
     - 风格族；
     - 来源；
     - 许可证；
     - 适用场景。
   - 只来自视觉参考网站的风格，标“人工提取”。
   - 没在真实项目里验收过的，不进预设库。
5. **找不到**：线上也没有合适资源时，按规格卡自己写，来源记“自写”。不得编造“来自某库”。

**产出**：补充资源清单（来源、许可证、用途）；新沉淀的预设与 `registry.json` 变更。  
**完成证据**：每个外部资源都有可核对的来源和许可证；沉淀的预设有验收记录。  
**不得替代**：`MI` 的动效检索与集成规则。

## 风格引擎验收

- 现状清点：写死值有位置、有去向（`DS0`、`DS3`）。
- 探索和应用分开；改已有产品前有用户确认（`DS1`）。
- 规格卡每个值都有来源（`DS2`）。
- token 只有一处定义；页面里没有新的写死值（`DS4`）。
- `style_consistency_audit.py` 通过，并排截图无不一致（`DS5`）。
- 外部资源来源和许可证齐全，没有付费、未审或编造来源的资源（`DS6`）。
