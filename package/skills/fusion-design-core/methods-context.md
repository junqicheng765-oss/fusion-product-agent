# 产品输入到设计语言

对应总框架 N0–N3。目的不是重新做产品定义，而是把上游提供的用户、问题、价值、行业和约束，转换成设计能够执行和验收的行为模型、语境要求与设计原则。

执行纪律：

- 已有证据先复用，不为填模板强制研究。
- 人口属性、行业标签和情绪词只能触发分析，不能直接生成界面结论。
- 每个设计推断必须保留：输入 → 证据 → 解释 → 设计含义 → 影响决定。
- 不同答案不改变本轮设计时，记录但不展开。
- 需要补证时调用现有研究方法，不在本文件伪造用户事实。
- 行业竞品、同类操作竞品和服务同类用户的竞品使用独立的 [methods-competitive.md](methods-competitive.md)，不混进用户研究或项目内部复用。

## CT0 上游输入解包

**对应节点**：N0。  
**触发问题**：上游究竟确认了什么、要求了什么、哪些只是建议手段？  
**最低输入**：原始任务、产品文档或一段上游交接。  
**跳过**：不得跳过；直接制作也至少做最小解包。

**步骤**

1. 原样保存任务原话、文档版本和引用位置。
2. 分开提取：
   - 目标结果。
   - 产品事实与证据。
   - 已确认、冻结和明确不做。
   - 请求的设计手段。
   - 期望交付物。
   - 时间、技术、品牌、合规和资产约束。
3. 每条标 `INPUT_FACT / DESIGN_INFERENCE / ASSUMPTION / MISSING / USER_DECISION`。
4. 对同一问题存在不同版本时并列记录来源、时间和适用范围，不自行拼成一条。
5. 检查请求的手段是否被误写成产品问题，例如“做卡片”“改高级”“加推荐”。

**产出**：上游任务卡、来源清单、冲突和缺口。  
**完成证据**：第三人能指出哪些是上游事实、哪些是设计请求、哪些尚无依据。  
**不得替代**：产品负责人对业务目标、范围和优先级的确认。

## CT1 设计支持深度

**对应节点**：N1。  
**触发问题**：本任务需要设计师直接执行，还是先补分析、探索或验证？  
**最低输入**：CT0 上游任务卡。  
**跳过**：不得跳过；但判断可在一段话内完成。

**步骤**

1. 检查对象、范围、来源、风险、可逆性和完成证据。
2. 判断上游问题与价值是否足以支持本轮设计，不默认全部重做。
3. 选择一个主模式：
   - 直接制作。
   - 局部优化。
   - 问题探索。
   - 方案验证。
   - 设计还原/交付。
4. 写清本轮要交什么，以及哪些上游决定不允许重开。
5. 只有任务涉及新的设计判断时才进入 CT2–BR2；严格还原和低风险直接制作可跳过。新的一屏一定有新的设计判断，不跳过 CT6 和 CT9。

**产出**：主模式、初步终点、进入或跳过语境翻译的依据。  
**完成证据**：能说明为什么需要或不需要研究、流程、UI或视觉判断。  
**不得替代**：用“任务很小”掩盖高风险或不可逆影响。

## N1.5 上游决定预扫描

CT1 后先预扫描 D1–D3，不等待完整设计语境和原则：

1. D1–D3 足够且本轮复用：继续 CT2–CT9。
2. 已有材料但尚未形成问题判断：先调用 R0/R6/R8 中与缺口相符的方法。
3. 问题、用户任务或成功判断缺失且会改变方向：先调用 R1；需要真实过程证据时再调用 R3/R4。
4. 缺口必须由业务、合规或外部事实决定：标 `BLOCKED/WAIT_EXTERNAL`，暂停受影响部分。
5. 研究或补充输入完成后，必须回到 CT9 → BR1 → BR2，再进入完整 D1–D9 调度。

此时可以输出“部分 N0–N3”：已有输入、缺口、所需补证和当前停止点。不得为了通过 N3 而虚构设计任务或原则。

## CT2 行为群体与能力模型

**对应节点**：N2。  
**触发问题**：上游的“目标用户”是否足以指导设计响应？  
**最低输入**：目标用户描述和本轮任务。  
**跳过**：用户行为、能力和任务条件已有近期证据，且不同答案不会改变设计。

**步骤**

1. 将年龄、职业、地区等人口属性只作为线索，不作为分群结论。
2. 针对当前任务提取或补证：
   - 在任务中的角色和责任。
   - 领域熟练度。
   - 数字产品熟练度。
   - 任务频率与最近一次完成时间。
   - 阅读、视听、认知和操作能力。
   - 是否依赖辅助工具或他人。
   - 判断“够了、完成了、可以相信”的标准。
   - 当前替代做法与 workaround。
3. 只有任务步骤、约束或判断标准不同并会改变设计响应时才分群。
4. 有材料时调用 R2 行为分群；真实过程未知且影响设计时，再调用 R3 情境访谈或 R4 观察。
5. 无证据但可安全推进时写工作假设，不生成虚构人物故事。

**产出**

```text
行为群体：
任务角色与责任：
领域 / 数字熟练度：
任务频率：
能力与辅助需求：
完成与信任判断：
当前做法 / workaround：
与其他群体不同的设计响应：
来源与置信状态：
```

**完成证据**：每个群体至少对应一个不同设计响应；如果没有，就合并。  
**不得替代**：用“年轻人、老人、白领、宝妈”等标签直接决定复杂度、字号、颜色或组件。

## CT3 项目上下文与内部复用

**对应节点**：N2。  
**触发问题**：当前设计作为更大项目的一部分，哪些对象、术语、流程、交互、组件和资产可以复用或需要受控扩展？  
**最低输入**：本次任务在整体链路中的位置，以及相关模块、现状页面、设计系统或规格材料。  
**跳过**：完全独立的新产品/任务，且没有可复用的内部产品或设计系统。

外部行业竞品、同类操作竞品和服务同类用户的竞品不在 CT3 分析，分别调用 [methods-competitive.md](methods-competitive.md) 的 CMP1–CMP3。

**步骤**

1. 判断本次设计是：
   - 现有产品的新页面或模块。
   - 跨模块链路中的一个环节。
   - 同一服务在另一端、另一角色或另一触点的延伸。
2. 定位上游入口、下游去向、返回、中断恢复及相邻模块。
3. 检查内部复用：
   - 共享业务对象、名称、字段、状态和权限语义。
   - 已有导航、任务步骤、反馈、错误和凭证模式。
   - 设计系统组件、变量、布局、内容模板和真实资产。
   - 其他角色或模块已经确认的规则，及本环节是否必须保持连续。
4. 只有意图、语义、状态和权限一致时才可直接复用；外观相似但含义不同不能复用同一组件或交互。业务规则只能引用上游已确认来源。
5. 对内部对象和资产分类：
   - `REUSE`：语义和状态一致，直接复用。
   - `EXTEND`：保留系统规则，新增受控变体或状态。
   - `REFERENCE_ONLY`：只借鉴关系或原则，不能直接复用。
   - `NEW`：现有项目没有适配项，需要新增并说明全局影响。
6. 现有共享组件不满足任务时，区分局部变体、扩展共享组件或新建组件；不得静默修改全局组件。
7. 记录本地/共享/全局范围、责任人、授权状态、受影响页面和回归范围。共享 `EXTEND/NEW` 未获授权时标 `USER_DECISION/BLOCKED`。
8. 将每条复用结论映射到 D4–D9；熟悉或同项目存在不等于适合照搬。

**产出**

```text
本次设计在整体项目中的位置：
上游 / 下游 / 关联模块：
内部参考对象：
证据与确认来源：
项目复用：REUSE / EXTEND / REFERENCE_ONLY / NEW
作用范围：本地 / 共享 / 全局
意图 / 语义 / 状态 / 权限是否一致：
责任人与授权状态：
理由：
影响决定：
受影响模块与 D9 回归范围：
```

**完成证据**：已说明复用了什么、为什么可以复用、影响哪些相邻环节及需要回归什么；共享或全局 `EXTEND/NEW` 有责任人授权，未授权项保持阻断。  
**不得替代**：同项目中存在相似组件不能证明语义、权限和状态可直接复用；内部复用不能静默改写产品规则。

## CT4 使用情境与任务重建

**对应节点**：N2。  
**触发问题**：用户在什么条件下开始、完成、中断或恢复任务？  
**最低输入**：行为群体、任务结果，以及近期真实事件记录或可追溯的现状流程材料。没有后者时只能生成明确标注的假设链。  
**跳过**：情境差异不会改变步骤、信息、状态或反馈。

**步骤**

1. 没有近期行为或现状材料时，先调用 R3 情境访谈；用户说不清或说做可能冲突时调用 R4 观察。暂时无法补证但可安全探索时，整条链标 `ASSUMPTION`。
2. 写触发事件，而不是只写时间地点。
3. 记录时长预算、设备、网络、单手/双手、移动/固定、注意力和情绪。
4. 记录参与者、渠道切换、外部工具和必须等待的事件。
5. 用最近一次行为重建：触发 → 第一动作 → 判断 → 工具/找谁 → 卡点 → workaround → 完成/放弃 → 是否回来。
6. 需要多源综合时才调用 R5 同理心地图；跨步骤任务调用 R6 现状旅程。
7. 每个步骤标来源或 `ASSUMPTION`，只保留会改变本轮设计的情境差异。

**产出**：带来源状态的情境卡、现状任务链、关键中断/恢复点。  
**完成证据**：能指出情境具体改变了哪个步骤、信息需求或状态。  
**不得替代**：用“用户很着急、用户很焦虑”代替可观察条件。

## CT5 后果、风险与信任模型

**对应节点**：N2。  
**触发问题**：用户做错、看错、信错或无法恢复时会发生什么？  
**最低输入**：任务中的关键判断、动作或结果。  
**跳过**：纯低风险表达调整，且不影响判断、权限、金钱、健康、隐私或声誉。

**步骤**

1. 逐项列关键判断和动作，而不是只写“金融、医疗、高风险”。
2. 对每项分析：
   - 错误后果及影响对象。
   - 是否可逆、可撤销、可申诉或可追溯。
   - 用户提交前必须看见什么。
   - 数据来源、时间、精度、费用、风险和不确定性。
   - 需要何种确认、权限、留痕和凭证。
   - 失败、部分完成和结果未知时怎样恢复。
3. 将信任拆成可观察来源：信息出处、机构身份、状态透明、承诺兑现、控制权和历史记录。
4. 将影响映射到 D1–D9；视觉只能支持这些要求，不能代替它们。
5. 只要存在重大后果或信任主张，必须给 D9 增加相应的理解、任务、内容/信任或逐项验收要求。
6. 若行业规则或合规结论未提供，标 `MISSING` 或 `USER_DECISION`，不靠常识补全。

**产出**

```text
判断 / 动作：
错误后果与影响对象：
可逆 / 撤销 / 申诉 / 留痕：
提交前必须看见：
证据、来源、时间与精度：
确认、权限与凭证：
失败 / 未知结果的恢复：
影响 D1–D9：
D9 验证或验收要求：
```

**完成证据**：每个高后果动作都有信息、预防、反馈、恢复和与后果相称的 D9 证据要求。  
**不得替代**：“冷静、蓝色、专业感”不能证明产品可信或安全。

## CT6 信息与理解要求

**对应节点**：N2。  
**触发问题**：用户必须理解、比较或记住什么，才能做出正确判断？  
**最低输入**：任务目标、关键判断和内容样例或字段。  
**跳过**：纯资产制作，不改变信息和行动。

**步骤**

1. 按任务步骤列用户当时需要回答的问题。
2. 将信息分为：
   - 不知道就无法理解对象或风险。
   - 完成当前行动所需。
   - 比较或建立信任所需。
   - 可延后查看的帮助与详情。
3. 识别专业术语、数字、单位、时间、来源和长内容的理解风险。
4. 区分用户语言、行业精确术语和法律/合规原文；不能自行改写后称合规。
5. 标出需通过真实内容长度、极限数字或多语言检查的项目。

**产出**：任务问题—所需信息—理解风险—呈现时点。  
**完成证据**：每项首屏或当前步骤信息都能回答一个真实判断问题。  
**不得替代**：本方法定义信息要求，不直接决定最终排版。

## CT7 感知目标与品牌角色

**对应节点**：N2。  
**触发问题**：用户完成当前任务时，需要对产品形成什么判断或感受？  
**最低输入**：品牌依据、任务情境或明确委托。  
**跳过**：严格还原，或本轮不改变视觉表达。

**步骤**

1. 先写用户需要形成的判断，例如“数据有依据、操作可控、结果可恢复”，再写感受词。
2. 区分：
   - 任务带来的必要感知。
   - 已确认品牌属性。
   - 设计团队的审美偏好。
3. 将抽象词转换为可观察边界：
   - 哪类信息必须先被看见。
   - 哪些反馈必须稳定、明确、不过度打扰。
   - 哪些装饰、语气或运动会破坏任务判断。
4. 不在 CT7 指定唯一配色、字体或风格；只有本轮需要解决 D7 时，才在 Figma UI 中用 V4 气质句和同结构候选落地。

**产出**

```text
用户需要形成的判断：
期望感受：
来源：任务 / 品牌 / 委托 / 假设
支持它的可观察行为与信息：
明确不能出现：
待 D7 Figma UI 界面视觉决定：
```

**完成证据**：第三人能判断某个候选是否违反感知目标，而不是只讨论“好不好看”。  
**不得替代**：情绪词不能替代品牌战略、内容信任或任务可完成性。

## CT8 技术、数据与运营现实

**对应节点**：N2。  
**触发问题**：系统能力、数据、权限、内容运营或资产供给会不会改变设计承诺和状态？  
**最低输入**：已有技术/运营事实或明确未知项；不能仅凭行业常识填写。  
**跳过**：纯静态资产且不存在数据、权限、运行状态或持续供给。

**步骤**

1. 分别记录：
   - 数据来源、更新频率、延迟、完整性和精度。
   - 角色权限、可见范围和审批/人工介入。
   - 加载、失败、部分成功、结果未知和同步冲突。
   - 平台、设备、组件及可访问性能力。
   - 内容、图片、文案和人工服务是否能持续供给。
   - 研发、运营和维护成本对本轮范围的影响。
2. 每项区分已确认能力、待验证能力和产品愿望；“计划支持”不能写成“系统已经支持”。
3. 将现实限制翻译成 D4–D9 的范围、状态、反馈、内容、资产或验收要求。
4. 系统/运营事实缺失且会改变承诺时标 `BLOCKED` 或 `USER_DECISION`；可安全模拟时明确模拟边界。

**产出**

```text
技术 / 数据 / 运营事实：
来源与状态：
产品愿望与实际能力差异：
对设计承诺和状态的影响：
影响 D4–D9：
模拟边界 / 外部责任人：
```

**完成证据**：界面不会承诺不存在的数据、权限、实时性、内容或人工能力；关键运行状态有来源。  
**不得替代**：设计师不能代替研发、运营或数据负责人确认实际能力。

## CT9 设计含义矩阵

**对应节点**：N2 收敛。  
**触发问题**：前述信息怎样真正改变设计，而不是停留在用户描述？  
**最低输入**：CT2–CT8 或 CT0 中至少一项与本轮有关的结构化输入。  
**跳过**：直接制作或严格还原且没有新设计判断。

**步骤**

1. 一行只处理一条输入和一个主要设计含义。
2. 按下列链路填写：

```text
输入及来源
→ 可观察行为 / 条件
→ 解释
→ 备选解释
→ 设计含义
→ 影响决定
→ 若错影响
→ 最小补证
```

3. 出现“所以用卡片、所以用蓝色、所以做大字”时，检查中间是否缺行为或任务证据。
4. 同一证据支持相反方案时，不强行收敛；记录关键矛盾交给 BR2。
5. 删除不会改变任何 D1–D9 决定的描述。

**产出**：设计含义矩阵。  
**完成证据**：每条设计含义可追溯、可反驳，并明确影响一个或多个设计决定。  
**不得替代**：推导链完整不等于已验证；证据强度仍需如实标注。

## BR1 设计任务定义

**对应节点**：N3。  
**触发问题**：设计师本轮究竟要帮助谁，在什么情境下改善什么结果？  
**最低输入**：上游产品目标和 CT9 相关设计含义。  
**跳过**：严格按稿还原或确切直接制作。

**步骤**

1. 分开写用户目标、业务目标和体验目标。
2. 写观点句：

```text
【行为群体】在【情境】需要【任务结果】，
因为【有来源的关键障碍/判断】。
```

3. 写设计任务句：

```text
在【情境】下，帮助【行为群体】完成【任务结果】，
减少【关键阻碍或不确定】，
同时满足【业务、风险或技术约束】。
```

4. 只有需要探索干预方向时才写 HMW；HMW 不得预装具体功能。
5. 任务句若换一种完全不同解法就不成立，说明仍写成了解法。

**产出**：目标三层、观点句、设计任务句；必要时附 HMW。  
**完成证据**：至少两种不同解法都可以响应同一任务句。  
**不得替代**：设计任务定义不能改写上游业务范围。

## BR2 设计原则、矛盾与待决项

**对应节点**：N3。  
**触发问题**：后续方案必须遵守什么，冲突时怎样取舍？  
**最低输入**：BR1 和 CT9。  
**跳过**：直接制作或还原只需复用已有规范。

**步骤**

1. 先列硬约束：安全、合规、权限、基本可访问性、冻结范围和正式设计系统。
2. 从 CT9 选择 3–7 条真正会改变方案的设计原则：

```text
因为【事实 / 证据 / 明确假设】，
设计必须【可观察规则】，
不得【具体反模式】，
通过【检查或行为】验收。
```

3. 列关键矛盾，例如完整与效率、熟悉与创新、转化与审慎、品牌表达与任务密度。
4. 先用硬约束淘汰方案；剩余方案再按一个本轮主目标排序。
5. 将不能由设计师决定的业务、品牌、合规或资源取舍标 `USER_DECISION`。
6. 原则没有证据但可暂用时标 `ASSUMPTION/ACCEPT_FOR_NOW`；本轮必须解决时标 `ASSUMPTION/RESOLVE_NOW`。

**产出**

```text
设计任务：
硬约束：
设计原则 1–7：
关键矛盾与主排序目标：
待验证假设：
需要人决定：
明确不做：
```

**完成证据**：给出两个候选时，可以据此淘汰、排序或指出待验证差异。  
**不得替代**：原则数量和措辞漂亮不能替代实际方案与验证。

## N0–N3 通过门

进入完整 D1–D9 下游路由前必须满足；不适用项写 `N/A + 跳过理由`：

- 上游事实、设计推断和假设已分开。
- 只有与本轮设计有关的语境被展开。
- 人口属性未直接生成界面结论。
- 属于大项目且本轮改变 D4–D7 时：必须执行 CT3 或引用有效内部复用审计，并写明复用/扩展项、相邻模块影响、授权状态和 D9 回归范围。
- 若使用行业竞品、同类操作竞品或服务同类用户的竞品支持判断：必须调用对应 CMP 方法并保留样本类型、版本、证据和适用边界。
- 若任务存在重大后果：已有信息、预防、反馈、恢复与 D9 证据要求。
- 若设计依赖技术、数据、权限、内容或运营：CT8 已完成，或缺口已标外部责任人。
- 设计任务、原则和关键矛盾能够实际筛选方案。
- 缺失的外部事实或授权已标 `BLOCKED/WAIT_EXTERNAL`，没有用视觉或交互补空。
