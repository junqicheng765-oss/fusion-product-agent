# 产品方法：从问题到行为与验收

## 先核实前提

区分原始证据、用户决定、推导建议、专业假设和实际验证。整理稿/会议意见不是正式批准；用户说“接口能做”仍需对应文档或运行证据。优先问影响当前取舍的问题，能自己读到的不让用户重复描述。涉及易变、高影响或专业领域的事实按宿主要求回源核实；没有证据写清受阻范围，不以通用知识替代本组织结论。

业务目标不是功能名或“提交成功”。描述当前任务、障碍、后果和期望变化；有依据再给衡量方式，不为每个项目编造指标。若有多种合理方案，比较改变现有路径与新建能力的代价，给出推荐与成立前提。

## 自行构建领域依据

使用者没有说出的专业规则、边界和异常由锤子主动发现与研究。按 [领域构建与价值闭环](domain-and-value.md) 区分可查专业知识、组织事实与经营选择，形成可追溯领域模型和规则；七类产品能力原文只提供判断方法。没有专家在场也先完成可研究和可推导部分，关键未知落实到具体取证动作及受阻范围。

## 由对象与角色讲清方案

按需要建立轻量产品模型：角色/职责 → 对象及归属 → 关系 → 合法状态与转换 → 可执行动作 → 规则与后果 → 异常与恢复。对首次使用明确对象不存在时如何创建、导入或加入；不能直接从熟练用户已配置好的首页开始。

规则至少说清适用角色、触发条件、作用对象、约束、可见结果与失败后的责任。业务资格、事实条件和实现方式分开：一个人能否使用某权益，不直接推出必须远程授权、验证码或实名。参数有来源；待选阈值保留候选，不能把样例金额当真实配置。

## 把方案转成任务路径

每条核心任务写清：谁从哪个入口，在何种前提下看到什么；依次点击/输入/选择什么；系统改变什么对象、反馈什么；退出/中断/失败后如何继续；什么可观察结果算完成。具体程度应支持业务理解和接收方构造用例，不用“系统处理一下”代替行为。

按当前范围检查空/无数据、非法或过期输入、慢网、失败、结果未知、部分成功、重复提交、途中权限变化、并发、异步通知、退出与恢复。只补适用项；发现新能力需求先判断是否超出范围，不因检查清单新增功能。

## PRD与验收

以当前正文维护规则，可按模块组织；稳定ID用于回查而非增加术语。核心路径与每阶段交互说明必须在完整方案或PRD中能找到，模板标题可以改变。需求应对应可验证结果；场景至少含前置、操作、预期、异常/不允许结果和验证层次。

生成用例不等于运行测试；技术建议不等于已通过研发确认；文档逻辑成立不等于接口可用。缺少关键规则时保留受影响段为候选，不靠把所有章节填满宣称完整。

## 专业模型按问题取用

本包唯一正式模型参考为 [能力索引](../knowledge/product-capability-model/capability-index.md) 所链接的原文。七类是观察视角，不是岗位或审批：

| 当前问题 | 主要回查 |
| --- | --- |
| 价值、领域、对象、关系、状态、规则与演进 | P1 |
| 心智、负担、动机、预期与信任 | P2 |
| 概念、动作、状态、复杂信息及语言一致性 | P3 |
| 页面/对象组织、入口、导航及跨空间任务 | P4 |
| 意图操作、可发现、反馈、控制、防误与效率 | P5 |
| 等待、中断、异步、失败、恢复与连续性 | P6 |
| 感知目标、层级、秩序、多通道、包容与品质 | P7 |

定位不清时读 [维度边界](../knowledge/product-capability-model/standards/dimension-boundaries.md)。只读当前相关的二级定义；例子用于找盲点，不移植品牌行为或其他项目答案。正式交接的适用性筛查记录缺证据与不适用的差别；不能把缺证据归到不适用，也不以平均分抵消阻断问题。
