# 正式设计交付：用户体验与产物顺序

用于正式产品界面设计、设计迭代和按稿还原。与[独立文案步骤](product-copy.md)及[产品到设计交接](design-and-demo.md)配合；不要求每个小任务都额外制作探索原型，也不扩大用户指定的终点。

## Demo的统一定义：正式产品前端交付

本包中的Demo，是本轮正式产品的本地前端交付：在约定端、尺寸和场景范围内，界面、交互和文案必须与目标生产版本一致。它交付可直接面向用户的前端体验，不能因名称是Demo而降低完成度，不能只做“让人理解大概意思”的可点击示意。

本地与生产的差别限定在运行和服务接入层：当前在本地运行前端，可用本地数据及受控服务返回替代尚未接入的后端；页面布局、组件样式、内容呈现、用户操作、校验、状态变化、反馈和恢复路径仍遵循同一正式产品规则，不做一套演示专用体验。运行方式、未接入服务和数据来源只写协作/交付说明，不进入用户界面。

- **一致性依据**：已有产品以现有正式界面/设计规范加本轮有效变更为准；0到1以本轮有效设计主稿、产品交互规则及文案基线为目标生产规格。尚无生产环境时不能虚称已与线上逐项比对，后续生产实现应遵循这套有效规格，改动先回同一基线处理。
- **交互必须真的发生**：约定交付范围内全部用户可见操作均须实现并逐项验证，不能以“非核心”为由交静态占位。在本地完成适用的输入、校验、选择/切换、提交、等待、结果展示、返回和恢复；受控返回遵循业务状态和确定场景，不以跳页、弹一句成功、禁用关键操作或主持人代点来代替。后端未接入不能成为省略本轮必要前端体验的理由。
- **缺项就是未完成**：若必要界面/交互/文字仍缺失或与有效规格不符，修复后再交付；确受条件限制的对应范围标为未完成/受阻，不因交付说明写了“模拟”就降低验收标准。原有本轮必做范围不能通过缩小声明变成通过。
- **探索稿另行命名**：用户明确只要线框、草图或探索原型时，按该终点交付并标明性质；它不属于本包默认的正式Demo。已有探索输入要先按正式标准补齐，不能连同其中的假设和临时表达一起交给用户。

## 1. 先识别产物性质

在现有设计任务或状态中记录，不另建审批：

| 产物 | 用途与要求 | 进入正式交付的条件 |
| --- | --- | --- |
| 探索原型 | 只回答指定的结构/流程/行为问题，按需要选择保真度；已知假设、模拟和未覆盖写在协作说明 | 不能自动充当正式设计源；需按本轮产品规则、就绪文案及正式设计标准逐项承接并修订 |
| 正式设计稿/主稿 | 按目标产品实际使用情境组织页面职责、信息、文案、控件、状态、视觉和资产；可分模块形成，不等于全系统已完成或用户已确认 | 输入来源和范围清楚，所需文案就绪，设计决定有有效选择/沿用/委托依据，QA0和内容/呈现检查据实记录 |
| 正式前端交付（Demo） | 本地运行与目标生产版本一致的界面、交互和文案；服务接入层可用本地数据/受控返回，前端体验按正式标准完成 | 按有效源逐项对照画面、实际操作、状态反馈和文字；本轮必要体验缺项不通过，未接入后端单独说明 |

“正式”描述产出标准，不自动表示人已批准、后端已实现或生产可用。代表页风格候选同样面向真实用户任务，但仍是候选；不把候选或自检写成人工确认。

## 2. 制作顺序按当前任务与路线执行

本轮动作/状态明确 → 对应范围文案编写与审查 → 代表页视觉选择或沿用现状 → 正式页面制作/精修 → QA0及实屏核对 → 需要时按同版还原Demo并验证交互 → 产品校对和交接。研究、流程推导可先开展；实际所需的关键选择按既有流程完成，不增加一轮“正式化批准”。

- **已有本产品Figma主稿或已选择Figma**：先在指定主稿完成受影响设计，旧页直接精修，新整页按需生成后精修；按同版Frame/Dev Mode与实际上下文还原Demo。不先本地另造一套Demo再反推主稿；HTML导入Figma仅限实际可用且明确选择的路线，不能冒充默认还原链。
- **明确选择本地设计**：本地页面/组件可以直接作为正式设计载体，同时提供可操作体验；记录其有效版本及检查证据，不强行新增Figma或先做另一份Demo。承诺的可编辑格式仍须真正交付。
- **只要方案或探索原型**：完成约定判断和边界后结束本次任务，不强行升级高保真或全系统设计；后续转正式设计时再检查与补齐。
- **存量迭代/小需求**：复用有效风格、组件、内容和既有决定，仅处理受影响范围；无需重做全部调研、风格选择或探索原型。

探索稿不能因“看起来能点”就成为正式源。若承接探索成果，复用有效的页面职责和行为，明确处理的假设/差异以及正式源版本；不得照搬其中的讲解布局、调试入口或临时文案。Figma能力/权限不足时只暂停受影响制作并引导恢复，不能静默切成本地后报告Figma设计完成。

## 3. 页面面向最终用户

- **结构与交互**：导航、主行动、反馈、返回和帮助服务真实用户任务。制作流程讲解、协作阶段进度、评审问题、状态强制切换和模拟控制放协作说明或独立测试工具，不做成产品常驻功能；这些控件不能成为走通核心任务的必要条件。
- **文字与信息**：使用有效《界面文案基线》原文。不写“本Demo展示”“点击体验此流程”“这里模拟”等制作/评审口吻；不把实现方案、待办、内部ID、注释或待补占位放成用户内容。真实产品本身需要的新手引导、规则说明和安全提示保留，不能为去除Demo味删掉必要帮助。
- **内容与资产**：优先使用获准的现状内容及资产；模拟数据要有合理业务含义、长度和状态关系，不能用“测试标题1”或随意重复内容代替正式设计。模拟值不作为真实经营事实，真实用户输入和引用原文不擅自改写；关键资产/内容缺失按设计方法补齐或明确阻断，不能靠换名宣称完成。
- **正式交互与反馈**：本地数据及受控服务返回只替代服务接入，前端操作、校验、状态变化与可见结果按正式规格完成；无动作或未知结果不显示成功，不凭文案新增撤销/重试等业务能力。服务未接入、数据来源、未验证条件与运行方式写入交付说明，不用“仅供演示”掩盖缺项，也不在用户画面加Demo横幅或演示说明。

## 4. 正式交付检查与回传

沿用设计专家QA0及文案/交互专项复核，不另跑一套平行设计审计。正式设计送审检查实际画面；可操作体验还要实际走核心任务及当前必要分支。逐项记录实际范围与证据：

| 检查 | 不合格时如何处理 |
| --- | --- |
| 产物性质、有效设计源和本轮范围明确；探索候选没有冒充主稿 | 恢复真实状态，补齐有效输入或正式化修订，不靠改文件名升级 |
| 页面信息、动作和文字面向真实用户，实屏与就绪文案一致 | 内容问题回产品文案基线，呈现/测试控制问题由设计修正，再检查受影响页面 |
| 画面完整且有代表性内容/资产，必要操作与反馈可理解 | 按原设计方法补齐或保留受影响范围阻断，不用占位或讲解替代 |
| Figma路线先完成本轮主稿，Demo来自同版节点；本地路线有明确选择和有效源版本 | 补齐主稿/版本对应或恢复约定路线，不用本地新画结果声称已按稿还原 |
| 前端按目标生产规格逐项对照，服务接入证据单独表达；必要前端体验没有被简化 | 未操作的写未动态验证，未接入的写未接入，不从设计通过推导生产可用 |

存在上述缺口时，对应范围交付为候选、待修或未验证，不写“正式交付检查通过”；可交付不受影响部分。小需求可在原有任务中短记，复杂项目按范围索引，不扩成全系统补稿。

成果回复必须分别报告“正式前端体验完成/未完成及差异”和“服务接入情况”，前端缺项不能因服务未接入被豁免。沿用现有记录承接布局/组件/响应、文案和实际交互的规格对照与证据，不新建一份规格副本。成果回复在既有阶段导航之后说明本轮产物性质、设计源及版本、真实覆盖、正式交付检查结论/证据和下一动作；保留[本轮文案审查摘要](product-copy.md#可见成果文案审查摘要)。协作过程和运行边界放成果说明，不写进目标产品画面；只在已有关键决定点使用原生Question。
