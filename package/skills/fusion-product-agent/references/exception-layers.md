# 异常输出：规则、文案与页面行为分层

涉及设计制作/还原时，继续按[呈现复用与制作分流](exception-presentation-reuse.md)先查实际资产，再决定复用、页面内状态、组件变体或独立页面，并保留归并前后覆盖。

用于本轮范围内确有异常处理需求的方案、设计、PRD和交接。先在内部检查适用异常，再按处理结果归并；检查清单不是逐条交付清单。轻量任务可在现有正文中合并表达，不强制新建文件或页面。

## 先归并，再决定哪些状态不同

按业务结果、权威来源、允许动作和恢复责任归并触发原因。网络断开、接口超时等技术现象如果导向同一结果和恢复方式，引用同一条处理规则；仅在结果是否已发生、用户可做什么、责任归属或不可逆后果确实不同时拆出状态。保留原始触发与适用范围供排查，不让每个触发条件自动变成独立功能或页面。

## 对外交付的五层

| 层次 | 写什么 | 避免什么 |
| --- | --- | --- |
| 共享处理规则 | 规则 ID、适用对象/动作、结果判定依据、数据保留、重试或查询原则、责任方 | 在每个 case 和页面重复写同一处理逻辑 |
| 真正不同的状态 | 状态、进入/退出条件、允许动作和权威结果；只列会改变行为的差异 | 把每个错误码或网络现象当成业务状态 |
| 异常清单与文案引用 | 异常 ID、关联规则/状态、对应COPY ID与文案基线版本、动态字段来源和就绪状态；原文读取同一文案基线 | 把后端错误原样透传，或为同一语义在各页面复制多份文案 |
| 页面规则包 | 页面/步骤引用哪些异常 ID，何时出现、在哪里呈现、优先级与阻断、操作去向、输入保留和状态更新 | 重写共享规则或文案；把一张异常矩阵交给研发逐行实现 |
| 代表性验收例 | 每种不同结果与恢复路径的少量前置、操作、可观察结果和不允许结果 | 枚举所有触发条件与页面的笛卡尔积 |

《界面文案基线》是最终文字的唯一有效来源，按[独立文案步骤](product-copy.md)由产品主线编写、审查、修改和维护；异常清单只维护异常ID—规则/状态—COPY ID及有效文案版本的关系，页面规则包通过异常ID引用它。同一语义复用同一文案，只有用户任务或可执行动作不同才提出页面变体及理由，由产品主线审查后写回同一基线。设计负责具体页面位置、呈现方式和页面行为，不另定最终文字。方案阶段缺少页面时先写文案意图与待设计位置，不假定已有页面、接口或查询能力。已有等价文案资源直接复用，不为套模板重编号或再建一套文字。

文案应分别说清已知事实、不确定性和下一步，不承诺未经核实的保存、撤销、重试或处理结果。动态字段标明来源；待业务确认或待接口核实的内容保持候选状态。高影响的结果未知、部分成功、权限变化等只有处理后果相同才合并，不能为了缩短清单抹去真实差异。

设计方法中的异常矩阵可用于内部发现和检查阻断出口。向业务、研发或 QA 交付时按上述层次收敛：研发接收共享规则、差异状态和页面规则；QA 依据这些规则扩展测试数据。代表性例子证明不同处理路径，不构成逐例开发清单，也不替代每条核心需求的可验证验收映射；合并重复触发数据不能删除不同权限、结果未知、部分成功或高风险恢复要求。新增 case 若没有带来新的状态、文案语义、页面行为或验收结果，归入已有条目并记录覆盖关系。

## 必须落到产物：异常页面规则与文案对应

本轮确有面向用户的异常处理时，实际形成对应表或等价关联视图，不能只在交接说明里说“按异常规范执行”。优先扩展已有页面规则包/异常表；无等价产物时用[对应表模板](../assets/exception-page-map.md)，可写入项目 `product/异常页面规则与文案对应.md`。小需求可内联原正文；没有适用异常时说明依据，不为空表新增业务分支。既有ID不重编，不额外强制一种映射ID。

### 渐进形成与就绪

- **方案与交互阶段**：产品主线明确异常触发、关联规则/状态、已知结果、允许操作及恢复依据，并定位页面/步骤；缺页可先记录任务位置和缺口，不伪造Frame。
- **文案步骤**：按已明确行为完成对应COPY与变量审查。对应关系引用同一文案基线；未核实的查询、重试、撤销、保留和自动恢复能力不能靠按钮或提示补出。行为未知时受影响项保持阻断。
- **正式页面制作前**：设计补齐本轮拟制作范围的呈现方式/位置、优先级/阻断、组件/变体、动作去向、输入保留及状态更新。与产品语义冲突返回主线；需新文字返回文案步骤后同步。可先推导交互，不要求先有设计稿才能写此表，也不要求先完成全系统对应表。
- **设计、还原与交接时**：补入实际页面/节点、版本及检查证据，交付当前有效对应表。设计/前端未制作、已制作未验证、实际验证分别记录。呈现已明确但缺实际节点不妨碍开始制作；规则或适用文字未就绪不能据此制作受影响的正式页面。

依据须区分产品约定与接入事实：0到1或新增能力可依据已明确的业务规则、能力合同和责任设计正式前端，不要求后端已实现；本地受控返回仍按正式前端定义替代服务接入，接入未完成另记。阻断的是业务行为、结果依据或恢复边界未明确，不能仅因没有真实接口就省略约定交互；同时不能把本地返回说成真实查询已验证。

### 每组对应关系需要回答什么

| 信息组 | 可直接实施的最低内容 |
| --- | --- |
| 定位与触发 | 页面/步骤及适用端/角色/范围、异常ID、实际触发与已知结果；关联规则/状态及有效来源 |
| 呈现与共用 | 页面内哪个位置、何时显示/消失；引用[共用基线](shared-components-and-rules.md)中的组件/规则及允许变体，确需独立页时引用设计决定 |
| 阻断与优先级 | 阻断哪个动作、允许什么；并存提示的优先级/替换/保留规则按实际需要明确，不只写“高/中/低” |
| 操作与恢复 | 每个用户动作及去向、取消/关闭的结果；输入如何保留、状态何时/凭什么更新、结果返回后如何退出。无操作写明，无需恢复或不适用说明理由 |
| 文字与变量 | 标题/正文/按钮/无障碍提示等角色对应COPY ID、有效文案版本与可读取位置；变量来源/缺值约束引用文案基线 |
| 验收与现状 | AC或等价可观察前置/操作/结果/不允许结果；实际采用的设计/前端版本、证据类型和位置、未验证/阻断范围 |

字段可合并或引用已有章节，不强求宽表或逐字段重复抄写；关键信息不得以空白代替未知。多个技术触发共用同一后果和处理规则时保留归并与覆盖关系；同一异常在不同页面动作不同时写有依据的差异。同一个弹窗、内联提示或页面状态可承载多条关系，对应表不是新增Frame/路由清单，异常如何分层仍按上文。

### 唯一文案与人读可用性

正文、按钮和提示的准确文字只在《界面文案基线》维护。对应表按角色关联COPY ID/版本，并保证接收者能从入口读到该版原文；只给无法读取的ID不算完成。需要一眼查看文字时，可从该基线生成带来源/版本的只读展示或在当前交付导出中展开，不能独立改字。标题与按钮可引用多个COPY ID，不把整段提示硬压成一个ID，也不为页面数量重复编号。

变更文字回文案基线，变更业务含义回产品正文，变更共享行为回共用定义；更新受影响对应关系、设计和前端采用记录。若发现引用过期、缺失、已替代或语义不匹配，明确受影响项并修正或阻断；多个载体版本不同不直接判错，必须核对实际覆盖的有效内容。

### 交付前的对应核对

产品主线与设计在既有审查/QA0中完成：

1. 本轮需要用户感知或操作的异常均可定位到页面/步骤及对应关系；仅内部处理、不展示给用户的项写明处理依据，不强造页面。
2. 异常、规则/状态、共用项、COPY及验收引用可读取且适用，无必需文字缺失/未审查、旧版本误用或不同源含义冲突。
3. 文案中的按钮与恢复承诺确有业务依据；界面实际呈现与动作去向、输入保留、状态更新符合对应规则。未执行动态验证时只报告静态一致，不写“已走通”。
4. 共享修改回查使用位置，代表性验收覆盖真正不同的结果与恢复路径；未触达范围、缺口、处理方及下一动作随交接保留。

成果回复显式给出对应产物入口/版本、本轮范围与就绪状态、关键差异或未覆盖；文案有新编/审查/修订时继续按既有文案摘要展示，不增逐条审批。本表就绪是规格可使用，不能代替真实接口、Figma画面或前端操作验证。

## 简例：提交结果暂时未知

以下仅演示结构，不代表任何项目已具备结果查询能力。

- 共享规则 R1：提交后无法确认结果时，不把超时直接判为失败；先核对原请求，避免盲目重复提交，并保留用户已填内容。
- 差异状态 S1：结果未知；权威结果未返回前，不能显示“提交失败”或“提交成功”。
- 异常清单 E1：关联R1/S1，引用文案基线中的COPY-001及其有效版本。COPY-001的候选标题为“暂时无法确认提交结果”；若真实查询入口已核实，可采用“请先查看处理结果，避免重复提交”和“查看结果”。无查询或输入保留能力证据时，相应规则、动作和文案都保持候选并补证，不据此制作正式按钮。
- 页面规则 P1：提交页在 S1 时引用 E1，说明呈现位置、是否阻断再次提交、操作去向、输入保留及后续结果更新；其他页面只需引用 E1 并写明实际差异。
- 代表性验收例：请求发出后超时进入 S1，页面不宣称失败且不丢输入；权威结果随后返回时按实际结果更新，不产生第二次业务提交。
