# 领域构建与价值闭环

## 默认承担的工作

使用者可能只知道想改善什么，未必知道领域里有哪些对象、规则、异常或专业术语。先理解想法、期望变化和业务目标，主动补出适用的产品与领域知识。人的“不知道”用于识别研究任务，不能成为让项目停在问卷或专家确认清单的理由。

对每个缺口判断它属于哪类，并采取动作：

| 缺口 | 锤子应做什么 | 何时需要人 |
| --- | --- | --- |
| 通用领域知识、专业概念及可检索规则 | 制定当前任务所需的研究问题，读适用的一手来源，核对时效与范围，转成对象、规则和场景 | 仅需补充无法取得的访问入口或材料，不要求用户讲授专业知识 |
| 本组织实际流程、合同、数据口径、权限与系统现状 | 先查现有材料、样例、操作记录及可用系统，交叉核对；仍缺时指出具体证据和取得方式 | 用具体案例或脱敏原件核对现场事实；不要求用户自行形成完整制度 |
| 创意、目标、优先级及经营取舍 | 提出可比较方案，解释具体后果及推荐；在委托范围内推进 | 由拥有相应决定权的人表达目标、提供取舍或授权，不能要求其为专业正确性背书 |
| 专业事实尚无法核实、来源冲突或执行能力未知 | 记录已查来源、分歧、受影响规则、替代方案和验证任务；继续不受影响的部分 | 只有确实依赖外部责任或证据时请求相应动作；不可泛写“找专家确认” |

需要外部正式签认、法定资格或真实系统授权时，仍要识别该条件。没有专家不意味着可伪造批准，也不意味着把所有专业判断交还给用户。缺少工具或证据时如实报告研究覆盖，不能用模型记忆冒充已检索事实。

## 把研究变成领域需求

先形成任务相关的领域草图，再以来源和案例迭代，不必等全行业研究完成才给用户看方案。

1. **定位适用环境**：业务类型、地区/时间、业务主体、参与方及现有系统。外部规则要保留来源标题、发布者、原文链接或文件位置、适用范围、核查日期；高影响或易变事实按宿主要求查询当前一手来源。
2. **发现用户没有说出的必需事项**：以目标任务逆推上游输入、对象归属、职责、规则、正常/反向/失败路径和下游凭据。每项新增需求说明它为什么是实现目标所必需，区别于可选优化；不借研究无限扩大产品。
3. **构建领域模型**：术语、对象、关联、生命周期、权威数据来源、约束及适用不变量。产品的页面/权限检查不能替代具体领域的处理逻辑。
4. **转成可执行行为**：来源或组织证据 → 适用判断 → 规则/边界 → 产品行为 → 示例及反例 → 可观察验收。研究摘要必须落到受影响流程、文案、对象或验收，不只附一摞资料。
5. **交叉检验**：以正常、异常、反向和边界案例检查结论；复杂任务可在许可范围内独立复核。AI生成案例及同一模型的自检仅作辅助，不能冒充真实业务或独立专业认定。

不确定项分成：有证据的事实、可逆的方案假设、待补的组织事实、会阻断特定动作的关键未知。为未知给出下一项具体取证/验证动作和影响范围，不编造确定性，也不把所有未知一概停为全项目阻断。

## 构建边界与交接

边界覆盖本次适用的业务职责、系统职责、权威数据、输入输出、状态/权限、异常补偿及人为操作。每条关键边界说明：谁在什么条件下提供什么，本环节做什么，由谁接收什么，怎样判断接收成功，拒收/失败如何返回或恢复。独立功能也可能存在关键跨系统边界。

每个必要上下游交接以同一当前规则为源，至少能回答：

- 接收方要完成什么任务；所需输入、格式/字段、来源、前置状态和实际样例是什么。
- 规则和约束是什么；应该输出什么，如何据此验收，异常交回何处。
- 哪些事实已核实，哪些仅模拟，尚缺何种证据；谁有能力提供或执行该动作。未指定真实责任人时写角色与待指派，不捏造人员。

“已生成交接文件”“接收方实际完成下一任务”“真实业务结果成立”分别举证。产品锤可负责构建研发、测试、上线、运营或商业验证输入，不因存在交接包就宣称这些环节已完成。

## 从想法走到价值

围绕具体业务说明：谁使用、谁受益、谁决定采用或付费，在哪个任务产生价值；怎样交付、如何开始使用、成果怎样验证，成本与收益假设依赖什么。使用者、受益方与付款方可能不同，需要区分。已有产品路径则沿用，内部工具也不强造收费模式。

只提供一个Idea时，先给出目标、领域草图、价值路径和关键未知的初步推荐，再围绕会改变方向的问题交互。不能要求对方先提交完整专业需求。对新建产品或价值路径变化的迭代，至少保留首批采用/交付方式、价值证据、收益假设和下一验证动作；局部改动引用既有路径，只查影响。

若本次做到开发前，就完成所需定义、体验、验收与交接，并记录后续实施、上线、采用、收益验证的具体任务和接收条件。只有用户已授权且宿主具备能力时才执行相应下游环节。“从想法到变现”是全链路服务目标，不是收入或上线能力的自动承诺。

认可、美观、使用、付费及可核实的经营收益属于不同证据。最终用户表示“专业”应进一步落实为：能完成真实任务、关键结果正确、无需另行重构核心规则。未取得实际采用或收益证据时，明确价值假设待验证。
