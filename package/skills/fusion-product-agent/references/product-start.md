# 产品启动与设计开工条件

产品主线负责目标、领域需求、边界、方案与交接。设计是其中的专业环节：以有效产品输入进行研究、交互与视觉设计，不凭一句产品名称自行确定用途和核心范围。

## 先判断输入能支持什么

从用户原话、已授权项目材料、有效决定和明确委托恢复以下内容；小任务只核对影响本次工作的部分，不要求人填写整张表：

| 内容 | 需要知道什么 |
| --- | --- |
| 目标与用途 | 希望改善谁的什么任务，为什么做；未知时给可能方向和推荐 |
| 使用者与情境 | 谁在什么场景用；AI的候选画像不能冒充真实用户研究 |
| 使用端与现实约束 | 当前任务涉及的设备、平台、现状和必须保留项；可委托的选择给推荐 |
| 核心任务与范围 | 本轮首先跑通什么，明确不做什么；不同方向不能混成默认全做 |
| 本轮终点 | 先讨论、做方案、探索性原型，还是完整产品设计及交接；不能由交付形态反推业务选择已委托 |

每项保留来源：用户表达、既有有效决定、明确委托下采用的推荐、候选假设或未知。采用推荐不证明市场事实、系统能力或行业规则正确；后者仍需实际证据。来源可以是聊天或现有材料，无须为了过关新增表格或审批文件。

## 只有一句想法时的首轮

1. 简短复述已知想法，不扩成一份假定需求。自行做足以解释方向的初步研究，给出可能用途、核心场景和推荐，并说明会产生的主要差异。
2. 把会改变产品方向的问题集中到少量原生 Question 中，通常每轮1–3项。优先校准目标、用户/情境和首期范围，端或交付终点有实质歧义时一并问。可给“按推荐方向推进”，但不能只让用户挑风格、头像、颜色或工具来代替产品目标校准。
3. 发出问题后停止依赖答案的方案定稿与制作。异步问题返回“已发送”不代表已回答；预选项、沉默和时间经过不算选择。原生工具不可用时用清楚的文字问题，不伪称弹窗、不静默代答。可以继续不依赖答案的取证工作。
4. 收到回答后，把本轮目标、适用情境、核心范围/不做项和终点形成可见摘要，注明有效决定或委托；这份摘要无需再强制确认一遍。只有剩余关键分歧需要新的选择。

例如“帮我设计一个掼蛋游戏”只给了产品类型。可提出熟人组局、练习或赛事等候选用途，解释推荐，再校准核心方向；不能自动认定是某个使用端、真人联机和特定运营模式，然后直接交付设计稿或Demo。通用规则、玩法差异、异常与专业方案由锤子研究和提出，不让非专家补专业答案。

## 什么时候进入方案与设计

- 目标、核心情境、当前范围及终点已经有足够明确的输入、既有有效决定，或在明确范围内获得委托，且没有会改变当前方向的未决事项：继续构建领域规则、边界和方案。向用户说明当前依据与下一环节，不因创建文件或内部自检增加审批。
- 仍有关键意图缺口：候选规则、比较方案和文字/简图可以帮助讨论；不能把推断写成用户确认，不能制作依赖该选择的正式设计或完整Demo。普通可逆细节的假设推进不适用于替人确定目标、用户和核心范围。
- 产品交给设计时，附能定位的目标/范围来源或委托、相关规则/场景、业务验收、本轮制作范围及未决影响。设计接单再核对；缺失时回到产品主线补齐，不能在设计决策文件里自行填成“已确认”。设计模块自己的风格与制作停止点继续有效。
- 设计中的业务变化回产品主线处理；产品主线继续组织后续PRD、验收和交接。设计或Demo完成不等于整个产品工作完成。

## 裁剪与委托

- 已有充分需求、确认记录或增量迭代输入时复用，不为走流程再问一遍；局部文案替换、严格还原、咨询或只评审不扩成新产品访谈。
- “按推荐来/你来决定”在已表达或明确委托的范围内有效。明确委托定义产品方向时可据此推荐并推进，记录依据与假设，不强制来回确认。单独一句“帮我设计一个产品”不是全部业务选择的委托；授权制作最终产物也不等于授权跳过方向校准。
- 用户明确只要一版探索性Demo或草图时，可在其授权范围内用假设制作，并在交付说明中区分探索假设、未验证事实和正式产品基线。不要把探索交付冒充目标已确认，也不要在面向最终用户的界面加入讲解式Demo文案。
- “我不懂”意味着锤子应研究、解释具体场景并提供易选推荐，不意味着用户默认接受全部推断。组织事实缺失时先找原件；不能用提问无限等待专家出现。

这是Skill的执行约束，不是宿主工具的强制拦截器。实际是否先提问、是否在等待期间停止制作，需要真实对话行为验证，不能用静态文件检查代替。
