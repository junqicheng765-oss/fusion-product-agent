# 独立步骤：产品文案编写与审查

## 位置与职责

在本轮页面职责、用户动作、状态和操作结果明确之后，正式页面制作之前，由产品主线单独执行文案编写与审查，产出一份《界面文案基线》。设计研究、流程和交互推导可以先开展；不能等排版时再临场编字，也不要求先写完整PRD或全系统文案。代表链路先完成该链路，模块展开时增量补齐。

这是一项有明确输入、输出和就绪条件的工作步骤，不是“设计时顺便润色”或仅在Demo完成后查错。状态入口与成果回复显式显示“当前：文案编写与审查”，附本轮文案基线及版本；沿用[六阶段导航](progress-navigation.md)，不新增逐句人工审批。

产品主线负责内容含义、用词和审查；设计负责信息层级、呈现、可读性及实际画面复核。使用[模板](../assets/interface-copy.md)，默认写入调用者项目的 `product/界面文案基线.md`；已有等价文案资源时以其为唯一有效源，补齐引用、范围、审查记录和版本即可。多模块可分文件，由一个入口索引；不要再复制一套可独立修改的全量文案表。

## 1. 输入与范围

读取当前有效产品正文、目标用户与情境、对象词表、任务流程、页面职责、动作/状态/结果及必要的风险后果；已有产品同时读取受影响的现状文案与风格规范。按现有页面/状态和共享组件确定范围，复用稳定ID；只为真正需要下游引用的文案或同语义共享组补充稳定 `COPY-` ID，修订不换ID。没有文字的装饰不造文案条目，不为填文案表新增业务状态。

缺少动作结果、责任、时限等业务事实时先回产品正文补证，不能用一句“请重试”或虚构承诺补闭环。设计发现新增控件/状态时，先明确其真实行为和依据，再补该部分文案。仅缺表达细节由Agent给出合适措辞，无须使用者懂文案方法；涉及目标取舍、承诺、风险或品牌决定的必要问题才通过原生Question询问。

涉及异常时，按[异常分层输出](exception-layers.md)先归并共享规则和差异状态；异常ID关联规则/状态并引用本基线中的COPY ID及有效版本，页面规则只写呈现和行为差异，不再维护另一份异常文字。无真实恢复能力依据时先补规则/接口事实，不能靠文案新增查询、重试或保存能力。

## 2. 先编写，再审查与修订

先写当前用户真实使用时应看到的文字，再按[界面文案统一质量标准](copy-quality.md)审查。四组标准作为共同入口：面向实际用户、准确且一致、可理解可行动、可被设计与实现使用；其中已整合七大能力的相关要求与正式定义引用，不再另跑一份平行清单。

P3六项负责命名、动作、状态、复杂信息转译、语言一致性和语境适配；P1提供事实依据，P2/P4/P5/P6/P7按当前情境补充理解、信息位置、操作反馈、时间过程和感知验证要求。按本轮范围筛选并细读相关定义，不为每句文字重跑48项。内容缺口、行为缺口与呈现缺口按主责回查，不能只改措辞掩盖问题。

编写与审查时落实内容要求；需要制作后才能核验的风险显著性、字号/长值适配、真实操作与跨通道一致等，先写入文案基线和设计任务的验证要求，制作后再取证。未完成实屏验证不阻断已就绪的文字交给设计，但不得提前标成全部文案/交互通过。

在同一产物的审查记录中保留问题、修改前后、依据、结论和残留项；无需为每句无问题文案抄一遍审查意见。分别记录“Agent已编写”“Agent已审查修订”“用户已决定的关键项”，不得把自检写成人工确认。文字审查通过不证明实屏排版、实际理解或交互已通过。

### 文案变更的同批确认

沿设计方法 U1/U6，在新增、删除、合并或改写的成果文案进入排版、生图或实际页面前，由产品主线在同一审查摘要中合并展示原文/位置、建议内容、依据及含义/范围影响，通过原生 Question 取得具体确认。初次编写如实说明没有旧版；确认前保留建议稿，不把 Agent 自审记成人工批准。已有具体有效的逐项或整批批准按版本和范围复用，不重复询问；笼统的优化委托、工具路线或风格选择不代替文案批准。已有有效且本轮不变的文字、纯排版和真实变量替换不触发新确认。必要业务/承诺决定仍回对应决定点，不新增逐句审批或另一套文案表；不依赖未决文字的工作可以继续。

## 可见成果：文案审查摘要

触发本步骤的编写、审查或修订，以及首次交给设计使用时，在本轮最终可见回复中展示以下摘要；基线头部保存同一摘要，详细发现仍记在原有审查与修改记录中，不新建第二份文案源。开始工作时说明本次处理范围，完成后给可核对结果，不能仅写“文案检查通过”。

- **产物与范围**：给真实可打开的文案基线链接、当前版本及对比版本，注明新编并审查、局部修订复查，或复用既有已审查版本；覆盖哪些页面/状态/共享组件，哪些未覆盖。
- **检查与结论**：说明本轮采用的具体质量判断及事实依据，例如动作结果与规则是否一致、术语和下一步是否清楚；区分内容已审查就绪、局部阻断、实屏检查和动态验证，不能用内容自检替代后两者。
- **关键变化与原因**：选对含义、理解或动作有影响的代表项，展示COPY ID/位置、原文 → 当前文字及理由，并链接完整修改记录。初次编写没有历史版本时写“首次编写，无项目旧版”，只有实际保留草稿才可展示草稿修订，不能编造旧文案；新增/删除分别注明。没有改动如实说明复用或未发现需修改项，不硬凑发现、数量或差异。
- **阻断与下一动作**：说明残留问题、影响范围、谁处理以及怎样恢复；无阻断就说明交给设计使用哪版、接下来形成什么。业务含义、风险承诺等必要人工决定回对应决定点；普通表达修改由 Agent 拟稿、自审，实际使用前沿上述同批文案确认复用或取得具体批准。

摘要随当前实质变化展示，不把全部文案逐句贴进对话。仅继续使用已展示过且未变的基线，简短注明沿用版本及未新增审查即可；已展示的旧发现不得反复冒充本轮变化。实屏复核引起改字时更新同一基线，展示本次增量；只改排版时说明呈现修正、文字未变。

**连续推进仍要可见**：审查后输入和授权足够时直接继续设计，不为展示摘要另设审批或等待。即使最终回复的当前位置已经是视觉选择或制作，也保留本轮文案审查摘要。设计/Figma模块把基线版本、核对性质、关键变化/无变化及残留随成果回传；产品主线负责最终展示，不能用“子模块已检查”代替。文件已保存、摘要已对用户展示、用户已决定分别记录；摘要只写入状态文件不能算已展示，恢复时补出尚未展示的有效结果。

## 3. 文案就绪后，才进入对应页面制作

本轮范围就绪须同时满足：

1. 所需页面/状态/共享组件文字及动态模板已覆盖，能定位条目、有效版本和产品依据。
2. 编写和审查已完成；影响该范围的业务含义、关键后果、适用文案变更批准与必要人工选择不存在未解决阻断。
3. 设计任务带入文案基线入口与版本、适用COPY ID和原文、变量/呈现约束，以及统一质量标准中需制作后验证的适用要求；不是只给一个无法读取的表名或ID。

无需逐句请人批准。已有有效且本轮不变的文字直接复用，局部改字只回查影响范围。只读配置/资产检查、设计研究和无关范围可以继续；探索草稿可标清缺口，但不得拿自动补字的草稿冒充正式设计交付。

## 4. 交给设计与Figma执行

按[产品到设计交接](design-and-demo.md)和执行任务包（技能 `fusion-figma-workflow` 内的 `references/task-package.md`）传递文案。所有制作路线都使用同一基线：Figma Agent提示词、Computer Use编辑、明确选择的本地制作和Dev Mode还原均不得自行润色、改写含义或填入讲解文案。需要制作的方向候选按 DS1 使用同一份就绪的代表页文案，避免把文案差异误当风格差异。

设计专家的方法U6承接产品主线已审查就绪的文案，不重新编写另一套文字，继续做呈现与可用性判断；不额外要求逐句冻结审批。允许按约定换行、排版、动态值替换；需要缩写、增删、改变按钮或补状态时，带具体位置和理由回到本步骤。产品主线判断并更新同一基线及版本，再同步受影响Figma、Demo和交接材料；纯表达修订由 Agent 提案并沿同批文案确认处理，业务变化回相应决定点；有效批准复用，不在设计环节再设一轮确认。不能让代码、画布和文案表各留一版。

## 5. 制作后的实屏对照

设计稿形成后核对实际文本与当前文案基线的对应、长值/缺值、截断遮挡、层级、遗漏与状态错配；Demo展示前仍执行文案与交互专项复核（技能 `fusion-figma-workflow` 内的 `references/demo-review.md`），实际验证提示与动作结果一致。发现内容问题回本步骤修订，呈现问题由设计修正，行为问题回交互/实现环节；不要把所有问题都用改字掩盖。

交接同时提供当前文案基线版本、设计节点/版本和Demo版本的对应及检查证据。未实际看图或操作的部分据实标明。文案定稿是设计的输入，实屏复核是另一项证据，两者不能互相代替。
