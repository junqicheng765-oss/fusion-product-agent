# 工作合同：本次做到哪里

开始或续做时从已有输入恢复以下内容；缺失项由Agent先查资料，不把整表交给用户填：

新产品或目标/范围不明时，先按[产品启动条件](product-start.md)校准使用者意图。研究负责补专业知识，不能从公开资料“查出”使用者为什么要做、要优先解决谁的问题。有效输入或明确委托足够时直接复用，不增加固定审批轮次。

- 使用者知识条件：默认产品和领域知识不完整、没有专家随时补位；识别需要锤子自行研究的部分，不能把知识考试作为启动条件。
- 决策用途和真实问题：谁在什么任务受阻，改善什么，现状依据是什么。
- 范围：目标用户、使用端、核心任务、必要对象和依赖，哪些本期明确不做。
- 保留项：现有资产、设计系统、已确认行为、受保护文件/页面和责任边界。
- 成果与终点：咨询/方案/PRD/设计/可操作Demo/交接中本次明确要求哪些；谁接收、何时算完成。
- 价值路径：当前任务怎样连到交付、真实采用、付费或可核实经营收益；本轮验证到哪一步，下游接收什么。
- 判断依据：原始来源、当前决定、约束、尚未证实的事实或能力；没有数据不编造收益和目标值。

## 裁剪与默认终点

| 用户请求 | 默认产出与结束 |
| --- | --- |
| “分析/帮我判断/整理待确认清单” | 结论、依据、取舍或可填写行动清单；不自动造PRD、Demo |
| “只做方案/只梳理需求” | 指定范围的流程与规则方案，标明待决和验证责任；无需Demo |
| “完整产品设计/一直到开发前” | 产品正文、必要设计、可操作有样式Demo、验收与设计/研发交接；结束于进入生产开发前 |
| “完善已有Demo” | 读取本次影响的现状与规则，修改对应链路，验证共享影响；不重建整个产品 |
| “只评审” | 指定版本与范围的发现、影响、建议和待验证；不修改原件 |
| “继续” | 承接已授权未完成工作与当前终点；未获明确审阅的业务取舍不会因此自动确认 |

“原型”单独出现且完成深度不明确时，先依据上下文判断是结构、静态设计还是可操作体验；差异会改变成本和交付判断时才问。没有必要时不把常识性实现选择推给用户。

工作优先级：有效的任务范围与业务决定 → 当前可核实的业务/系统证据 → 本包运行合同与产品判断方法。决定能指定期待行为，不能证明接口存在、法律适用或用户研究结论。来源冲突先检查时间、范围、效力，不用“最新文件”自动覆盖正式决定；受影响部分保持待决。

## 持续推进

推进过程按[流程位置展示](progress-navigation.md)维护产品六阶段及适用的设计四步骤。每次成果回复首行显示当前位置与真实状态，结尾说明下一动作；展示路线不意味着每步都要人批准，也不因合并步骤而取消导航。

完整设计按“目标与创意交互→领域研究与规则/边界构建→方案→代表体验→模块→交接与价值验证任务”形成反馈闭环。研究随证据与体验反馈迭代；与人的交互贯穿目标校准和业务场景核对，不局限于开场访谈。核心对象或高风险规则必须在相关操作制作前足够明确，不需等每项细节全部定稿才给代表体验；也不以代表路径通过代替其他约定核心任务的完整覆盖。

产品启动与关键业务取舍必须有有效输入或委托，不能因窗口合并而消失。设计在产品主线内承接有效任务，步骤、风格选择、停止点和终审由[设计专家](../../fusion-design-core/SKILL.md)负责，不适用旧融合包的简化节奏。文件生成、格式检查、内部能力核查、快照和工具恢复不增加审批。已有足够依据和授权的可逆工作直接完成；未决影响一个模块时继续其他独立模块。

完成时明确三件事：本轮哪些成果已具备，依据哪种确认/委托与实际验证，哪些依赖或下游工作仍未完成。授权范围内的产品交付可完成而真实生产依赖仍待验证，分别记录。
