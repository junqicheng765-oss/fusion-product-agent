# 异常分层：真实对话回归用例

以下检查应在加载本包的新会话里实际执行；静态文档和脚本通过不代表模型行为已验证。每次记录宿主、模型、包版本、用户原话、有效产品依据、实际产物及异常 ID 引用，分别判定通过、失败或未执行。

| 场景 | 输入 | 应观察的行为 | 失败信号 |
| --- | --- | --- | --- |
| 多个技术触发共享结果 | 已有提交任务，超时与断网都无法确认提交结果，且没有已核实的结果查询能力；要求产出开发前规格 | 将触发映射到同一共享规则和“结果未知”状态；文案不声称失败或提供不存在的查询入口；页面规则说明如何避免重复提交，输入保留仅在现有能力有依据时承诺；验收例只覆盖不同结果/恢复路径 | 每个触发各造一套功能、文案和页面；把超时写成失败；虚构“查看结果”按钮 |
| 真正不同的业务结果 | 同一批处理可能全部失败、部分成功或结果未知；权威返回与允许重试动作已给定 | 只有结果、允许动作或恢复责任不同才拆状态；共享规则不被每个 case 复制；各状态有清楚的退出条件 | 为压缩篇幅合并不同后果；逐错误码列状态；规则互相矛盾 |
| 一份清单覆盖多个页面 | 同一异常会在提交页和记录页出现；两页任务和可执行动作不同；要求设计任务与交接包 | 异常清单维护异常ID与COPY ID/版本关系，一处文案基线维护最终文字；两个页面分别引用 ID，写展示时机、位置、阻断、操作去向、输入/状态更新；确需文案变体时说明原因 | 两页各维护独立文案且语义冲突；页面规则只列异常名，没有行为；把页面变体误写为新的业务状态 |
| 轻量咨询 | 用户只问“该考虑哪些异常”，尚未确定产品页面 | 给归并原则、适用异常和待核实项；文案位置保持候选，不强制生成页面规则文件 | 虚构页面、接口与操作按钮；输出成套开发任务 |

复核时再检查设计回传、产品正文、Demo和研发/QA交接是否沿用同一规则与异常 ID。新增测试数据若未改变结果、文案语义或页面行为，应归入已有条目，不增加开发项。
